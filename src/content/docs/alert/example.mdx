<Callout variant="info" title="Three cases threaded through every chapter">
The three cases introduced on this page run through the rest of the methodology. The finance-team phishing case (real intrusion, endpoint-origin) ends in an escalation to incident response. The Cursor IDE Empire-pattern case (false-positive) ends in a documented close at triage. The SaaS token-theft case (real intrusion, identity-origin, no endpoint evidence at any point) also ends in an escalation, reached by a different evidence path. All three produce a record an auditor can read months later. The Alert chapter is where each case starts.
</Callout>

<Callout variant="warn" title="The cases are illustrative, not photorealistic">
Both walkthroughs are cleaner than real telemetry. Live cases have missing parent processes, offset timestamps across log sources, partial coverage on the host you most need, retention windows that end before the staging activity, and one user who didn't enable MFA. The cases are written to teach the methodology cleanly, when you apply them in production, expect to spend additional time reconciling sources, filing tooling-gap tickets, and noting "unable to determine" where the evidence runs out. The methodology is what gives you a place to stand when the data isn't clean; it doesn't pretend the data is.
</Callout>

<ChapterExample
  title="Case A · The finance-team phishing alert"
  scenario="A SIEM rule fires at 09:11. On a finance laptop, a Word process opened from Outlook spawned cmd.exe, which spawned PowerShell with -NoProfile -WindowStyle Hidden -EncodedCommand. The destination of the resulting network call is a domain registered four days ago. The named user is dlin, a finance analyst."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Hand to Subject"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>Before anything else, the analyst reads what fired and why. The rule's logic chains three behavioral signals: <strong>an Office process spawning a shell (Outlook → winword.exe → cmd.exe → PowerShell)</strong>, <strong><code>-EncodedCommand</code> with <code>-NoProfile</code></strong> (a near-universal indicator of automated execution), and <strong>outbound traffic to a low-reputation domain</strong> within 30 seconds. The rule is a behavioral-analytics rule, not a signature. False-positive rate is documented as roughly 1 in 200 fires; the rule has high precision when the chain is complete.</p>
    <p>Three signals in a single chain is far more weight than any one of them would carry alone. The analyst starts from a strong prior before even opening the alert payload.</p>
    <p>One modernization note: since Microsoft began blocking internet-sourced macros by default in 2022, this classic chain requires the user to unblock the document or the file to arrive without the Mark of the Web (via an ISO or ZIP container, for example). Much commodity initial access has shifted to LNK smuggling and fake-update lures; the macro chain still appears, it is just no longer the default path.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four-dimensional validation:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The parent-child chain matches a textbook initial-access pattern used by <DefineTerm term="PowerShell Empire">An open-source post-exploitation framework that uses PowerShell agents on Windows and Python agents on Linux. Empire was widely used by red teams and continues to influence threat-actor tradecraft. Many real-world intrusions still show Empire-style command-line and network patterns.</DefineTerm> and similar PowerShell-based agents.</li>
      <li><strong>Environmental.</strong> Finance analysts on this laptop class do not normally invoke PowerShell. The host's 30-day baseline confirms it.</li>
      <li><strong>Intelligence.</strong> The destination domain is registered four days ago, hosted on a bulletproof provider, low prevalence, and resolves to an IP block previously seen in commodity-phishing reporting.</li>
      <li><strong>Business.</strong> dlin has read access to the cloud finance reporting platform via federated SSO. The laptop is the trust pivot for a regulated-data system.</li>
    </ul>
    <p>All four context dimensions agree the signal is worth a deeper investigation. None of them is decisive on its own; the combination is.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <p>Structured extraction from the alert payload:</p>
    <ul class="example-step__list">
      <li><strong>Command line.</strong> <code>powershell.exe -NoP -W Hidden -EncodedCommand &lt;base64&gt;</code>. The base64 decodes to a small downloader that reaches the suspicious domain.</li>
      <li><strong>Process tree.</strong> outlook.exe (PID 5212) → winword.exe (PID 7420) → cmd.exe (PID 8104) → powershell.exe (PID 8128). The winword.exe start time aligns with an attachment-open event in the mailbox audit log.</li>
      <li><strong>Network.</strong> 09:11:43 UTC outbound HTTPS to <code>invoice-records[.]com/upd</code>. Self-signed TLS cert. Approximately 18 KB transferred.</li>
      <li><strong>File system.</strong> <code>%TEMP%\upd.ps1</code> written at 09:11:44 UTC. SHA-256 captured.</li>
      <li><strong>Identity.</strong> Active session: dlin@corp. Logon type 2 (interactive). MFA satisfied at the 09:08 interactive login.</li>
    </ul>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> reading "MFA satisfied" as evidence the account is safe. MFA proved a human logged in at 09:08; it says nothing about what ran under that session three minutes later. The alert is about post-authentication behavior, and clean authentication does not weaken it.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Frame the hypothesis</h3>
    <p>Alert finishes by stating the hypothesis the next phases will test. <strong>Working hypothesis:</strong> an attacker delivered a phishing email containing a macro-bearing document; dlin opened the attachment; the macro launched the cmd → PowerShell chain; the resulting agent established outbound C2 to a recently-registered staging domain. The case looks like a textbook Empire-style initial access.</p>
    <p>The phrasing is deliberate. The analyst is not declaring an incident. They are recording an actionable hypothesis with explicit evidence and known gaps, so Subject knows where to expand the investigation.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand to Subject</h3>
    <p>Subject inherits a structured starting point:</p>
    <ul class="example-step__list">
      <li><strong>Named entities.</strong> dlin (user), laptop-finance-09 (host), invoice-records[.]com (external domain), the originating sender (TBD via mail log pull).</li>
      <li><strong>Open questions.</strong> Who else got the email? Did anyone else execute the macro? What did the federated cloud session do, if anything?</li>
      <li><strong>Confidence.</strong> High on the parent-child chain (complete telemetry, corroborated across process tree, mailbox audit, file system, and network); low on attribution (no actor signature, only TTP-level match to commodity Empire-style tooling). Labels per the <a href="/docs/documentation/standards#confidence">shared rubric</a>.</li>
    </ul>
  </div>

</ExampleStepper>

</ChapterExample>

<KeyTakeaway>
The Alert phase did not declare compromise. It produced a structured, defensible hypothesis with explicit evidence and known gaps. Subject picks up from here. The same case continues on every subsequent chapter's example page.
</KeyTakeaway>

## Case B · The developer-workstation Empire-pattern alert

The same Alert methodology applied to a very different signal. A second alert fires later the same day, on a different team's laptop, and the parent-child chain looks superficially similar, but the host, the user, and the binary all tell a different story.

<ChapterExample
  title="Case B · The Cursor IDE Empire-pattern alert"
  scenario="A behavioral-EDR alert fires at 14:03 on a macOS developer workstation. A signed helper binary (Cursor Helper, part of the Cursor AI-assisted IDE) spawned a child process that disabled its sandbox and made encrypted outbound network calls. The detection mapped the pattern to known Empire-style post-exploitation behavior. The named user is a frontend engineer."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Hand to Subject"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>The rule that fired is a cross-platform behavioral-analytics rule looking for "process disables its sandbox, spawns helper, opens encrypted outbound socket." The rule was originally written from an engagement against an EmPyre agent (the Python 2.6/2.7 macOS/Linux sister agent to PowerShell Empire, merged into the framework in Empire 2.0 in 2016, both names refer to the same lineage) and was later ported to macOS. Documented false-positive rate on macOS developer hosts: ~6× higher than on managed productivity laptops. That is a known calibration issue, captured in the rule's metadata.</p>
    <p>The rule's confidence on this host class is therefore lower from the start. The analyst notes that explicitly before opening the payload.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four-dimensional validation reads differently from Case A:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The pattern (disabled sandbox, encrypted outbound from a helper process) does overlap with Empire's macOS agent behavior at the surface level. But the binary itself is signed and notarized by the vendor, and the install path is a system-managed application directory, not a user-writable staging area.</li>
      <li><strong>Environmental.</strong> The host is a managed developer workstation. Helper-process activity from IDEs is part of the daily baseline. The user's peers show the same pattern on the same vendor binary.</li>
      <li><strong>Intelligence.</strong> No prior incidents involving this binary or vendor. The TLS destination resolves to the vendor's documented inference infrastructure with a valid cert.</li>
      <li><strong>Business.</strong> Source code exposure exists, but the binary's runtime behavior is consistent with the vendor's documented operating mode.</li>
    </ul>
    <p>Three of the four context dimensions point away from compromise. The technical dimension has a surface match but is contradicted by deeper context. The methodology calls for continuing the investigation, not closing the alert, the hypothesis is now "likely false-positive, confirm via Subject and Uncover."</p>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> treating "signed and notarized" as a clear on its own. Signed malware exists, and so do stolen certificates; the signature proves who published the binary, not that its behavior is benign. What carries the weight here is the combination: signature <em>plus</em> system-managed install path <em>plus</em> peer-group baseline <em>plus</em> vendor-documented behavior. Any one of those alone is a weaker claim than it feels.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <ul class="example-step__list">
      <li><strong>Command line.</strong> <code>/Applications/Cursor.app/Contents/Frameworks/Cursor Helper (Plugin).app/Contents/MacOS/Cursor Helper (Plugin) --type=utility ...</code>. Vendor-standard.</li>
      <li><strong>Process tree.</strong> launchd → Cursor; the main Cursor process spawns Cursor Helper and Cursor Helper (Plugin) as direct children (Electron helpers are children of the main app, never of each other). launchd is Apple's platform-signed init process; the three Cursor binaries are signed by Anysphere (Developer ID) and notarized by Apple.</li>
      <li><strong>Network.</strong> Multiple TLS connections to <code>*.cursor.sh</code> and to a small set of LLM-inference hosts, all with valid certificates, all resolving via standard public DNS.</li>
      <li><strong>File system.</strong> Reads in the user's home and the Cursor application support directory. No writes outside expected paths.</li>
      <li><strong>Identity.</strong> Active session: a frontend engineer. SSO login at 09:14 with FIDO2 second factor.</li>
    </ul>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Frame the hypothesis</h3>
    <p><strong>Working hypothesis:</strong> the detection logic correctly recognized a process-behavior pattern that overlaps with Empire-style macOS post-exploitation tradecraft. The binary, signature chain, install path, and behavioral baseline all suggest this is the documented operating mode of a vendor-supplied IDE plugin host, not adversary tooling. Subject and Uncover will either confirm the false-positive read or surface signals that override it.</p>
    <p>The hypothesis is deliberately not "definitely not malicious." The Alert phase records what the evidence permits, not what the analyst feels.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand to Subject</h3>
    <p>Subject inherits a different starting point from Case A, narrower, but with explicit caveats:</p>
    <ul class="example-step__list">
      <li><strong>Named entities.</strong> The frontend engineer (user), the macOS laptop (host), Cursor Helper (Plugin) (binary), the vendor's inference endpoints (external).</li>
      <li><strong>Open questions.</strong> Does the binary's behavior match peer-group baselines? Are there detection-tuning opportunities for this host class?</li>
      <li><strong>Confidence.</strong> High on the binary identity and signature chain (signed, notarized, corroborated by vendor documentation); medium on runtime posture (sandbox-disabled behavior is intrinsically harder to baseline).</li>
    </ul>
  </div>

</ExampleStepper>

</ChapterExample>

<Callout variant="info" title="Two cases so far, one methodology">
Case A produced a hypothesis pointing toward compromise. Case B produced a hypothesis pointing toward false-positive. The Alert phase did not "decide" either. It produced the structured starting point Subject needs in either direction. The methodology is what makes both verdicts defensible, including the eventual close at triage for Case B and the escalation to IR for Case A.
</Callout>

## Case C · The SaaS-tenant token-theft alert

The third case never touches an endpoint. There is no process tree, no command line, no file write. Everything the analyst will ever see lives in the identity provider's sign-in log and the SaaS tenant's audit log, and the methodology has to work anyway.

<ChapterExample
  title="Case C · The replayed session on the mail tenant"
  scenario="A SIEM correlation rule fires at 09:15. The identity provider flagged a risky session at 09:03: a session token for rvega, a customer-success lead, was presented from a hosting-provider IP in another country eleven minutes after her normal corporate sign-in, with a different browser fingerprint. Three minutes later, the tenant audit log recorded a new inbox rule on her mailbox. No endpoint alert fired anywhere."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Hand to Subject"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>The rule is a two-signal correlation: <strong>an IdP risk event (session token presented from a new autonomous system with a mismatched browser fingerprint)</strong> joined to <strong>a new inbox rule created on the same account within 30 minutes</strong>. Either signal alone is noisy: travel and VPNs trip the first, and users create mail rules all day. Together they describe one specific attack: a stolen session being used, then hidden.</p>
    <p>The join key is worth noticing before the payload is even open. Nothing here shares a host or a PID. The two events are joined on the <strong>account and the session</strong>, which is exactly how the <a href="/docs/alert/parsing/cloud-identity">cloud and identity parsing page</a> says this class of alert must be read.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four-dimensional validation:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The 09:03 sign-in reused an existing session token: no password entry, no <DefineTerm term="Multi-Factor Authentication (MFA)" display="MFA" /> prompt. A legitimate new device would have triggered both. Token reuse without an authentication ceremony is the signature of <DefineTerm term="Session Hijack" display="session hijack" /> via a stolen cookie.</li>
      <li><strong>Environmental.</strong> rvega's 90-day sign-in baseline is two devices, one city, one ASN. The 09:03 presentation is a first for the ASN, the geography, and the fingerprint. The 08:47 sign-in that preceded it was normal in every dimension.</li>
      <li><strong>Intelligence.</strong> The source IP belongs to a VPS provider whose ranges appear in current reporting on adversary-in-the-middle (AiTM) phishing kits, which proxy the real login page and capture the session cookie after MFA succeeds.</li>
      <li><strong>Business.</strong> rvega's mailbox holds customer contract and billing threads. Historically this is the staging ground for payment-redirect fraud, and the mailbox contents are customer personal data with regulatory weight.</li>
    </ul>
    <p>All four dimensions point the same direction, and none of them required an endpoint.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <p>Structured extraction, from identity and tenant logs instead of a process tree:</p>
    <ul class="example-step__list">
      <li><strong>Sign-in chain.</strong> 08:47:19 UTC, corporate laptop, MFA satisfied, home ASN. 08:52:41 UTC, click on a "shared document" link recorded by the email gateway. 09:03:12 UTC, the same session ID presented from the VPS ASN, new fingerprint, no MFA event.</li>
      <li><strong>Session.</strong> One session ID spans both presentations. That single field is what makes this one story instead of two logins.</li>
      <li><strong>Tenant audit.</strong> 09:06:55 UTC, new inbox rule named <code>.</code> (a single dot): messages containing "invoice", "payment", or "bank" moved to a subscriptions folder and marked read.</li>
      <li><strong>Consent grant.</strong> 09:09:30 UTC, OAuth consent to an unverified application named "Mail Backup Sync" with offline mailbox-read scopes.</li>
      <li><strong>Identity.</strong> rvega, customer-success lead. No admin roles. Access to the CRM and the shared billing mailbox via group membership.</li>
    </ul>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> the session ID field. Read as two sign-ins, 08:47 and 09:03 look like a normal morning plus a VPN; read as one session presented twice with no second authentication ceremony, they are a theft. The single join field is the difference between closing this as travel noise and catching the intrusion.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Frame the hypothesis</h3>
    <p><strong>Working hypothesis:</strong> rvega followed a phishing link to an AiTM proxy that captured her session cookie after a legitimate MFA approval; the attacker replayed the session from a VPS, created an inbox-hiding rule to conceal payment-themed mail, and consented an OAuth application for persistent mailbox access. The pattern matches current business-email-compromise staging: the attacker is positioning to read and eventually redirect payment conversations.</p>
    <p>As in Case A, this is a hypothesis with named evidence, not a declared incident. The difference is the evidence type: every artifact is an identity or tenant event, and confidence rests on the session join, not on a process chain.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand to Subject</h3>
    <p>Subject inherits an identity-shaped starting point:</p>
    <ul class="example-step__list">
      <li><strong>Named entities.</strong> rvega (user), the hijacked session ID, the VPS source IP, the inbox rule named <code>.</code>, the "Mail Backup Sync" OAuth application, and the phishing link's domain from the 08:52 gateway record.</li>
      <li><strong>Open questions.</strong> Who else received the same link? Did anyone else's session present from that ASN? What has the consented app already read? Is the attacker session still alive right now?</li>
      <li><strong>Confidence.</strong> High on session theft (single session ID across both presentations, corroborated by the fingerprint mismatch and missing MFA ceremony); medium on the AiTM delivery mechanism (inferred from the link click timing, pending the gateway's URL verdict); labels per the <a href="/docs/documentation/standards#confidence">shared rubric</a>.</li>
    </ul>
  </div>

</ExampleStepper>

</ChapterExample>

<Callout variant="info" title="Three cases, one methodology">
Case A pointed toward endpoint compromise, Case B toward false-positive, Case C toward identity compromise with no endpoint in the story at all. The same five moves produced all three: read the detection, validate in four dimensions, parse the metadata, frame the hypothesis, hand off named entities. The evidence types changed; the methodology did not.
</Callout>

<KeyTakeaway>
The Alert phase is the anchor for everything that follows. Three different alerts produced three different hypotheses because the detection mechanism, validation, and parsing were applied to each, and Case C proves the point the parsing chapter makes: when there is no process tree, the identity chain is the spine of the case. All three cases continue on every chapter's example page that follows.
</KeyTakeaway>
