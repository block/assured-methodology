<Callout variant="info" title="Where this fits in Alert">
<DefineTerm term="Parsing" /> is the third pillar of the Alert chapter. Detection mechanisms explained how the engine decided. Validation tested whether the signal is real. Parsing extracts the <DefineTerm term="Metadata" display="metadata" /> at the level of detail the rest of the investigation needs. Without it, the analyst is working with an abstraction.
</Callout>

This matters because adversaries hide their intent inside the very fields you would parse. An EDR alert might report `powershell.exe` executing with an encoded command parameter. Without parsing, the underlying command (and the attacker's intent) stays obscured.

## What parsing has to handle

Modern SOCs ingest everything from plain-text <DefineTerm term="Syslog" display="syslog" /> to cloud-native JSON. Parsing frameworks have to normalize that into queryable, structured data, and they have to do it while the adversary is actively trying to hide.

Good parsing decodes what can be decoded, enriches what can be looked up, records what was never captured as a named visibility gap, and preserves the context downstream phases need.

## The checklist

Nine steps, in order, for any alert. Not every alert needs every step: skip the ones the alert has no data for, and say so in the record. Each step links to the telemetry page that teaches it in depth.

1. **Find the raw record.** Open the source event, not only the console's parsed view, and note which telemetry source and format produced it. Fields the parser dropped or renamed are still in the raw record. See [formats and normalization](/docs/alert/parsing/multi-format/).
2. **Fix the clock.** Convert every timestamp to UTC in RFC 3339 form, and note whether it is event time or ingest time. An RFC 3164 syslog line carries no zone and no year, so the collector decided its time.
3. **Name what was not captured.** An empty field is a fact about telemetry. "Command line not captured (4688 policy off)" is a finding; "no command line" is a guess. Record each gap, so later phases do not read absence as evidence.
4. **Decode what can be decoded.** Look for the decoded script in PowerShell's 4104 events first, then decode by hand (Base64, then UTF-16LE). Normalize flag prefixes before you match on them. See [command line analysis](/docs/alert/parsing/command-line/).
5. **Rebuild the lineage on unique IDs.** Join parent and child on <code>ProcessGuid</code> or the EDR's process ID, never on PID alone. Check the creator against the reported parent, and read a macOS signature, Team ID, notarization and install path as evidence about provenance, not behavior. See [process relationships](/docs/alert/parsing/process-relationships/).
6. **Tie each connection to a process.** Join the process half (Sysmon Event ID 3, EDR network events) to the wire half (proxy, firewall, Zeek, flow logs) on addresses, ports and time. Keep what you observed separate from what you infer, and name the benign twin. See [network correlation](/docs/alert/parsing/network/).
7. **Check what landed, and where it came from.** File creates, persistence locations on every platform, and the Mark of the Web or the macOS quarantine attribute on anything downloaded. See [file system activity](/docs/alert/parsing/file-system/).
8. **For cloud and identity alerts, read the verb and the actor.** The API call, the identity behind it, and the role chain joined on stable keys; for sign-ins, interactive or non-interactive, and the session ID. See [cloud and identity logs](/docs/alert/parsing/cloud-identity/).
9. **Redact, then record.** Strip passwords, tokens and session cookies before anything goes into a ticket, a chat or an AI assistant, and keep the raw original in the evidence store. Then fill the three buckets below and hand them to Subject with the gaps named.

## Reading telemetry: one layer, five surfaces

Field extraction is the floor. Above it, advanced parsing reconstructs adversary behavior across five <DefineTerm term="Telemetry" display="telemetry" /> surfaces: command lines, process relationships, network activity, file system activity, and the cloud control plane. Beneath all five sits a normalization layer that is not a behavioral surface at all, but the plumbing that determines whether the surfaces can be read as one dataset. Each gets its own page. The six pages are field reference: read the one an alert sends you to, when it sends you there, rather than all six in one sitting.

## Three categories of information from every alert

Whatever surface you are parsing, the output should populate three buckets:

<div class="info-buckets">
  <div class="info-bucket">
    <span class="info-bucket__label">Alert metadata</span>
    <p>Who saw it, when, how confident, what bucket it fits.</p>
    <ul>
      <li>Alert ID and timestamp for unique identification and temporal sequencing.</li>
      <li>Source system and detection mechanism (which engine fired, under what logic).</li>
      <li>Severity and confidence to guide triage priority.</li>
      <li>Category and classification (privilege escalation, lateral movement, exfiltration).</li>
    </ul>
  </div>

  <div class="info-bucket">
    <span class="info-bucket__label">Technical detail</span>
    <p>The investigative substance.</p>
    <ul>
      <li>Affected systems and accounts (endpoints, servers, identities involved).</li>
      <li>Network information (IPs, ports, protocols, session IDs).</li>
      <li>File and process information (paths, hashes, command-line parameters).</li>
      <li>Registry and configuration changes (persistence, policy mods, drift).</li>
    </ul>
  </div>

  <div class="info-bucket">
    <span class="info-bucket__label">Contextual enrichment</span>
    <p>The organizational lens.</p>
    <ul>
      <li>Business impact (what does this potentially disrupt).</li>
      <li>Regulated-data flags (asset or dataset tagged PHI, cardholder data, personal data) for <a href="/docs/scope/regulatory/">Scope</a> to evaluate.</li>
      <li>Historical correlation (does this fit a recurring pattern or campaign).</li>
      <li>Threat intelligence (known IOCs, adversary TTPs, campaign signatures).</li>
    </ul>
  </div>
</div>

---

<KeyTakeaway>
Parsing turns raw output into investigative input. The checklist is the same for every alert: raw record, clock, gaps, decode, lineage, connections, files, identity, then redact and record. Each of the five surfaces gives you a different angle on adversary intent, and the normalization layer is what lets you read them as one dataset.
</KeyTakeaway>
