The four endpoint surfaces share an assumption: there is a host, and the host records what ran on it. Control-plane activity breaks that assumption. When an attacker with stolen keys enumerates your S3 buckets, no process tree exists anywhere you can see. The only record is the audit log of the cloud provider or identity provider, so parsing that record *is* the investigation. This page uses <DefineTerm term="AWS CloudTrail" /> and the major IdPs as the worked vocabulary; Azure Activity Logs and GCP audit logs differ in field names, not in concept.

## Anatomy of a CloudTrail record

Every management API call becomes one JSON event. Most fields are noise for triage; these are the ones that decide verdicts:

```json
{
  "eventTime": "2026-07-08T03:12:44Z",
  "eventSource": "s3.amazonaws.com",
  "eventName": "ListBuckets",
  "userIdentity": {
    "type": "AssumedRole",
    "arn": "arn:aws:sts::111122223333:assumed-role/ci-deploy/build-runner",
    "accessKeyId": "ASIA...",
    "sessionContext": {
      "sessionIssuer": { "userName": "ci-deploy" },
      "attributes": { "mfaAuthenticated": "false" }
    }
  },
  "sourceIPAddress": "203.0.113.50",
  "userAgent": "aws-cli/2.17.0 ...",
  "errorCode": "AccessDenied"
}
```

<div class="field-cards">
  <div class="field-card">
    <h3><code>eventSource</code> + <code>eventName</code></h3>
    <p>The verb. Which service, which API call. Reads (<code>List*</code>, <code>Describe*</code>, <code>Get*</code>) have the shape of reconnaissance — and of every inventory scanner, cost tool, and monitoring agent in the account, which produce the bulk of them. Writes (<code>Create*</code>, <code>Put*</code>, <code>Attach*</code>, <code>Update*</code>) change the environment. A burst of reads followed by a policy write, from an identity with no history of either, is the cloud shape of recon-then-privilege-escalation: a hypothesis worth the next pivot, not a verdict.</p>
  </div>
  <div class="field-card">
    <h3><code>userIdentity</code></h3>
    <p>The actor, and the field juniors misread most. <code>type</code> tells you whether this was a long-lived IAM user, an assumed role, root, or a service. For <code>AssumedRole</code>, the ARN names both the role and the session; <code>sessionContext.sessionIssuer</code> names where the session came from.</p>
  </div>
  <div class="field-card">
    <h3><code>accessKeyId</code> prefix</h3>
    <p><code>AKIA</code> means long-term IAM user credentials; <code>ASIA</code> means temporary credentials issued by <DefineTerm term="STS">AWS Security Token Service. The AWS service that issues temporary credentials when an identity assumes a role. STS credentials expire on a schedule (minutes to hours) and carry an ASIA key prefix, distinguishing them from long-term AKIA user keys.</DefineTerm>. Long-term keys showing up in new places are a bigger deal than short-lived ones, and stolen <code>ASIA</code> creds have a built-in expiry clock that shapes the attacker's tempo.</p>
  </div>
  <div class="field-card">
    <h3><code>sourceIPAddress</code> + <code>userAgent</code></h3>
    <p>Where the call physically came from and what tool made it. A role that normally acts from a VPC CIDR via an SDK suddenly acting from a residential IP via <code>aws-cli</code> is a story in two fields. Console sessions, SDKs, and Terraform all have recognizable agent strings.</p>
  </div>
  <div class="field-card">
    <h3><code>errorCode</code></h3>
    <p>Failures are telemetry. A spray of <code>AccessDenied</code> across many services from one identity has the shape of permission enumeration — someone mapping what a credential can do. Check the identity's baseline first: a misconfigured scanner or a role whose policy just shrank sprays the same way every day. If the spray is genuinely new, treat silence after it as the hypothesis that they found what works, and confirm it by pivoting to what <em>succeeded</em> next — the silence itself proves nothing.</p>
  </div>
  <div class="field-card">
    <h3><code>mfaAuthenticated</code></h3>
    <p>Inside <code>sessionContext.attributes</code>. Whether this session was backed by <DefineTerm term="Multi-Factor Authentication (MFA)" display="MFA" /> <em>as far as AWS saw it</em> — federated sessions report <code>false</code> even when the upstream IdP enforced MFA, because the challenge happened outside AWS. Sensitive actions from non-MFA sessions deserve a harder look, but check the IdP's sign-in log before recording "no MFA" as a fact.</p>
  </div>
</div>

## Follow the identity chain, not the process tree

The cloud equivalent of parent-child lineage is role chaining. An identity assumes a role, that session assumes another role, and each hop is a separate <code>AssumeRole</code> event in the trail. Reconstructing the chain answers the question the process tree used to answer: who is actually acting here?

<div class="chain-steps">
  <div class="chain-step">
    <span class="chain-step__num">1</span>
    <p>Start at the suspicious event. <code>userIdentity.sessionContext.sessionIssuer</code> names the role the session came from.</p>
  </div>
  <div class="chain-step">
    <span class="chain-step__num">2</span>
    <p>Search the trail for the <code>AssumeRole</code> call that created that session. Join on the stable key: the temporary <code>accessKeyId</code> in your event's <code>userIdentity</code> equals the <code>accessKeyId</code> in the <code>AssumeRole</code> call's <code>responseElements.credentials</code>. The session name is attacker-chosen and nonunique — often a tell worth reading, never a join key.</p>
  </div>
  <div class="chain-step">
    <span class="chain-step__num">3</span>
    <p>That event's own <code>userIdentity</code> is the previous link. Repeat until you reach a human, a long-term key, or a workload. That endpoint of the chain is your Subject-phase entity.</p>
  </div>
</div>

<Callout variant="info" title="Parse from the organization trail">
Each account's local trail can be silenced by anyone with admin in that account, and attackers know it. The organization-level trail aggregates every member account into storage the compromised account cannot touch, which makes it both the tamper-resistant copy and the only place a cross-account role chain appears end to end. If your alert came from one account's console, re-run the pivot against the org trail before trusting an absence.
</Callout>

## The IMDS pattern

The instance metadata service (IMDS) at `169.254.169.254` hands every EC2 workload the temporary credentials for its instance role. That design makes one intrusion shape so common it deserves its own recognition pattern: an attacker who can make a server fetch a URL (SSRF) or who lands on the box reads the metadata endpoint, steals the role credentials, and replays them from infrastructure they control.

<div class="imds-cards">
  <div class="imds-card imds-card--attack">
    <span class="imds-card__label">The shape</span>
    <p>Web app receives a crafted request → server fetches <code>169.254.169.254/latest/meta-data/iam/...</code> → role credentials exfiltrated → CloudTrail shows that role acting from an IP that is not the instance.</p>
  </div>
  <div class="imds-card imds-card--tell">
    <span class="imds-card__label">The tell in the trail</span>
    <p>An instance role's credentials used from outside the expected network path. That single discrepancy (role says "this EC2 instance," source IP says "somewhere else") is the highest-signal field comparison on this page. GuardDuty ships a finding class for exactly this.</p>
  </div>
  <div class="imds-card imds-card--context">
    <span class="imds-card__label">Context that changes the read</span>
    <p>IMDSv2 requires a session token first, which kills most SSRF variants of the theft. If the fleet enforces IMDSv2 and you still see off-box credential use, think on-host compromise rather than SSRF.</p>
  </div>
</div>

## IdP sign-in logs

For identity-provider alerts (<DefineTerm term="Okta" />, <DefineTerm term="Azure AD (Entra ID)" display="Microsoft Entra ID" />), the sign-in record is the raw material. The fields rhyme with CloudTrail's: who, from where, with what client, and did the second factor actually happen.

<div class="idp-list">
  <div class="idp-item">
    <span class="idp-item__bullet"></span>
    <div>
      <strong>Outcome plus MFA result, read against sign-in type.</strong> A success with no new MFA event is routine for noninteractive sign-ins — token refreshes, service flows, sessions whose earlier MFA claim still satisfies policy — and providers log those separately from interactive ones. The session-token-replay hypothesis starts when a session shows up with no authentication event behind it at all: a stolen cookie (adversary-in-the-middle phishing) lets the attacker skip authenticating entirely. It stays a hypothesis until corroborated — the same session ID surfacing from a new device or ASN mid-life, or session activity the legitimate device never produced.
    </div>
  </div>
  <div class="idp-item">
    <span class="idp-item__bullet"></span>
    <div>
      <strong>Denial patterns before an approval.</strong> A run of push-notification denials followed by a small-hours approval is MFA fatigue: the user gave in, not logged in. The timeline of factor events tells that story; the final "success" alone hides it.
    </div>
  </div>
  <div class="idp-item">
    <span class="idp-item__bullet"></span>
    <div>
      <strong>Client, device, and network novelty.</strong> New device fingerprint, new OS, new ASN, or geography inconsistent with the user's last sign-in. Any one alone is weak (VPNs and travel exist); novelty across several fields at once, against the user's own baseline, is what earns escalation of attention.
    </div>
  </div>
  <div class="idp-item">
    <span class="idp-item__bullet"></span>
    <div>
      <strong>What the session did next.</strong> The sign-in is only the entry. Follow the session ID forward: consent granted to a new OAuth app, a mail rule created, an API token minted. Those follow-on events are where a compromised session becomes a compromised account.
    </div>
  </div>
</div>

<KeyTakeaway>
The control plane is a first-class parsing surface. Read the verb (<code>eventName</code>), identify the actor (<code>userIdentity</code>, and the role chain behind it, joined on stable identifiers), compare where the call came from against where it should come from, and treat failures and missing MFA events as signal to check against the identity's baseline and the provider's semantics — not as verdicts. No process tree will come to save you here; the log is all there is.
</KeyTakeaway>
