## What to look for: inspection

Common <DefineTerm term="Obfuscation" display="obfuscation" /> patterns (ATT&CK T1027.010, Command Obfuscation). Base64-encoded <DefineTerm term="PowerShell" /> launchers are standard output from post-exploitation frameworks such as <DefineTerm term="Cobalt Strike" /> and BC Security's Empire; caret and substring tricks are catalogued in Daniel Bohannon's Invoke-DOSfuscation research (2018):

<div class="obfuscation-grid">
  <div class="obfuscation-card">
    <h3>Base64 encoding</h3>
    <code>powershell.exe -EncodedCommand &lt;long-base64-string&gt;</code>
    <p>The encoded blob hides the actual command from plain-text matching. The decode workflow below turns it back into readable intent.</p>
  </div>
  <div class="obfuscation-card">
    <h3>Caret insertion</h3>
    <code>cmd.exe /c e^ch^o "Hello"</code>
    <p>cmd strips the escape carets before execution, so the command runs normally while breaking naive substring signatures. Interior quotes (<code>w"h"oami</code>) work the same way. Parsing tip: carets survive only in the cmd.exe line itself. Read the child process's command line, which arrives with the carets already stripped.</p>
  </div>
  <div class="obfuscation-card">
    <h3>Variable expansion</h3>
    <code>$env:COMSPEC</code>
    <p>Uses environment variables to mask binary references. cmd can even assemble strings from variable substrings (<code>%COMSPEC:&#126;-7,1%</code> extracts a single letter), so the payload never appears literally.</p>
  </div>
</div>

Adversaries also abuse trusted system binaries (ATT&CK T1218, System Binary Proxy Execution): <DefineTerm term="LOLBins" display="LOLBins" /> such as `certutil.exe` for downloads, `regsvr32.exe` for DLL execution, `bitsadmin.exe` for transfers. These blend in because the binary is signed, trusted, and present on every host, which defeats allowlisting and hash-based detection. They are not footprint-free: downloaded files land on disk (certutil can also leave entries under CryptnetUrlCache), BITS jobs appear in the Microsoft-Windows-Bits-Client/Operational log and the QMGR job database, and the command line itself is usually the strongest artifact. The LOLBAS project (lolbas-project.github.io) catalogs Windows examples; GTFOBins and LOOBins cover Linux/Unix and macOS.

<Callout variant="info" title="Paste-and-run (ClickFix)">
A fake CAPTCHA, browser error or "verification" page tells the user to paste a command into the Run dialog (Win+R), a terminal, or File Explorer's address bar (ATT&CK T1204.004, Malicious Copy and Paste). Look for <code>explorer.exe</code> launching <code>powershell.exe</code>, <code>mshta.exe</code> or <code>curl.exe</code> with a URL, seconds after a browser visit, often with flags such as <code>-w h</code> and <code>iex(irm ...)</code>. Run-dialog variants leave the pasted command as a new value under <code>HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU</code>. The user ran it themselves, so no exploit or attachment appears in the tree.
</Callout>

<Callout variant="warn" title="Educational, not operational">
The examples in this chapter are illustrative. We deliberately do not show fully working invocation strings. Analysts need to recognize the *shape* of adversary technique, not have a copy-pasteable cookbook. Decoding what an attacker already ran is defensive analysis, and everything below stays on that side of the line. If you need to test detections, use isolated lab environments and sanctioned red-team tools.
</Callout>

## The decode workflow

The single most common parsing task this page exists for: an alert hands you `powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...` and the verdict depends on what that blob says. It is encoding, not encryption. There is no key. It decodes locally in seconds, if you know the one gotcha.

<div class="decode-steps">
  <div class="decode-step">
    <span class="decode-step__num">0</span>
    <div>
      <h3>Check whether Windows already decoded it</h3>
      <p>If PowerShell Script Block Logging is enabled (or the block tripped PowerShell's automatic logging of suspicious script blocks, which runs even when full logging is off), Event 4104 in Microsoft-Windows-PowerShell/Operational holds the decoded text of every layer, joined by <code>ScriptBlockId</code>. Module logging (4103), AMSI telemetry in your EDR, and transcription files can hold it too. Pull that first; decode by hand only when it is absent, and record which you used. The old <code>powershell -version 2</code> downgrade that evaded these controls is gone on hosts where Microsoft has removed PowerShell 2.0.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">1</span>
    <div>
      <h3>Extract the blob</h3>
      <p>Copy the Base64 string out of the alert into a local decoder. Never paste it into a terminal that could execute it, and never run the command to "see what it does." <a href="https://gchq.github.io/CyberChef/" target="_blank" rel="noopener noreferrer">CyberChef</a>, which runs entirely client-side in the browser (use the downloadable offline build for sensitive cases), is the standard tool.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">2</span>
    <div>
      <h3>Decode Base64, then interpret as UTF-16LE</h3>
      <p>This is the gotcha that trips every junior once: <code>-EncodedCommand</code> takes Base64 of <strong>UTF-16LE</strong> text, because that is what Windows means by "Unicode." Decode it as UTF-8 and you get the characters interleaved with null bytes (<code>I·E·X· ·(·N·e·w</code>), which some tools render as gibberish or CJK characters. In CyberChef the recipe is From Base64 followed by Decode Text (UTF-16LE). If your output has a space or dot between every letter, you skipped the second step.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">3</span>
    <div>
      <h3>Read the result, and expect another layer</h3>
      <p>The example blob above opens with <code>IEX (New-Object ...</code>: the classic download-and-execute-in-memory cradle. Real payloads often nest: the decoded text itself calls <code>FromBase64String</code> plus a Gzip or Deflate decompress, then <code>IEX</code> again. Keep unwinding layers in the decoder until you reach readable intent, and record each layer in your notes.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">4</span>
    <div>
      <h3>Treat what falls out as hot</h3>
      <p>URLs, domains, and IPs inside the decoded payload are live attacker infrastructure until proven otherwise. Do not browse them to check. They are IOCs: record them, look them up in <DefineTerm term="Threat Intelligence" display="threat intelligence" />, and pivot on them in the network telemetry.</p>
    </div>
  </div>
</div>

## The flags do not spell themselves out

PowerShell accepts abbreviated parameter prefixes: `-e`, `-en`, and `-enc` all resolve to `-EncodedCommand`, even though `-ExecutionPolicy` shares the `-e` prefix. A detection or a triage search that string-matches the full flag name misses every abbreviated form, which is exactly why attackers abbreviate. Parse by meaning, not by literal string. Normalize before you match: PowerShell also accepts <code>/</code> and Unicode dashes such as the en dash as the parameter prefix (<code>/enc</code>, <code>–enc</code>), and abbreviated values (<code>-w h</code>). A search for "-enc" misses all of them.

<div class="flags-table" role="table" aria-label="PowerShell flag abbreviations">
  <div class="flags-row flags-row--head" role="row">
    <span role="columnheader">Full parameter</span>
    <span role="columnheader">Common short forms</span>
    <span role="columnheader">What it signals</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-EncodedCommand</code></span>
    <span role="cell"><code>-e</code>, <code>-en</code>, <code>-enc</code>, <code>-ec</code></span>
    <span role="cell">Payload is Base64 of UTF-16LE. Decode it.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-NoProfile</code></span>
    <span role="cell"><code>-nop</code></span>
    <span role="cell">Skips profile scripts for a clean, fast, unmonitored-feeling start. Common in automation and in attacks alike.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-WindowStyle Hidden</code></span>
    <span role="cell"><code>-w hidden</code>, <code>-win h</code></span>
    <span role="cell">No visible window. Legitimate scheduled scripts use it; so does nearly all malware.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-NonInteractive</code></span>
    <span role="cell"><code>-noni</code></span>
    <span role="cell">No prompt back to a human. Expected from services, notable from a user session.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-ExecutionPolicy Bypass</code></span>
    <span role="cell"><code>-ep bypass</code>, <code>-exec bypass</code></span>
    <span role="cell">Disables script-execution restrictions for this process. Not an exploit (the policy is not a security boundary), but a strong tell of unmanaged script execution.</span>
  </div>
</div>

No single flag is a verdict. `-nop -w hidden -enc` together on a workstation, spawned from an Office process, is a very different sentence than the same flags in a signed vendor scheduled task. The combination plus the context decides, and the decoded payload settles it.

## When there is no command line to parse

Sometimes the alert's command-line field is simply empty. The most common reason is not evasion; it is configuration. Windows Security Event 4688 records process creations, but its CommandLine field populates only when the "Include command line in process creation events" policy is enabled, and it is off by default. If it was never turned on, every historical event is blank and there is no retroactive fix. 4688 itself has a prerequisite too: the Audit Process Creation subcategory, also off by default, so on an unconfigured host there is no 4688 at all. When both are on, command lines can carry passwords and tokens: redact them before pasting into tickets or chat.

<div class="gap-cards">
  <div class="gap-card">
    <h3>Know your source</h3>
    <p>Security 4688 without the policy: no command line. <DefineTerm term="Sysmon" /> Event ID 1: full command line, parent, and hashes by default. EDR process telemetry: almost always captures it. Which source feeds your console determines what you can parse.</p>
  </div>
  <div class="gap-card">
    <h3>An empty field is a fact about telemetry</h3>
    <p>Record "command line not captured (4688 policy disabled)" rather than "no command line," and pivot to the sources that do have it. Absence of the field is a visibility gap, not evidence the process ran without arguments.</p>
  </div>
</div>

<Reveal summary="Annotated sample: a 4688 with the command line missing" variant="deep-dive">

Trimmed and fictional; the field names are real.

```xml
<EventData>
  <Data Name="SubjectUserName">jdoe</Data>
  <Data Name="SubjectLogonId">0x3e7a21</Data>
  <Data Name="NewProcessId">0x1fc0</Data>
  <Data Name="NewProcessName">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
  <Data Name="TokenElevationType">%%1938</Data>
  <Data Name="ProcessId">0x1d4c</Data>
  <Data Name="CommandLine"></Data>
  <Data Name="ParentProcessName">C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE</Data>
  <Data Name="MandatoryLabel">S-1-16-8192</Data>
</EventData>
```

- <code>CommandLine</code> is present and empty: the event schema has the field, the policy did not fill it. Record it as not captured, then pull the same process from Sysmon Event ID 1 or the EDR by host, PID and start time.
- The IDs are hexadecimal. <code>NewProcessId</code> 0x1fc0 is PID 8128, the new process. <code>ProcessId</code> 0x1d4c (PID 7500) is the creator, not the new process, which is the field juniors swap most often.
- <code>TokenElevationType</code> <code>%%1938</code> is a limited (UAC-filtered) token; <code>%%1937</code> is elevated, and <code>%%1936</code> is a full token with UAC off or the built-in administrator. <code>MandatoryLabel</code> S-1-16-8192 is Medium integrity.
- <code>SubjectLogonId</code> ties the creation to the logon session in the matching 4624.

</Reveal>

## Execution context

The same command can be benign or malicious depending on context. Four contextual signals matter most:

<div class="context-grid">
  <div class="context-card">
    <span class="context-card__label">01 · User context</span>
    <p><code>NT AUTHORITY\SYSTEM</code> vs. a standard user. A SYSTEM-context process whose lineage leads back to a user's interactive session suggests privilege escalation; installers handed off to the Windows Installer service are the common benign exception.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">02 · Timing</span>
    <p>Outside business hours vs. scheduled maintenance window. Cross-reference with change tickets and the user's known patterns.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">03 · Parent process</span>
    <p><code>cmd.exe</code> spawned by <code>outlook.exe</code> is suspicious. The same command from Task Scheduler is usually legitimate.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">04 · Directory</span>
    <p><code>C:\Windows\Temp</code>, <code>%TEMP%</code> and <code>C:\Users\Public</code> deserve a second look. <code>%APPDATA%</code> and <code>%LOCALAPPDATA%</code> are mixed: per-user installs such as OneDrive and VS Code live there legitimately, so check the software inventory before reading location as intent. <code>C:\Program Files</code> is expected.</p>
  </div>
</div>

<Reveal summary="Example: PowerShell under an Office chain">
Outlook → Word → PowerShell signals a macro in an opened attachment: the macro runs inside Word (or Excel), which becomes PowerShell's parent, with Outlook one level above. That is less common now that Office blocks macros in internet-sourced files by default, so check whether the file carried the Mark of the Web and how the block was bypassed (unblocked by the user, saved to a Trusted Location, or delivered in a container that strips the mark). PowerShell spawned directly by outlook.exe is rarer and high-signal: it points at Outlook-based persistence (a malicious rule, a custom form, a folder Home Page, or the Outlook VBA project; ATT&CK T1137) or an exploit of Outlook itself. What you would check next:

- The attachment that was opened, and whether it carried the Mark of the Web.
- The script's <DefineTerm term="Command Line" display="command line" /> for download cradle patterns.
- Outbound network activity from PowerShell in the next 60 seconds.
- For a direct outlook.exe parent: the mailbox's rules, custom forms, folder Home Page settings, and the <code>VbaProject.OTM</code> file.
- Whether the user's mailbox shows similar emails to other recipients.

The same PowerShell command from Task Scheduler during a maintenance window is almost certainly legitimate. Same command, different parent, different verdict.
</Reveal>

## Beyond PowerShell and cmd

The same analysis transfers off Windows; only the vocabulary changes.

<div class="platform-list">
  <div class="platform-item">
    <span class="platform-item__bullet"></span>
    <div>
      <strong>macOS and Linux pipes.</strong> <code>curl ... | sh</code> and <code>echo &lt;base64&gt; | base64 -d | bash</code> are the download cradle and the encoded command of the Unix world. <code>osascript -e</code> running AppleScript from a non-interactive parent is the macOS counterpart of an Office macro spawning a shell. Two shapes dominate current macOS stealer intrusions (AMOS, MacSync, Odyssey): <code>osascript</code> drawing a fake system password prompt (<code>display dialog ... with hidden answer</code>), and a user pasting a <code>curl | bash</code> or base64 one-liner into Terminal from a fake "verification" page.
    </div>
  </div>
  <div class="platform-item">
    <span class="platform-item__bullet"></span>
    <div>
      <strong>Vendor-standard noise to recognize.</strong> Electron apps launch helpers with flags like <code>--type=utility</code> or <code>--type=renderer</code>. The command line in <a href="/docs/alert/example/#case-b">Case B</a> of the Alert worked example (a macOS developer workstation running the Cursor IDE) is exactly this shape: long, odd-looking, and vendor-standard. Knowing the legitimate shapes is what keeps them from eating triage time.
    </div>
  </div>
</div>

## Pattern recognition

Build mental patterns for atypical use of common binaries. These are the shapes you want to recognize before reading the command in detail.

<div class="pattern-list">
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Unusual LOLBin invocations.</strong> <code>rundll32.exe</code>, <code>mshta.exe</code>, <code>regsvr32.exe</code> invoked outside their normal contexts, and <code>wmic.exe</code> (legacy: removed from current Windows 11 builds in 2026; on modern hosts expect the same WMI abuse via <code>Get-CimInstance</code> / <code>Invoke-CimMethod</code>, or <code>wmiprvse.exe</code> as the parent).
    </div>
  </div>
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Framework flags.</strong> The combinations in the flag table above, especially <code>-nop -w hidden -enc</code> together.
    </div>
  </div>
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Indirect execution.</strong> A trusted binary loading attacker-controlled content from a remote location. The binary is legitimate. The payload is not.
    </div>
  </div>
</div>

## Check yourself

An alert shows <code>powershell.exe /w 1 /enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...</code> with <code>explorer.exe</code> as its parent, twenty seconds after the user's browser loaded an unfamiliar page. Parse it before you open the answer: what do the flags mean, what is the first source you check for the payload, and what does the parent tell you?

<Reveal summary="One way to answer">
<code>/w 1</code> is <code>-WindowStyle Hidden</code> (1 is the numeric value for Hidden) and <code>/enc</code> is <code>-EncodedCommand</code>, both with the <code>/</code> prefix a search for "-enc" would miss. Check Event 4104 for the decoded script blocks first; if it is absent, decode by hand (Base64, then UTF-16LE), and the opening <code>IEX (New-Object</code> says a download cradle follows. A browser visit followed by explorer.exe launching PowerShell is the paste-and-run (ClickFix) shape: look for a new RunMRU value, and treat the URL inside the payload as live infrastructure.
</Reveal>

<DefineTerm term="Command Line Analysis" display="Command line analysis" /> is where <DefineTerm term="Parsing" display="parsing" /> becomes investigation.
