## What to look for: inspection

Common <DefineTerm term="Obfuscation" display="obfuscation" /> patterns observed in frameworks like <DefineTerm term="PowerShell" /> Empire and <DefineTerm term="Cobalt Strike" />:

<div class="obfuscation-grid">
  <div class="obfuscation-card">
    <h3>Base64 encoding</h3>
    <code>powershell.exe -EncodedCommand &lt;long-base64-string&gt;</code>
    <p>The encoded blob hides the actual command from plain-text matching. The decode workflow below turns it back into readable intent.</p>
  </div>
  <div class="obfuscation-card">
    <h3>Caret insertion</h3>
    <code>cmd.exe /c e^ch^o "Hello"</code>
    <p>cmd strips the escape carets before execution, so the command runs normally while breaking naive substring signatures. Interior quotes (<code>w"h"oami</code>) work the same way.</p>
  </div>
  <div class="obfuscation-card">
    <h3>Variable expansion</h3>
    <code>$env:COMSPEC</code>
    <p>Uses environment variables to mask binary references. cmd can even assemble strings from variable substrings (<code>%COMSPEC:~-7,1%</code> extracts a single letter), so the payload never appears literally.</p>
  </div>
</div>

Adversaries also abuse trusted system binaries: <DefineTerm term="LOLBins" display="LOLBins" /> such as `certutil.exe` for downloads, `regsvr32.exe` for DLL execution, `bitsadmin.exe` for transfers. These leave minimal forensic footprint because the binary itself is signed and trusted.

<Callout variant="warn" title="Educational, not operational">
The examples in this chapter are illustrative. We deliberately do not show fully working invocation strings. Analysts need to recognize the *shape* of adversary technique, not have a copy-pasteable cookbook. Decoding what an attacker already ran is defensive analysis, and everything below stays on that side of the line. If you need to test detections, use isolated lab environments and sanctioned red-team tools.
</Callout>

## The decode workflow

The single most common parsing task this page exists for: an alert hands you `powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...` and the verdict depends on what that blob says. It is encoding, not encryption. There is no key. It decodes locally in seconds, if you know the one gotcha.

<div class="decode-steps">
  <div class="decode-step">
    <span class="decode-step__num">1</span>
    <div>
      <h3>Extract the blob</h3>
      <p>Copy the Base64 string out of the alert into a local decoder. Never paste it into a terminal that could execute it, and never run the command to "see what it does." <a href="https://gchq.github.io/CyberChef/" target="_blank" rel="noopener noreferrer">CyberChef</a> running locally in a browser tab is the standard tool.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">2</span>
    <div>
      <h3>Decode Base64, then interpret as UTF-16LE</h3>
      <p>This is the gotcha that trips every junior once: <code>-EncodedCommand</code> takes Base64 of <strong>UTF-16LE</strong> text, because that is what Windows means by "Unicode." Decode it as UTF-8 and you get the characters interleaved with null bytes (<code>I·E·X· ·(·N·e·w</code>), which some tools render as gibberish or CJK characters. In CyberChef the recipe is From Base64 followed by Decode Text (UTF-16LE). If your output has a space or dot between every letter, you skipped the second step.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">3</span>
    <div>
      <h3>Read the result, and expect another layer</h3>
      <p>The example blob above opens with <code>IEX (New-Object ...</code>, the classic download-and-execute-in-memory cradle. Real payloads often nest: the decoded text itself calls <code>FromBase64String</code> plus a Gzip or Deflate decompress, then <code>IEX</code> again. Keep unwinding layers in the decoder until you reach readable intent, and record each layer in your notes.</p>
    </div>
  </div>
  <div class="decode-step">
    <span class="decode-step__num">4</span>
    <div>
      <h3>Treat what falls out as hot</h3>
      <p>URLs, domains, and IPs inside the decoded payload are live attacker infrastructure until proven otherwise. Do not browse them to check. They are IoCs: record them, look them up in <DefineTerm term="Threat Intelligence" display="threat intelligence" />, and pivot on them in the network telemetry.</p>
    </div>
  </div>
</div>

## The flags do not spell themselves out

PowerShell accepts abbreviated parameter prefixes: `-e`, `-en`, and `-enc` all resolve to `-EncodedCommand`, even though `-ExecutionPolicy` shares the `-e` prefix. A detection or a triage search that string-matches the full flag name misses every abbreviated form, which is exactly why attackers abbreviate. Parse by meaning, not by literal string.

<div class="flags-table" role="table" aria-label="PowerShell flag abbreviations">
  <div class="flags-row flags-row--head" role="row">
    <span role="columnheader">Full parameter</span>
    <span role="columnheader">Common short forms</span>
    <span role="columnheader">What it signals</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-EncodedCommand</code></span>
    <span role="cell"><code>-e</code>, <code>-en</code>, <code>-enc</code>, <code>-ec</code></span>
    <span role="cell">Payload is Base64 of UTF-16LE. Decode it.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-NoProfile</code></span>
    <span role="cell"><code>-nop</code></span>
    <span role="cell">Skips profile scripts for a clean, fast, unmonitored-feeling start. Common in automation and in attacks alike.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-WindowStyle Hidden</code></span>
    <span role="cell"><code>-w hidden</code>, <code>-win h</code></span>
    <span role="cell">No visible window. Legitimate scheduled scripts use it; so does nearly all malware.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-NonInteractive</code></span>
    <span role="cell"><code>-noni</code></span>
    <span role="cell">No prompt back to a human. Expected from services, notable from a user session.</span>
  </div>
  <div class="flags-row" role="row">
    <span role="cell"><code>-ExecutionPolicy Bypass</code></span>
    <span role="cell"><code>-ep bypass</code>, <code>-exec bypass</code></span>
    <span role="cell">Disables script-execution restrictions for this process. Not an exploit (the policy is not a security boundary), but a strong tell of unmanaged script execution.</span>
  </div>
</div>

No single flag is a verdict. `-nop -w hidden -enc` together on a workstation, spawned from an Office process, is a very different sentence than the same flags in a signed vendor scheduled task. The combination plus the context decides, and the decoded payload settles it.

## When there is no command line to parse

Sometimes the alert's command-line field is simply empty. The most common reason is not evasion; it is configuration. Windows Security Event 4688 records process creations, but its CommandLine field populates only when the "Include command line in process creation events" policy is enabled, and it is off by default. If it was never turned on, every historical event is blank and there is no retroactive fix.

<div class="gap-cards">
  <div class="gap-card">
    <h3>Know your source</h3>
    <p>Security 4688 without the policy: no command line. <DefineTerm term="Sysmon" /> Event ID 1: full command line, parent, and hashes by default. EDR process telemetry: almost always captures it. Which source feeds your console determines what you can parse.</p>
  </div>
  <div class="gap-card">
    <h3>An empty field is a fact about telemetry</h3>
    <p>Record "command line not captured (4688 policy disabled)" rather than "no command line," and pivot to the sources that do have it. Absence of the field is a visibility gap, not evidence the process ran without arguments.</p>
  </div>
</div>

## Execution context

The same command can be benign or malicious depending on context. Four contextual signals matter most:

<div class="context-grid">
  <div class="context-card">
    <span class="context-card__label">01 · User context</span>
    <p><code>NT AUTHORITY\SYSTEM</code> vs. a standard user account. System-level execution from a user-initiated process is rarely legitimate.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">02 · Timing</span>
    <p>Outside business hours vs. scheduled maintenance window. Cross-reference with change tickets and the user's known patterns.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">03 · Parent process</span>
    <p><code>cmd.exe</code> spawned by <code>outlook.exe</code> is suspicious. The same command from Task Scheduler is usually legitimate.</p>
  </div>
  <div class="context-card">
    <span class="context-card__label">04 · Directory</span>
    <p><code>C:\Windows\Temp</code> or <code>%APPDATA%</code> is suspicious. <code>C:\Program Files</code> is expected.</p>
  </div>
</div>

<Reveal summary="Example: PowerShell from Outlook">
A PowerShell script launched by Outlook signals likely macro <DefineTerm term="Execution" display="execution" /> from an email attachment. What you would check next:

- The Outlook session's recent attachment activity.
- The script's <DefineTerm term="Command Line" display="command line" /> for download cradle patterns.
- Outbound network activity from PowerShell in the next 60 seconds.
- Whether the <DefineTerm term="User" display="user" />'s mailbox shows similar emails to other recipients.

The same PowerShell command from Task Scheduler during a maintenance window is almost certainly legitimate. Same command, different parent, different verdict.
</Reveal>

## Beyond PowerShell and cmd

The same analysis transfers off Windows; only the vocabulary changes.

<div class="platform-list">
  <div class="platform-item">
    <span class="platform-item__bullet"></span>
    <div>
      <strong>macOS and Linux pipes.</strong> <code>curl ... | sh</code> and <code>echo &lt;base64&gt; | base64 -d | bash</code> are the download cradle and the encoded command of the Unix world. <code>osascript -e</code> running AppleScript from a non-interactive parent is the macOS counterpart of an Office macro spawning a shell.
    </div>
  </div>
  <div class="platform-item">
    <span class="platform-item__bullet"></span>
    <div>
      <strong>Vendor-standard noise to recognize.</strong> Electron apps launch helpers with flags like <code>--type=utility</code> or <code>--type=renderer</code>. The Alert worked example's Case B command line is exactly this shape: long, odd-looking, and vendor-standard. Knowing the legitimate shapes is what keeps them from eating triage time.
    </div>
  </div>
</div>

## Pattern recognition

Build mental patterns for atypical use of common binaries. These are the shapes you want to recognize before reading the command in detail.

<div class="pattern-list">
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Unusual LOLBin invocations.</strong> <code>rundll32.exe</code>, <code>mshta.exe</code>, <code>wmic.exe</code>, <code>regsvr32.exe</code> invoked outside their normal contexts.
    </div>
  </div>
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Framework flags.</strong> Command-line flags that suggest framework use: <code>-NoP</code>, <code>-EncodedCommand</code> (or any prefix of it), <code>-WindowStyle Hidden</code>, <code>-NonInteractive</code>.
    </div>
  </div>
  <div class="pattern-item">
    <span class="pattern-item__bullet"></span>
    <div>
      <strong>Indirect execution.</strong> A trusted binary loading attacker-controlled content from a remote location. The binary is legitimate. The payload is not.
    </div>
  </div>
</div>

<KeyTakeaway>
<DefineTerm term="Command Line Analysis" display="Command line analysis" /> is where <DefineTerm term="Parsing" display="parsing" /> becomes investigation. The decode workflow turns an encoded blob into readable intent, the flag table keeps abbreviations from hiding it, and the 4688 gap reminds you to know what your telemetry actually captured. What the command says, weighed against its context, anchors everything downstream.
</KeyTakeaway>
