This page covers the plumbing under the behavioral surfaces: the formats telemetry arrives in, the platform sources that generate it, and the normalization that makes it all queryable as one dataset. It is not a surface of adversary behavior. It is the layer that determines whether you can read the surfaces at all.

## The four format families

      <h3>Windows Event Logs (EVTX)</h3>
    </div>
    <p class="format-card__intro">
      Windows writes structured records to log channels (Security, System, Application, and many subscribed providers) using the EVTX file format. Each record has a numeric <DefineTerm term="Event ID">A short integer that identifies what kind of event the record describes. Windows publishes a catalog of event IDs (4624 for a successful logon, 4688 for a process creation, and so on). Within a provider the same ID always means the same kind of event, which is what makes EVTX queryable; across providers IDs collide (Event ID 1 is process creation in Sysmon but a system-time change from Kernel-General in the System log), so always read the ID together with its channel and provider. Different providers also use different IDs for the same thing: Sysmon 1 and Security 4688 both record process creation.</DefineTerm> identifying what happened. Triage tooling parses the relevant IDs into structured fields.
    </p>
    <p class="format-card__sub">Common IDs an analyst will read:</p>
    <ul>
      <li><strong>Process events:</strong> 4688 (creation), 4689 (termination)</li>
      <li><strong>Authentication:</strong> 4624 (successful logon), 4625 (failed logon), 4768/4769 (Kerberos ticket requests)</li>
      <li><strong>Privileged logon:</strong> 4672 (special privileges assigned to a new logon; routine for SYSTEM, admins and service accounts, notable for a standard user; pair it with the matching 4624 by Logon ID and baseline it rather than reading it as escalation)</li>
      <li><strong>Account and group changes:</strong> 4720 (user account created), 4738 (user account changed), 4728/4732/4756 (member added to a security-enabled global, local or universal group), 4704 (user right assigned)</li>
      <li><strong>Persistence:</strong> 4697 (service installed, Security log) / 7045 (service installed, System log), 4698 (scheduled task created)</li>
      <li><strong>Script content:</strong> 4104 (PowerShell script block, Microsoft-Windows-PowerShell/Operational; full coverage requires Script Block Logging)</li>
      <li><strong>Tampering:</strong> 1102 (Security audit log cleared), 104 (System log cleared)</li>
    </ul>
    <p class="format-card__sub">4688 appears only if the Audit Process Creation subcategory is enabled, and includes the command line only if "Include command line in process creation events" is also enabled. Neither is on by default.</p>

      <h3>Syslog (RFC 5424 / RFC 3164)</h3>
    </div>
    <p class="format-card__intro">
      <DefineTerm term="Syslog" /> is the long-standing standard for streaming text-formatted log messages over the network. Each message carries a severity, a facility, a timestamp, and a free-form text body. RFC 5424 is the modern spec, but most network gear still emits the older BSD framing (RFC 3164), so expect both in one pipeline. It remains the lingua franca for network devices and for forwarding Linux logs, though many modern distributions (Debian 12 and later, for example) record locally only to the systemd journal (queried with <code>journalctl</code>) and need a forwarder to emit syslog or JSON. Watch the timestamps: RFC 3164 carries no year and no time zone, so the receiving collector's clock and configuration silently decide when the event happened.
    </p>
    <p class="format-card__sub">Where you will see syslog:</p>
    <ul>
      <li><strong>Network devices:</strong> firewalls, routers, switches, load balancers</li>
      <li><strong>Linux systems:</strong> kernel logs, application events, auth events</li>
      <li><strong>Cloud platforms:</strong> container orchestration, microservice logs</li>
      <li><strong>IoT and OT:</strong> ICS, embedded devices</li>
    </ul>
  </div>

    </div>
    <p class="format-card__intro">
      <DefineTerm term="CEF">Common Event Format. A log format pioneered by ArcSight (now OpenText ESM) that adds a structured header (vendor, product, event name, severity) and key-value extensions to a syslog-style line. CEF made it possible for many vendors to ship logs that SIEMs could parse without writing a custom parser per product.</DefineTerm> is the format that made multi-vendor SIEM ingestion practical. It overlays a structured header on a syslog message so the SIEM knows the vendor, product, severity, and event class without guessing.
    </p>
    <p class="format-card__sub">Common ecosystems:</p>
    <ul>
      <li><strong>SIEM platforms:</strong> OpenText ESM (formerly ArcSight ESM, where CEF originated), Splunk (now part of Cisco), Microsoft Sentinel (CEF via the Azure Monitor Agent), IBM QRadar SIEM (which also has its own LEEF format)</li>
      <li><strong>Standardized fields:</strong> device vendor, product, version, signature</li>
      <li><strong>Custom extensions:</strong> vendor-specific attributes</li>
      <li><strong>Integration:</strong> broad SOAR compatibility</li>

### What the raw records look like

A console shows you its parsed view of a record. Before you trust that view, read one raw record per source and find the fields you will rely on. The samples below are trimmed and fictional; the field names are real. Raw records carry what the parsed view hides, including passwords, tokens and session cookies in command lines, URLs and headers: redact secrets before you paste a raw record into a ticket, a chat or an AI assistant, and keep the unredacted original in the evidence store.

<Reveal summary="Annotated samples: Sysmon, syslog, CEF, auditd" variant="deep-dive">

**Sysmon Event ID 1 (process creation), XML event data:**

```xml
<EventData>
  <Data Name="UtcTime">2026-03-10 14:22:04.871</Data>
  <Data Name="ProcessGuid">{6a1f0c3e-2b7d-65f0-4c1a-000000001a00}</Data>
  <Data Name="ProcessId">8128</Data>
  <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
  <Data Name="CommandLine">powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...</Data>
  <Data Name="User">CORP\jdoe</Data>
  <Data Name="LogonId">0x3e7a21</Data>
  <Data Name="IntegrityLevel">Medium</Data>
  <Data Name="ParentProcessGuid">{6a1f0c3e-2b7c-65f0-3b19-000000001a00}</Data>
  <Data Name="ParentImage">C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE</Data>
  <Data Name="ParentCommandLine">"WINWORD.EXE" /n "C:\Users\jdoe\Downloads\remittance.docm"</Data>
</EventData>
```

- <code>ProcessGuid</code> and <code>ParentProcessGuid</code> are the join keys for the process tree. Windows reuses PIDs, so a PID alone can point at the wrong process.
- <code>CommandLine</code> and <code>ParentCommandLine</code> carry intent; the next page decodes the first one.
- <code>LogonId</code> ties the process to a logon session (the matching 4624). <code>IntegrityLevel</code> says whether the token was elevated.
- <code>UtcTime</code> is UTC. Security 4688 carries the same facts under other names (<code>NewProcessName</code>, <code>ParentProcessName</code>, <code>SubjectLogonId</code>, <code>TokenElevationType</code>, <code>MandatoryLabel</code>), and its <code>CommandLine</code> field exists only if the policy is on.

**Syslog, the same firewall event in both framings:**

```text
<134>1 2026-03-10T14:22:05.003Z fw01.corp.example filterlog 2211 - - pass out tcp 10.20.4.17:51544 -> 198.51.100.23:443
<134>Mar 10 14:22:05 fw01 filterlog[2211]: pass out tcp 10.20.4.17:51544 -> 198.51.100.23:443
```

- <code>&lt;134&gt;</code> is the priority: facility 16 (local0) times 8, plus severity 6 (informational).
- The RFC 5424 line (first) carries a version, a full timestamp with a zone, the host, app name and process ID, then empty message-ID and structured-data fields (<code>-</code>).
- The RFC 3164 line (second) carries no year and no zone. Whatever time your SIEM shows for it, the collector decided.

**CEF, a secure web gateway record:**

```text
CEF:0|ExampleVendor|SecureGateway|5.2|url-allowed|URL allowed|3|rt=1773152525003 suser=jdoe src=10.20.4.17 dst=198.51.100.23 request=https://cdn-relay.example/upd cat=Newly Registered Domain act=allowed
```

- Seven pipe-delimited header fields: CEF version, vendor, product, product version, signature ID, event name, severity.
- Then space-separated <code>key=value</code> extensions. <code>rt</code> is the receipt time in epoch milliseconds (UTC); <code>suser</code>, <code>src</code>, <code>dst</code> and <code>request</code> are the fields you will join on.

**auditd, a process execution on a Linux build server:**

```text
type=SYSCALL msg=audit(1773152530.412:8812): arch=c000003e syscall=59 success=yes exit=0 ppid=2140 pid=2187 auid=1003 uid=1003 comm="bash" exe="/usr/bin/bash" key="exec"
type=EXECVE msg=audit(1773152530.412:8812): argc=3 a0="bash" a1="-c" a2=69643B20756E616D65202D61
```

- One event spans several records that share the <code>msg=audit(...)</code> stamp: epoch seconds (UTC) plus a serial number. Join the <code>SYSCALL</code> record (who and which binary) to the <code>EXECVE</code> record (the arguments) on that stamp.
- The arguments arrive split across <code>a0</code> to <code>aN</code>. <code>a2</code> has no quotes because it is hex: auditd hex-encodes any argument that contains a space, a quote or a control character. It decodes to <code>id; uname -a</code>, the first discovery commands of a hands-on intruder, or of an administrator. A search for "uname" in the raw log misses it.
- <code>auid</code> is the login user ID, which survives <code>sudo</code> and <code>su</code>; <code>uid</code> is the user the process ran as. When they differ, the person behind the process is the <code>auid</code>.

</Reveal>

## Where the telemetry comes from, per platform

Formats are only half the story. The behavioral surfaces in this chapter (process trees, command lines, file activity) depend on a telemetry source actually recording them, and the source differs by platform. Knowing which source feeds your console tells you what the data can and cannot show.

<div class="telem-grid">
  <div class="telem-card">
    <span class="telem-card__os">Windows</span>
    <h3><DefineTerm term="Sysmon" /></h3>
    <p>Sysinternals System Monitor: a free standalone download and, since 2026, also a built-in optional feature of Windows 11 and Windows Server 2025 (off until enabled; built-in and standalone cannot run side by side). Its process-creation event (Event ID 1) carries the full command line, parent command line, hashes, and a ProcessGuid that survives PID reuse. Network connections (3) and image loads (7) are off by default; what else you see (file creates 11, registry writes 13, DNS queries 22) depends entirely on the configuration. Parse the XML event data, not the rendered message, which built-in Sysmon localizes. It is the de facto standard source for the process and command-line telemetry this chapter teaches, and the usual compensating control when Security 4688 is missing its command line.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">Linux</span>
    <h3>auditd and eBPF sensors</h3>
    <p>The kernel audit framework (<code>auditd</code>) records syscall-level events; an <code>execve</code> rule gives you process executions with arguments. Two parsing stumbles: the arguments arrive split across <code>a0</code>, <code>a1</code> ... <code>aN</code> fields, and any argument containing a space or special character is hex-encoded, so decode before you search. Modern EDR and open tooling increasingly use eBPF sensors for the same visibility with less overhead. Either way, output typically flows out as syslog or JSON.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">macOS</span>
    <h3>Endpoint Security framework and unified log</h3>
    <p>Since macOS 10.15, EDR agents get process, file, and signing telemetry from Apple's <DefineTerm term="Endpoint Security framework">Apple's kernel-supported API (introduced in macOS 10.15) that delivers real-time process execution, file, and code-signing events to security agents. It replaced kernel extensions as the sanctioned way for EDR products to observe macOS activity.</DefineTerm>, which is where a macOS process tree like that of <a href="/docs/alert/example/#case-b">Case B</a> in the Alert worked example (a macOS developer workstation running the Cursor IDE) comes from. The unified log holds the OS's own high-volume record, queryable with <code>log show</code>.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">Cross-platform</span>
    <h3>osquery</h3>
    <p>Exposes the live state of Windows, macOS, and Linux hosts as SQL tables (processes, users, launch items, listening ports). Strong for point-in-time interrogation and fleet-wide hunting; it complements, rather than replaces, the streaming sources above.</p>
  </div>
</div>

<Callout variant="info" title="Data quality is half the work">
Alerts often arrive without full metadata. Parent process missing, asset identifier truncated, <DefineTerm term="Command Line" display="command line" /> cut off at a byte boundary. Advanced parsing systems integrate enrichment from <DefineTerm term="Configuration Management Database (CMDB)" display="CMDBs" />, identity directories (Active Directory, <DefineTerm term="Microsoft Entra ID (formerly Azure AD)" display="Microsoft Entra ID" />, <DefineTerm term="Okta" />), and <DefineTerm term="Threat Intelligence" display="threat-intelligence" /> feeds (Google Threat Intelligence, which now carries Mandiant's research; CrowdStrike; <DefineTerm term="Recorded Future" />) so the structured output is complete enough to act on.

## Why standardization matters

A single intrusion almost always produces telemetry across more than one format. Imagine an attacker phishes a user on a Windows laptop, the laptop reaches out through the corporate firewall to an external domain, the secure web gateway logs the same request, and the cloud identity provider records the resulting authentication. That is four formats describing one event:

<div class="story-grid">
  <div class="story-step">
    <span class="story-step__num">01</span>
    <span class="story-step__label">EVTX</span>
    <p>The Windows laptop writes a 4688 process-creation event to its Security log: the mail client spawning an unexpected child process under the user's account.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">02</span>
    <span class="story-step__label">Syslog</span>
    <p>The firewall sends a syslog message describing the outbound HTTPS connection: source IP, destination IP, port, and traffic volume.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">03</span>
    <span class="story-step__label">CEF</span>
    <p>The secure web gateway sends a CEF record for the same HTTPS request: vendor and product in the header, then user, URL, URL category, and action as extensions.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">04</span>
    <span class="story-step__label">JSON</span>
    <p>The cloud identity provider records a JSON event describing the federated login that followed (timestamp, user, IP, MFA result).</p>
  </div>
</div>

Four formats. Four different field names for the same concept. Four different timestamp conventions. Without standardization, the analyst has to write four parallel parsers in their head just to ask the basic question: did the same user account that triggered the laptop alert show up in the cloud identity log within the next ten minutes?

| Format | Where the time lives | What it means |
|---|---|---|
| EVTX | <code>TimeCreated SystemTime</code> | UTC |
| Syslog (RFC 3164) | The header timestamp | Local time, no year, no zone: the collector guesses |
| CEF | <code>rt=</code> | Epoch milliseconds or <code>MMM dd yyyy HH:mm:ss</code>, depending on the device |
| JSON (CloudTrail <code>eventTime</code>) | A named field | ISO 8601, UTC |

Normalize to UTC and write times in RFC 3339 form with an explicit offset (<code>2026-03-10T14:22:05Z</code>), so nobody downstream has to guess the zone. Record whether each timestamp is event time or ingest time, and note any known clock skew between sources: a ten-minute correlation window is meaningless across a five-minute skew.

That question is trivial when every event uses the same field names. It is hard when each format has its own vocabulary. Standardization is the engineering investment that makes the trivial version possible at scale.

## One shape: schema normalization

<DefineTerm term="Normalization" display="Normalization" /> maps every source's vendor-specific fields into a common schema, so a malicious <DefineTerm term="PowerShell" /> execution reported by the EDR and the related connection logged by the firewall land in the same structure with the same field names. These are the event schemas you will meet. Your console almost certainly speaks one of these; learn its field names for user, host, process and source IP first.

<div class="schema-grid">
  <div class="schema-card">
    <span class="schema-card__tag">Cross-vendor</span>
    <h3>OCSF</h3>
    <p>Open Cybersecurity Schema Framework, a Linux Foundation project since November 2024. Vendor-neutral, the native storage schema of Amazon Security Lake, and increasingly the default for cross-tool integration. If your platform supports it, prioritize it; check which schema version your tools emit, because OCSF ships several releases a year.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Elastic and OpenTelemetry</span>
    <h3>ECS</h3>
    <p>Elastic Common Schema, now merged into the OpenTelemetry semantic conventions. What you query in Elastic Security, and the field vocabulary a growing share of open collectors emit.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Splunk</span>
    <h3>CIM</h3>
    <p>Splunk's Common Information Model: data models (Authentication, Endpoint, Network Traffic) that searches and Enterprise Security correlation rules run against.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Microsoft Sentinel</span>
    <h3>ASIM</h3>
    <p>Advanced Security Information Model: query-time parsers that let one Sentinel query cover every source of a given event type.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Google SecOps</span>
    <h3>UDM</h3>
    <p>Unified Data Model: the normalized event and entity schema Google Security Operations parses every source into before rules and searches run.</p>
  </div>
</div>

Two standards often appear next to these and are not event schemas: <DefineTerm term="Structured Threat Information Expression (STIX)" display="STIX 2.1" /> carries threat intelligence (what an IOC means); <DefineTerm term="OpenC2" /> expresses response actions (what to do about it). Both matter to a SOC, but neither normalizes event telemetry.

Whatever schema you adopt, normalization maps diverse vendor-specific fields into four buckets. They line up with the <a href="/docs/alert/parsing/#three-categories-of-information-from-every-alert">three buckets in Reading any alert</a>: in schema terms, its Technical detail bucket splits into affected entities and primary observables.

<div class="principles-grid">
  <div class="principle-card">
    <span class="principle-card__num">01</span>
    <h3>Detection metadata</h3>
    <p>Alert name, detection logic, severity, confidence. Timestamps standardized to UTC in ISO 8601.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">02</span>
    <h3>Affected entities</h3>
    <p>Hostnames, IPs, user accounts, cloud assets, containers. Anything the alert references.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">03</span>
    <h3>Primary observables</h3>
    <p>File hashes, domains, URLs, registry keys, <DefineTerm term="IoC">Indicator of Compromise. An artifact that suggests intrusion: a file hash, domain, IP, registry key, or behavioral pattern. IOCs feed signature detection and post-event correlation.</DefineTerm>. The artifacts to correlate against.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">04</span>

Normalization also requires flattening nested structures where useful and harmonizing identifiers so automated cross-tool correlation works. Within ASSURED, prioritize normalization of detection metadata, affected entities, and primary observables. Those are the fields downstream phases depend on.

<Callout variant="info" title="Severity, confidence, and priority are three different numbers">
The detection-metadata bucket carries two fields that read alike and mean different things, and triage adds a third. <strong>Severity</strong> is the detection engineer's estimate of how bad the activity would be if real, set when the rule was written, before your environment entered the picture. <strong>Confidence</strong> is the detector's estimate of how likely the match is to be what it claims: a statement about the rule's precision, not about the threat. <strong>Priority</strong> is what triage produces: a provisional queue position set at intake from severity, confidence and asset or user criticality (see <a href="/docs/scope/criticality/">criticality</a>), then confirmed or revised in the <a href="/docs/risk/">Risk phase</a> once the evidence is in. It is the only one of the three the analyst owns. A critical-severity, low-confidence alert on a lab host and a medium-severity, high-confidence alert on a domain controller can rightly land in opposite queue positions.
</Callout>

<Callout variant="info" title="For platform owners, not the triage queue">
Maintaining the normalization layer is engineering work, not triage work. If you own the pipeline rather than the queue: document and version the mapping logic, test mappings against representative payloads before rollout, review on a cadence so vendor format drift gets caught early, and share ownership across <DefineTerm term="Security Operations" display="security operations" />, data engineering, and tool owners. Tools that help: <DefineTerm term="Cribl" />, <DefineTerm term="Logstash" />, <DefineTerm term="Fluentd" /> and Fluent Bit, Vector, the OpenTelemetry Collector, and the native normalization in modern SIEMs. The analyst's job is narrower: know which schema your console speaks and what got dropped on the way in.
</Callout>

## Check yourself

The Sysmon record, the firewall lines and the CEF record above describe the same minute on the same laptop. Before reading on, write down the fields you would join on and the first thing you would check about the times.

<Reveal summary="One way to answer">
Join on the user (<code>User</code> is <code>CORP\jdoe</code> in Sysmon, <code>suser</code> is <code>jdoe</code> in CEF, so normalize the domain prefix first), on the host's address (<code>src=10.20.4.17</code>, confirmed as the laptop's address at that time from DHCP or the EDR's host record), and on the destination (<code>198.51.100.23:443</code>). Then the times: Sysmon <code>UtcTime</code> and CEF <code>rt</code> are UTC, but the RFC 3164 firewall line has no zone, so confirm the collector's configuration before you put it on the same timeline. The process half of the connection (which process opened it) would come from Sysmon Event ID 3 or the EDR's network events, if they were collected.
</Reveal>

<KeyTakeaway>
Format diversity is the cost of having visibility everywhere. <DefineTerm term="Schema Normalization" display="Schema normalization" /> (OCSF, ECS, Splunk CIM, ASIM, UDM) is the investment that turns that diversity into one queryable dataset. Invisible when it works, painful when it does not, and the foundation every behavioral surface in this chapter builds on.
</KeyTakeaway>
