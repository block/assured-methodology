This page covers the plumbing under the behavioral surfaces: the formats telemetry arrives in, the platform sources that generate it, and the normalization that makes it all queryable as one dataset. It is not a surface of adversary behavior. It is the layer that determines whether you can read the surfaces at all.

## The four format families

<div class="formats-grid">
  <div class="format-card format-card--evtx">
    <div class="format-card__head">
      <span class="format-card__icon">🏢</span>
      <h3>Windows Event Logs (EVTX)</h3>
    </div>
    <p class="format-card__intro">
      Windows writes structured records to log channels (Security, System, Application, and many subscribed providers) using the EVTX file format. Each record has a numeric <DefineTerm term="Event ID">A short integer that identifies what kind of event the record describes. Windows publishes a catalog of event IDs (4624 for a successful logon, 4688 for a process creation, and so on). Within a provider the same ID always means the same kind of event, which is what makes EVTX queryable; across providers IDs collide (Sysmon's event 1 is process creation, the Security log's 4688 is too), so always read the ID together with its channel and provider.</DefineTerm> identifying what happened. Triage tooling parses the relevant IDs into structured fields.
    </p>
    <p class="format-card__sub">Common IDs an analyst will read:</p>
    <ul>
      <li><strong>Process events:</strong> 4688 (creation), 4689 (termination)</li>
      <li><strong>Authentication:</strong> 4624 (successful logon), 4625 (failed logon)</li>
      <li><strong>Privilege escalation:</strong> 4672 (special privileges assigned)</li>
      <li><strong>Account changes:</strong> 4738 (user account changed)</li>
    </ul>
  </div>

  <div class="format-card format-card--syslog">
    <div class="format-card__head">
      <span class="format-card__icon">🌐</span>
      <h3>Syslog (RFC 5424 / RFC 3164)</h3>
    </div>
    <p class="format-card__intro">
      <DefineTerm term="Syslog" /> is the long-standing standard for streaming text-formatted <DefineTerm term="Log" display="log" /> messages over the network. Each message carries a severity, a facility, a timestamp, and a free-form text body. RFC 5424 is the modern spec, but most network gear still emits the older BSD framing (RFC 3164), so expect both in one pipeline. It is the default format for Linux systems and most network devices because it is simple, universally supported, and easy to forward.
    </p>
    <p class="format-card__sub">Where you will see syslog:</p>
    <ul>
      <li><strong>Network devices:</strong> firewalls, routers, switches, load balancers</li>
      <li><strong>Linux systems:</strong> kernel logs, application events, auth events</li>
      <li><strong>Cloud platforms:</strong> container orchestration, microservice logs</li>
      <li><strong>IoT and OT:</strong> ICS, embedded devices</li>
    </ul>
  </div>

  <div class="format-card format-card--cef">
    <div class="format-card__head">
      <span class="format-card__icon">📋</span>
      <h3>Common Event Format (CEF)</h3>
    </div>
    <p class="format-card__intro">
      <DefineTerm term="CEF">Common Event Format. A log format pioneered by ArcSight that adds a structured header (vendor, product, event name, severity) and key-value extensions to a syslog-style line. CEF made it possible for many vendors to ship logs that SIEMs could parse without writing a custom parser per product.</DefineTerm> is the format that made multi-vendor SIEM ingestion practical. It overlays a structured header on a syslog message so the SIEM knows the vendor, product, severity, and event class without guessing.
    </p>
    <p class="format-card__sub">Common ecosystems:</p>
    <ul>
      <li><strong>SIEM platforms:</strong> ArcSight, QRadar, Splunk Enterprise Security</li>
      <li><strong>Standardized fields:</strong> device vendor, product, version, signature</li>
      <li><strong>Custom extensions:</strong> vendor-specific attributes</li>
      <li><strong>Integration:</strong> broad SOAR compatibility</li>
    </ul>
  </div>

  <div class="format-card format-card--json">
    <div class="format-card__head">
      <span class="format-card__icon">🔧</span>
      <h3>JSON / structured data</h3>
    </div>
    <p class="format-card__intro">
      Modern cloud and SaaS platforms emit logs as structured JSON. Every event is an object with named fields, which makes the data instantly queryable without <DefineTerm term="Parsing" display="parsing" /> tricks. Most modern SIEMs ingest JSON natively and store it as-is, preserving fidelity that older text formats lose.
    </p>
    <p class="format-card__sub">Where JSON dominates:</p>
    <ul>
      <li><strong>Cloud services:</strong> AWS CloudTrail, Azure Activity Logs, GCP audit logs</li>
      <li><strong>Modern SIEMs:</strong> native JSON ingestion</li>
      <li><strong>API streams:</strong> RESTful webhooks, event buses</li>
      <li><strong>Container telemetry:</strong> Kubernetes audit, container runtime events</li>
    </ul>
  </div>
</div>

## Where the telemetry comes from, per platform

Formats are only half the story. The behavioral surfaces in this chapter (process trees, command lines, file activity) depend on a telemetry source actually recording them, and the source differs by platform. Knowing which source feeds your console tells you what the data can and cannot show.

<div class="telem-grid">
  <div class="telem-card">
    <span class="telem-card__os">Windows</span>
    <h3><DefineTerm term="Sysmon" /></h3>
    <p>Free Sysinternals driver that logs rich process creations (Event ID 1, with full command line, hashes, and parent), network connections, DLL and driver loads, and more into its own EVTX channel. The de facto standard source for the process and command-line telemetry this chapter teaches, and the usual compensating control when Security 4688 is missing its command line.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">Linux</span>
    <h3>auditd and eBPF sensors</h3>
    <p>The kernel audit framework (<code>auditd</code>) records syscall-level events; an <code>execve</code> rule gives you process executions with arguments. Modern EDR and open tooling increasingly use eBPF sensors for the same visibility with less overhead. Either way, output typically flows out as syslog or JSON.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">macOS</span>
    <h3>Endpoint Security framework and unified log</h3>
    <p>Since macOS 10.15, EDR agents get process, file, and signing telemetry from Apple's <DefineTerm term="Endpoint Security framework">Apple's kernel-supported API (introduced in macOS 10.15) that delivers real-time process execution, file, and code-signing events to security agents. It replaced kernel extensions as the sanctioned way for EDR products to observe macOS activity.</DefineTerm>, which is where a macOS process tree like Case B's comes from. The unified log holds the OS's own high-volume record, queryable with <code>log show</code>.</p>
  </div>
  <div class="telem-card">
    <span class="telem-card__os">Cross-platform</span>
    <h3>osquery</h3>
    <p>Exposes the live state of Windows, macOS, and Linux hosts as SQL tables (processes, users, launch items, listening ports). Strong for point-in-time interrogation and fleet-wide hunting; it complements, rather than replaces, the streaming sources above.</p>
  </div>
</div>

<Callout variant="info" title="Data quality is half the work">
Alerts often arrive without full <DefineTerm term="Metadata" display="metadata" />. Parent process missing, asset identifier truncated, <DefineTerm term="Command Line" display="command line" /> cut off at a byte boundary. Advanced parsing systems integrate enrichment from CMDBs, identity directories (Active Directory, <DefineTerm term="Okta" />), and <DefineTerm term="Threat" display="threat" />-<DefineTerm term="Intelligence" display="intelligence" /> feeds (Mandiant, CrowdStrike, <DefineTerm term="Recorded Future" />) so the structured output is complete enough to act on.
</Callout>

## Why standardization matters

A single intrusion almost always produces <DefineTerm term="Telemetry" display="telemetry" /> across more than one format. Imagine an attacker phishes a <DefineTerm term="User" display="user" /> on a Windows laptop, the laptop reaches out through the corporate <DefineTerm term="Firewall" display="firewall" /> to an external <DefineTerm term="Domain" display="domain" />, the SIEM correlates the alert, and the cloud identity provider records the resulting authentication. That is four formats describing one event:

<div class="story-grid">
  <div class="story-step">
    <span class="story-step__num">01</span>
    <span class="story-step__label">EVTX</span>
    <p>The Windows laptop writes a 4688 process-creation event and a 4624 logon event to its local EVTX logs.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">02</span>
    <span class="story-step__label">Syslog</span>
    <p>The firewall sends a syslog message describing the outbound HTTPS connection: source IP, destination IP, port, and traffic volume.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">03</span>
    <span class="story-step__label">CEF</span>
    <p>The SIEM correlates the laptop's process activity with the firewall traffic and emits a CEF alert tagged with the threat category and severity.</p>
  </div>
  <div class="story-step">
    <span class="story-step__num">04</span>
    <span class="story-step__label">JSON</span>
    <p>The cloud identity provider records a JSON event describing the federated login that followed (timestamp, user, IP, MFA result).</p>
  </div>
</div>

Four formats. Four different field names for the same concept. Four different timestamp conventions. Without standardization, the analyst has to write four parallel parsers in their head just to ask the basic question: did the same <DefineTerm term="User Account" display="user account" /> that triggered the laptop alert show up in the cloud identity log within the next ten minutes?

That question is trivial when every event uses the same field names. It is hard when each format has its own vocabulary. Standardization is the engineering investment that makes the trivial version possible at scale.

<div class="standardization-benefits">
  <div class="benefit-row">
    <span class="benefit-row__icon">🔗</span>
    <div>
      <strong>Cross-source correlation.</strong> An identity field that means the same thing in EVTX, syslog, CEF, and JSON lets the SIEM join events across sources automatically.
    </div>
  </div>
  <div class="benefit-row">
    <span class="benefit-row__icon">🤖</span>
    <div>
      <strong>Automation that works on more than one source.</strong> SOAR playbooks need a predictable shape. Standardized data is what makes a playbook portable across alert sources.
    </div>
  </div>
  <div class="benefit-row">
    <span class="benefit-row__icon">📈</span>
    <div>
      <strong>Trend analysis at scale.</strong> Asking "how many failed authentications happened across all of our identity sources this week" is one query if the field names match. It is a research project if they do not.
    </div>
  </div>
  <div class="benefit-row">
    <span class="benefit-row__icon">📋</span>
    <div>
      <strong>Defensible audit trails.</strong> A regulator asking how a specific event was investigated wants to see the events in the same shape. Standardization makes that report a query, not a reconstruction.
    </div>
  </div>
</div>

## One shape: schema normalization

<DefineTerm term="Normalization" display="Normalization" /> maps every source's vendor-specific fields into a common schema, so a malicious <DefineTerm term="PowerShell" /> execution reported by the EDR and the related connection logged by the firewall land in the same structure with the same field names. Three open standards are worth knowing. Implementations differ; the goal is the same.

<div class="schema-grid">
  <div class="schema-card">
    <span class="schema-card__tag">Rising standard</span>
    <h3>OCSF</h3>
    <p>Open Cybersecurity Schema Framework. Vendor-neutral, cloud-friendly, increasingly the default for cross-tool integration. If your platform supports it, prioritize it.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Mature</span>
    <h3>STIX 2.1</h3>
    <p>Structured Threat Information Expression. Designed for sharing threat intelligence. Strong for indicators and TTPs. Less ergonomic for raw telemetry.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Action-oriented</span>
    <h3>OpenC2</h3>
    <p>Open Command and Control. Designed for expressing response actions in a portable way. Pairs well with STIX for indicators and OCSF for events.</p>
  </div>
</div>

Whatever schema you adopt, normalization maps diverse vendor-specific fields into four buckets:

<div class="principles-grid">
  <div class="principle-card">
    <span class="principle-card__num">01</span>
    <h4>Detection metadata</h4>
    <p>Alert name, detection logic, severity, confidence. Timestamps standardized to UTC in ISO 8601.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">02</span>
    <h4>Affected entities</h4>
    <p>Hostnames, IPs, user accounts, cloud assets, containers. Anything the alert references.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">03</span>
    <h4>Primary observables</h4>
    <p>File hashes, domains, URLs, registry keys, <DefineTerm term="IoC">Indicator of Compromise. An artifact that suggests intrusion: a file hash, domain, IP, registry key, or behavioral pattern. IoCs feed signature detection and post-event correlation.</DefineTerm>. The artifacts to correlate against.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">04</span>
    <h4>Contextual data</h4>
    <p>MITRE ATT&CK mappings, enrichment tags, kill-chain stage, threat-intelligence annotations.</p>
  </div>
</div>

Normalization also requires flattening nested structures where useful and harmonizing identifiers so automated cross-tool correlation works. Within ASSURED, prioritize normalization of detection <DefineTerm term="Metadata" display="metadata" />, affected entities, and primary observables. Those are the fields downstream phases depend on.

<Callout variant="info" title="Severity, confidence, and priority are three different numbers">
The detection-metadata bucket carries two fields that read alike and mean different things, and triage adds a third. <strong>Severity</strong> is the detection engineer's estimate of how bad the activity would be if real, set when the rule was written, before your environment entered the picture. <strong>Confidence</strong> is the detector's estimate of how likely the match is to be what it claims: a statement about the rule's precision, not about the threat. <strong>Priority</strong> is what triage produces: the queue position, computed from severity and confidence plus asset context during the <a href="/docs/risk/">Risk phase</a>, and the only one of the three the analyst owns. A critical-severity, low-confidence alert on a lab host and a medium-severity, high-confidence alert on a domain controller can rightly land in opposite queue positions.
</Callout>

<Callout variant="info" title="For platform owners, not the triage queue">
Maintaining the normalization layer is engineering work, not triage work. If you own the pipeline rather than the queue: document and version the mapping logic, test mappings against representative payloads before rollout, review on a cadence so vendor format drift gets caught early, and share ownership across <DefineTerm term="Security Operations" display="security operations" />, data engineering, and tool owners. Tools that help: <DefineTerm term="Logstash" />, <DefineTerm term="Fluentd" />, <DefineTerm term="Cribl" />, and the native normalization in modern SIEMs. The analyst's job is narrower: know which schema your console speaks and what got dropped on the way in.
</Callout>

<KeyTakeaway>
Format diversity is the cost of having visibility everywhere. <DefineTerm term="Schema Normalization" display="Schema normalization" /> (OCSF, STIX, <DefineTerm term="OpenC2" />) is the investment that turns that diversity into one queryable dataset. Invisible when it works, painful when it does not, and the foundation every behavioral surface in this chapter builds on.
</KeyTakeaway>
