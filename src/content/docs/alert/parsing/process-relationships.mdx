## Normal patterns

These are the lineages that should not surprise you. On Windows:

<div class="lineage-grid">
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>explorer.exe → winword.exe</code>
    <p>User-launched document activity.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>services.exe → svchost.exe</code>
    <p>Normal Windows service initiation.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>svchost.exe (Schedule) → &lt;scheduled binary&gt;</code>
    <p>Scheduled task execution: on modern Windows, tasks spawn from svchost.exe running the Schedule service, sometimes via taskhostw.exe. (taskeng.exe was retired in Windows 10 1511; on Windows 10/11 or Server 2016+ it does not exist, so seeing it there is a masquerading red flag.)</p>
  </div>
</div>

And on macOS, where <a href="/docs/alert/example/#case-b">Case B</a> in the Alert worked example (a macOS developer workstation running the Cursor IDE) lives:

<div class="lineage-grid">
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>launchd → &lt;almost everything&gt;</code>
    <p>launchd is PID 1: macOS's init process, service manager, and scheduler in one. Daemons, agents, and user-launched apps all ultimately descend from it, so "parent is launchd" carries far less signal than "parent is services.exe" does on Windows.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>Cursor → Cursor Helper (Plugin) → child</code>
    <p>Electron apps launch their core helpers (Renderer, GPU, network, utility) from the main app process. In VS Code-family editors such as Cursor, the extension-host helper then legitimately launches processes of its own: language servers, indexers, shells, git, language runtimes. The anomaly is a helper whose ancestry leads outside the app, or a helper binary running from outside the signed app bundle.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>Terminal.app → zsh → &lt;tool&gt;</code>
    <p>Interactive shell work descends from a terminal. The suspicious mirror image is a GUI app with no business shelling out (a PDF viewer, a chat client) spawning <code>bash</code> or <code>osascript</code>.</p>
  </div>
</div>

## Reading a macOS tree: signatures and notarization

Case B hands you this tree. Here is how to parse it:

```
launchd (PID 1)                         Apple platform binary
  └─ Cursor                             Developer ID: Anysphere, notarized
       ├─ Cursor Helper                 Developer ID: Anysphere, notarized
       └─ Cursor Helper (Plugin)        extension host, no sandbox
            └─ Cursor Helper (Plugin)   child: runs a script from inside Cursor.app
```

The alerted edge is the last one: the extension host launching a child that opened the outbound connections. It is vendor-documented behavior when the child's script lives inside the signed bundle, and the question to ask when it does not.

On macOS the tree gives you two extra parse targets that Windows lineage does not: the code-signing chain and notarization status. Together with the install path, they are strong evidence about provenance, not about behavior. Apple has notarized malware more than once (OSX.Shlayer payloads in 2020; a MacSync Stealer dropper in December 2025, whose certificate Apple later revoked). Notarization checks what was submitted, not what the app downloads after launch. So read signed-and-notarized as "who published it," and corroborate with path, Team ID reputation, peer baseline and behavior before clearing.

<div class="macos-parse">
  <div class="macos-parse__item">
    <h3>Signing identity</h3>
    <p>Apple's own platform binaries (launchd, the system daemons) are signed by Apple's Software Signing certificate. Third-party software is signed with a Developer ID certificate that names the vendor. The parse question is not "is it signed" but "who signed it, and does that match what the binary claims to be." Ad-hoc or missing signatures inside a tree of properly signed processes are the standout. Parse the Team ID, not just the name: it is the stable identifier, it is what intel reports and Apple revocations cite, and a lookalike vendor name with a different Team ID is a red flag. Mac App Store apps carry Apple's signature instead of a Developer ID.</p>
  </div>
  <div class="macos-parse__item">
    <h3>Notarization</h3>
    <p>Notarization is Apple's automated malware scan for third-party software distributed outside the App Store; Gatekeeper checks the ticket at first launch. Apple's own OS binaries are not notarized (they do not need to be), so "launchd is not notarized" is expected, while "this vendor app is not notarized" is a real flag on a managed fleet.</p>
  </div>
  <div class="macos-parse__item">
    <h3>Install path</h3>
    <p>A signed binary running from <code>/Applications</code> where the MDM (mobile device management) system installed it is baseline. The same binary name running out of <code>&#126;/Library</code>, <code>/tmp</code>, or a mounted DMG is staging. Signature says who built it; path says who put it there. <code>/Applications</code> is admin-writable, so the path counts only with the MDM record of what was installed there. Neither covers code the signed app loads at runtime: extensions, plugins, MCP servers.</p>
  </div>
</div>

Where does this telemetry come from? EDR agents on macOS consume the Endpoint Security framework for process and signing events; the [formats and normalization page](/docs/alert/parsing/multi-format/) covers the per-platform sources. The tells transfer directly: a hollowed-svchost equivalent does not exist on macOS, but "helper whose ancestry leads outside its app," "signed binary in the wrong path," and "unsigned process in a signed tree" are the same lineage-plus-trust reasoning this page teaches for Windows.

## What to flag

<Callout variant="info" title="Suspicious lineage signals">
- **Unexpected origins.** `notepad.exe` spawning `cmd.exe` or `powershell.exe`. Notepad should not be spawning anything.
- **Compressed timing.** Multiple processes launching within sub-second intervals suggests scripted automation. Installers and build systems produce the same burst legitimately, so weigh the parent process and the host's role before reading the burst as hostile.
- **Office spawning shells.** `winword.exe → cmd.exe → powershell.exe` is the classic macro-execution chain (rarer since Office began blocking macros in internet-sourced files by default in 2022).
- **Paste-and-run (ClickFix).** `explorer.exe → powershell.exe` or `mshta.exe` (or Windows Terminal → PowerShell in newer variants), with flags such as `-w h` and `iex(irm ...)`, seconds after a browser visit. Run-dialog variants leave the pasted command in `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU`. The user ran it themselves, so no exploit or attachment appears in the tree.
- **Other post-macro delivery.** A shortcut (`.lnk`) or script launched from a mounted ISO or an extracted archive (`wscript.exe`, `mshta.exe`, `cmd.exe` under explorer.exe), or `msiexec.exe` installing a package straight from a browser download.
- **System binaries in the wrong context.** A system binary (lsass.exe, services.exe, svchost.exe) running as a standard user, or from outside System32, or with an unexpected parent.
</Callout>

A direct spawn of `msdt.exe` by `winword.exe` strongly suggests exploitation of <DefineTerm term="Follina">CVE-2022-30190. A vulnerability in the Microsoft Support Diagnostic Tool that allowed a malicious Office document to trigger remote code execution via a crafted URL handler.</DefineTerm>, where a malicious document triggers the Microsoft Support Diagnostic Tool to run attacker-controlled code. (Microsoft patched Follina in the June 2022 cumulative updates and has deprecated MSDT itself, so on a patched host the chain is rare. Any Office process spawning msdt.exe is still worth investigating on its own.)

The activity looks like the impersonated user. Detection depends on lineage plus logon data: a child running as a different user than its parent with no matching 4624/4648 logon, a LogonId that belongs to another session, or Logon Type 9 (NewCredentials) from runas /netonly-style token creation.
    </p>
  </div>
</div>

- The originating email and attachment in the user's mailbox.
- Other recipients of the same email (lateral exposure).
- The <DefineTerm term="PowerShell" /> <DefineTerm term="Command Line" display="command line" /> for download cradle patterns.

Macros do not run in the preview pane or Protected View.

## Reconstructing the tree

A tree in a console is a reconstruction, stitched together from individual process-creation events. Four mechanics decide whether the stitching is right:

- **Join on unique IDs, never on PID alone.** Windows reuses PIDs, and so do macOS and Linux. Join on Sysmon's <code>ProcessGuid</code> / <code>ParentProcessGuid</code> or the EDR's unique process ID, plus start time. A PID join can attach a child to an unrelated process that later got the same number.
- **Exited and orphaned parents.** A child keeps its parent's PID after the parent exits, and live tools then show it with no parent at all, or with a new process that inherited the number. Rebuild from the historical creation events, not from what is running now.
- **Creator versus parent.** Usually the same process. They differ when a broker launches something on another process's behalf (<code>wmiprvse.exe</code> for WMI, <code>services.exe</code> for a service, a COM server, the Secondary Logon service for runas) and when the parent was deliberately forged (see parent PID spoofing below). When the parent is a broker, look one hop further back for who asked.
- **Missing links.** A parent with no creation event of its own is a visibility gap. Record it as one rather than filling it with the most likely story.

<Reveal summary="Annotated sample: why a PID join goes wrong" variant="deep-dive">

Three Sysmon Event ID 1 records from one laptop on one day, trimmed to the join fields. The samples are fictional; the field names are real.

```text
UtcTime                  ProcessGuid                             ProcessId  Image
2026-03-10 09:02:17.114  {6a1f0c3e-1a02-65f0-2210-000000001a00}  7500       OneDrive.exe     (exited 09:40)
2026-03-10 14:20:51.302  {6a1f0c3e-2b7c-65f0-3b19-000000001a00}  7500       WINWORD.EXE
2026-03-10 14:22:04.871  {6a1f0c3e-2b7d-65f0-4c1a-000000001a00}  8128       powershell.exe
                         ParentProcessGuid={6a1f0c3e-2b7c-65f0-3b19-000000001a00}  ParentProcessId=7500
```

- PID 7500 was used twice that day. A join on <code>ParentProcessId</code> alone returns both OneDrive and Word as candidate parents, and a query that keeps the first match puts PowerShell under OneDrive.
- <code>ParentProcessGuid</code> matches exactly one record, Word's. The GUID is unique per process start, which is the whole point of it.
- Without Sysmon, use the EDR's own unique process ID, or join on host plus PID plus a start time that falls inside the parent's lifetime, and record the join as weaker.

</Reveal>

## Evasion to know about

Adversaries who understand process tree analysis design their tradecraft to look normal in the tree. The five techniques below are ones an analyst will meet in real intrusions, each defeating a different layer of tree analysis (process hollowing, covered above, is a sixth). Recognizing them by name accelerates the moment of "wait, that is not what it looks like."

<div class="evasion-detail-list">
  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="m12.83 2.18a2 2 0 0 0-1.66 0L2.6 6.08a1 1 0 0 0 0 1.83l8.58 3.91a2 2 0 0 0 1.66 0l8.58-3.9a1 1 0 0 0 0-1.83Z"/><path d="m22 17.65-9.17 4.16a2 2 0 0 1-1.66 0L2 17.65"/><path d="m22 12.65-9.17 4.16a2 2 0 0 1-1.66 0L2 12.65"/></svg></span>
      <h3>DLL hijacking and side-loading (T1574.001)</h3>
    </div>
    <p>
      A <DefineTerm term="DLL">Dynamic Link Library. A shared library that Windows loads into a process at runtime to provide functions the process uses. Programs name the DLLs they need; Windows finds them by searching a defined order of directories.</DefineTerm> is loaded by a legitimate binary from one of several search paths in a defined order. An adversary places a malicious DLL earlier in that order than the real one. The legitimate, signed binary loads the malicious DLL instead of the real one, executing attacker code under the trust of the original program. The most common variant today is side-loading: a signed vendor EXE copied into a user-writable folder next to a malicious DLL with the name it expects.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a process tree that looks normal at the binary level, but with a DLL that was loaded from an unusual location (a writable directory, the user profile, a removable drive). EDRs that track DLL loads can flag this. Tree views that only show processes cannot.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M10.733 5.076a10.744 10.744 0 0 1 11.205 6.575 1 1 0 0 1 0 .696 10.747 10.747 0 0 1-1.444 2.49"/><path d="M14.084 14.158a3 3 0 0 1-4.242-4.242"/><path d="M17.479 17.499a10.75 10.75 0 0 1-15.417-5.151 1 1 0 0 1 0-.696 10.75 10.75 0 0 1 4.446-5.143"/><path d="m2 2 20 20"/></svg></span>
      <h3>Fileless execution</h3>
    </div>
    <p>
      <DefineTerm term="fileless">An execution model that runs the malicious payload entirely from memory, without ever writing it to disk. Common techniques include PowerShell loading code via reflection, WMI event subscriptions whose consumers execute script payloads (created through the WMI API, for example from PowerShell, or by compiling a MOF file with mofcomp; stored in the WMI repository; Sysmon events 19-21 record them), and .NET assemblies loaded straight into memory.</DefineTerm> attacks run their payload from memory, never landing on disk. Disk-based detections (file hashes, AV scans, file integrity monitoring) see nothing. The process tree shows only legitimate parents (often PowerShell or WMI).
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a long-running PowerShell or WMI process with a command line that decodes a base64 blob and executes it, or a WMI event subscription that fires at boot. Memory analysis and command-line decoding catch this; surface process inspection does not.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M15 2H6a2 2 0 0 0-2 2v16a2 2 0 0 0 2 2h12a2 2 0 0 0 2-2V7Z"/><path d="M14 2v4a2 2 0 0 0 2 2h4"/></svg></span>
      <h3>Alternate data streams (ADS, T1564.004; legacy)</h3>
    </div>
    <p>
      NTFS supports multiple data streams per file. The default stream is what most tools and users see. An <DefineTerm term="alternate data stream">A secondary data stream attached to an NTFS file. The primary stream is what you see in Explorer. The alternate stream is invisible to most tools but can be opened and executed directly. Used historically to hide payloads inside otherwise innocuous files.</DefineTerm> can hide a payload inside a normal-looking file, and the malicious code can be invoked directly from the stream.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a process whose image path has a second colon after the filename (<code>C:\Users\victim\readme.txt:hidden.exe</code>). Sysmon Event 15 (FileCreateStreamHash) records stream creation. Most modern EDRs flag ADS execution, but the technique is still seen in older or under-instrumented environments.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M14.7 6.3a1 1 0 0 0 0 1.4l1.6 1.6a1 1 0 0 0 1.4 0l3.77-3.77a6 6 0 0 1-7.94 7.94l-6.91 6.91a2.12 2.12 0 0 1-3-3l6.91-6.91a6 6 0 0 1 7.94-7.94l-3.76 3.76z"/></svg></span>
      <h3>LOLBin-only chains (T1218)</h3>
    </div>
    <p>
      The adversary uses only trusted system binaries (<DefineTerm term="LOLBins" display="LOLBins" /> such as <code>certutil</code>, <code>regsvr32</code>, <code>mshta</code>, <code>rundll32</code>) to download, decode, and execute attacker code. Payload files may land on disk (<code>certutil -urlcache -f</code> writes the target file, and certutil can leave a copy under CryptnetUrlCache, which is where file telemetry catches them), but no unsigned attacker executable runs, and no signature on any running binary is wrong.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> common system binaries being invoked with command-line flags they almost never use in legitimate operations (<code>certutil -urlcache -split -f</code>, <code>regsvr32 /s /u /n /i:http://...</code>). Command-line parsing is what catches this; the process names alone look harmless.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon" aria-hidden="true"><svg viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"><path d="M16 21v-2a4 4 0 0 0-4-4H6a4 4 0 0 0-4 4v2"/><circle cx="9" cy="7" r="4"/><path d="M22 21v-2a4 4 0 0 0-3-3.87"/><path d="M16 3.13a4 4 0 0 1 0 7.75"/></svg></span>
      <h3><DefineTerm term="Parent PID Spoofing" display="Parent PID spoofing" /> (T1134.004)</h3>
    </div>
    <p>
      The creating process asks Windows to record a different parent (CreateProcess with an explicit parent-process attribute, <code>PROC_THREAD_ATTRIBUTE_PARENT_PROCESS</code>), naming any process it has a handle to. A payload launched by Word then appears as a child of <code>explorer.exe</code>, and the tree tells a plausible story that never happened.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> the reported parent disagrees with the actual creator recorded by EDR or kernel ETW process telemetry, or the reported parent was not running interactively at the child's start time. Sysmon and Security 4688 record only the reported parent, so tools that show only it cannot see the spoof.
    </p>
  </div>
</div>

Under all of these sits one more layer: if the EDR agent itself is silenced (for example, by bring-your-own-vulnerable-driver tooling that kills it), the tree simply stops. A host that goes quiet in the middle of an incident is a finding, not a clean bill.

## Check yourself

An EDR tree shows <code>explorer.exe → rundll32.exe</code> on a finance workstation, with <code>rundll32.exe</code> loading a DLL from <code>%LOCALAPPDATA%\Temp</code>. The EDR's creator field for <code>rundll32.exe</code> names <code>excel.exe</code>, and Excel had a spreadsheet from an email open at the time. Parse it before you open the answer.

<Reveal summary="One way to answer">
The reported parent (explorer.exe) disagrees with the creator the EDR recorded (excel.exe), which is the parent PID spoofing telltale: the real lineage is Excel spawning rundll32, an Office-spawns-a-LOLBin chain dressed up as a user double-click. The DLL path is a user-writable temp directory, so the loaded module is the payload to hash and pivot on. Next: how the spreadsheet's macro got permission to run (Mark of the Web, Enable Content, container), the DLL's creation event and its source, and the network activity of the rundll32 process by its unique process ID.
</Reveal>
