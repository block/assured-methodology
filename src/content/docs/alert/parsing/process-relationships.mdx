## Normal patterns

These are the lineages that should not surprise you. On Windows:

<div class="lineage-grid">
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>explorer.exe → winword.exe</code>
    <p>User-launched document activity.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>services.exe → svchost.exe</code>
    <p>Normal Windows service initiation.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>svchost.exe (Schedule) → &lt;scheduled binary&gt;</code>
    <p>Scheduled task execution: on modern Windows, tasks spawn from svchost.exe running the Schedule service, sometimes via taskhostw.exe. (taskeng.exe was retired in 2015; seeing it on a current build is itself a masquerading red flag.)</p>
  </div>
</div>

And on macOS, where the Alert chapter's own Case B lives:

<div class="lineage-grid">
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>launchd → &lt;almost everything&gt;</code>
    <p>launchd is PID 1: macOS's init process, service manager, and scheduler in one. Daemons, agents, and user-launched apps all ultimately descend from it, so "parent is launchd" carries far less signal than "parent is services.exe" does on Windows.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>Cursor → Cursor Helper (Plugin)</code>
    <p>Electron and browser apps spawn their helpers (Renderer, GPU, Plugin, Utility) as direct children of the main app process, never of each other. A "helper" whose parent is not its own main app is the macOS lineage anomaly worth your attention.</p>
  </div>
  <div class="lineage-card lineage-card--ok">
    <span class="lineage-card__label">Expected</span>
    <code>Terminal.app → zsh → &lt;tool&gt;</code>
    <p>Interactive shell work descends from a terminal. The suspicious mirror image is a GUI app with no business shelling out (a PDF viewer, a chat client) spawning <code>bash</code> or <code>osascript</code>.</p>
  </div>
</div>

## Reading a macOS tree: signatures and notarization

Case B in the <a href="/docs/alert/example/">Alert worked example</a> hands you this tree. Here is how to parse it:

```
launchd (PID 1)                      Apple platform binary
  └─ Cursor                          Developer ID: Anysphere, notarized
       ├─ Cursor Helper              Developer ID: Anysphere, notarized
       └─ Cursor Helper (Plugin)     Developer ID: Anysphere, notarized
```

On macOS the tree gives you two extra parse targets that Windows lineage does not: the code-signing chain and notarization status. Together with the install path, they are the exculpatory (or damning) evidence.

<div class="macos-parse">
  <div class="macos-parse__item">
    <h4>Signing identity</h4>
    <p>Apple's own platform binaries (launchd, the system daemons) are signed by Apple's Software Signing certificate. Third-party software is signed with a Developer ID certificate that names the vendor. The parse question is not "is it signed" but "who signed it, and does that match what the binary claims to be." Ad-hoc or missing signatures inside a tree of properly signed processes are the standout.</p>
  </div>
  <div class="macos-parse__item">
    <h4>Notarization</h4>
    <p>Notarization is Apple's automated malware scan for third-party software distributed outside the App Store; Gatekeeper checks the ticket at first launch. Apple's own OS binaries are not notarized (they do not need to be), so "launchd is not notarized" is expected, while "this vendor app is not notarized" is a real flag on a managed fleet.</p>
  </div>
  <div class="macos-parse__item">
    <h4>Install path</h4>
    <p>A signed binary running from <code>/Applications</code> where the MDM installed it is baseline. The same binary name running out of <code>~/Library</code>, <code>/tmp</code>, or a mounted DMG is staging. Signature says who built it; path says who put it there.</p>
  </div>
</div>

Where does this telemetry come from? EDR agents on macOS consume the Endpoint Security framework for process and signing events; the [formats and normalization page](/docs/alert/parsing/multi-format/) covers the per-platform sources. The tells transfer directly: a hollowed-svchost equivalent does not exist on macOS, but "helper with the wrong parent," "signed binary in the wrong path," and "unsigned process in a signed tree" are the same lineage-plus-trust reasoning this page teaches for Windows.

## What to flag

<Callout variant="info" title="Suspicious lineage signals">
- **Unexpected origins.** `notepad.exe` spawning `wmic.exe`. Notepad should not be spawning anything.
- **Compressed timing.** Multiple processes launching within sub-second intervals suggests scripted automation. Installers and build systems produce the same burst legitimately, so weigh the parent process and the host's role before reading the burst as hostile.
- **Office spawning shells.** `winword.exe → cmd.exe → powershell.exe` is the classic macro-execution chain.
- **System binaries in <DefineTerm term="User" display="user" /> contexts.** Elevated processes running with anomalous parent-child relationships.
</Callout>

A direct spawn of `msdt.exe` by `winword.exe` strongly suggests exploitation of <DefineTerm term="Follina">CVE-2022-30190. A vulnerability in the Microsoft Support Diagnostic Tool that allowed a malicious Office document to trigger remote code execution via a crafted URL handler.</DefineTerm>, where a malicious document triggers the Microsoft Support Diagnostic Tool to run attacker-controlled code.

<CaseStudy
  title="Reconstructing a macro-borne intrusion"
  scenario="An EDR alert reports anomalous child processes spawned by Microsoft Word on a finance team workstation."
>

Process tree investigation reveals:

```
winword.exe (PID 3421)
  └─ cmd.exe (PID 3422)
       └─ powershell.exe (PID 3423)
            └─ outbound TLS connection to a recently registered domain
```

The chain alone is enough to recognize the pattern: macro <DefineTerm term="Execution" display="execution" /> from a document, shell launch, scripted download cradle, command-and-control establishment. The exact IP is not the point. The shape of the chain is.

<Reveal summary="What an analyst checks next">
- The originating email and attachment in the user's mailbox.
- Other recipients of the same email (lateral exposure).
- The <DefineTerm term="PowerShell" /> <DefineTerm term="Command Line" display="command line" /> for download cradle patterns.
- DNS queries from the host in the relevant window.
- File system creates in `%TEMP%` and `%APPDATA%` correlated to the PowerShell PID.
- Whether the user opened the document themselves or it executed on preview.
</Reveal>

</CaseStudy>

## Evasion to know about

Adversaries who understand process tree analysis design their tradecraft to look normal in the tree. The four techniques below are the most common evasions an analyst will encounter in real intrusions. Recognizing them by name accelerates the moment of "wait, that is not what it looks like."

<div class="evasion-detail-list">
  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon">🪤</span>
      <h4>DLL search order hijacking</h4>
    </div>
    <p>
      A <DefineTerm term="DLL">Dynamic Link Library. A shared library that Windows loads into a process at runtime to provide functions the process uses. Programs name the DLLs they need; Windows finds them by searching a defined order of directories.</DefineTerm> is loaded by a legitimate binary from one of several search paths in a defined order. An adversary places a malicious DLL earlier in that order than the real one. The legitimate, signed binary loads the malicious DLL instead of the real one, executing attacker code under the trust of the original program.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a process tree that looks normal at the binary level, but with a DLL that was loaded from an unusual location (a writable directory, the user profile, a removable drive). EDRs that track DLL loads can flag this. Tree views that only show processes cannot.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon">👻</span>
      <h4>Fileless execution</h4>
    </div>
    <p>
      <DefineTerm term="fileless">An execution model that runs the malicious payload entirely from memory, without ever writing it to disk. Common techniques include PowerShell loading code via reflection, WMI event subscriptions whose consumers execute script payloads (the MOF defining them is compiled into the WMI repository at persistence time), and .NET assemblies loaded straight into memory.</DefineTerm> attacks run their payload from memory, never landing on disk. Disk-based detections (file hashes, AV scans, file integrity monitoring) see nothing. The process tree shows only legitimate parents (often PowerShell or WMI).
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a long-running PowerShell or WMI process with a command line that decodes a base64 blob and executes it, or a WMI event subscription that fires at boot. Memory analysis and command-line decoding catch this; surface process inspection does not.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon">📑</span>
      <h4>Alternate data streams (ADS)</h4>
    </div>
    <p>
      NTFS supports multiple data streams per file. The default stream is what most tools and users see. An <DefineTerm term="alternate data stream">A secondary data stream attached to an NTFS file. The primary stream is what you see in Explorer. The alternate stream is invisible to most tools but can be opened and executed directly. Used historically to hide payloads inside otherwise innocuous files.</DefineTerm> can hide a payload inside a normal-looking file, and the malicious code can be invoked directly from the stream.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> a process whose image path includes a colon (<code>C:\Users\victim\readme.txt:hidden.exe</code>). The format <code>file:stream</code> is the giveaway. Most modern EDRs flag ADS execution, but the technique is still seen in older or under-instrumented environments.
    </p>
  </div>

  <div class="evasion-detail">
    <div class="evasion-detail__head">
      <span class="evasion-detail__icon">🛠️</span>
      <h4>LOLBin-only chains</h4>
    </div>
    <p>
      The adversary uses only trusted system binaries (<DefineTerm term="LOLBins" display="LOLBins" /> such as <code>certutil</code>, <code>regsvr32</code>, <code>mshta</code>, <code>rundll32</code>) to download, decode, and execute attacker code. No malicious file is ever written to disk by the adversary, and no signature on any of the binaries is wrong.
    </p>
    <p class="evasion-detail__tell">
      <strong>The telltale:</strong> common system binaries being invoked with command-line flags they almost never use in legitimate operations (<code>certutil -urlcache -split -f</code>, <code>regsvr32 /s /u /n /i:http://...</code>). Command-line parsing is what catches this; the process names alone look harmless.
    </p>
  </div>
</div>

</KeyTakeaway>
