## Why alert fatigue is a schema problem

Analysts face a flood of alerts from multiple systems, each using distinct field names, timestamp conventions, and nested structures. Without <DefineTerm term="Normalization" display="normalization" />:

<div class="schema-pain-grid">
  <div class="schema-pain-card">
    <div class="schema-pain-card__icon">🔊</div>
    <h4>Signal buried in noise</h4>
    <p>Critical indicators get lost in irrelevant fields and inconsistent naming.</p>
  </div>
  <div class="schema-pain-card">
    <div class="schema-pain-card__icon">⏱️</div>
    <h4>Investigations slow down</h4>
    <p>Analysts spend cycles reconciling field formats instead of investigating.</p>
  </div>
  <div class="schema-pain-card">
    <div class="schema-pain-card__icon">📈</div>
    <h4>MTTR inflates</h4>
    <p>Mean time to response grows linearly with alert volume.</p>
  </div>
</div>

A malicious <DefineTerm term="PowerShell" /> <DefineTerm term="Execution" display="execution" /> detected by an EDR generates an alert with proprietary fields. The related network connection logged by a <DefineTerm term="Firewall" display="firewall" /> or cloud proxy appears in a completely different format. Linking them manually requires effort that scales with volume. Volume keeps going up.

---

## The schemas that matter

Three open standards are worth knowing. Implementations differ; the goal is the same.

<div class="schema-grid">
  <div class="schema-card">
    <span class="schema-card__tag">Rising standard</span>
    <h3>OCSF</h3>
    <p>Open Cybersecurity Schema Framework. Vendor-neutral, cloud-friendly, increasingly the default for cross-tool integration. If your platform supports it, prioritize it.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Mature</span>
    <h3>STIX 2.1</h3>
    <p>Structured Threat Information Expression. Designed for sharing threat intelligence. Strong for indicators and TTPs. Less ergonomic for raw telemetry.</p>
  </div>
  <div class="schema-card">
    <span class="schema-card__tag">Action-oriented</span>
    <h3>OpenC2</h3>
    <p>Open Command and Control. Designed for expressing response actions in a portable way. Pairs well with STIX for indicators and OCSF for events.</p>
  </div>
</div>

## Core normalization principles

Whatever schema you adopt, normalization maps diverse vendor-specific fields into four buckets:

<div class="principles-grid">
  <div class="principle-card">
    <span class="principle-card__num">01</span>
    <h4>Detection metadata</h4>
    <p>Alert name, detection logic, severity, confidence. Timestamps standardized to UTC in ISO 8601.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">02</span>
    <h4>Affected entities</h4>
    <p>Hostnames, IPs, user accounts, cloud assets, containers. Anything the alert references.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">03</span>
    <h4>Primary observables</h4>
    <p>File hashes, domains, URLs, registry keys, <DefineTerm term="IoC">Indicator of Compromise. An artifact that suggests intrusion: a file hash, domain, IP, registry key, or behavioral pattern. IoCs feed signature detection and post-event correlation.</DefineTerm>. The artifacts to correlate against.</p>
  </div>
  <div class="principle-card">
    <span class="principle-card__num">04</span>
    <h4>Contextual data</h4>
    <p>MITRE ATT&CK mappings, enrichment tags, kill-chain stage, threat-intelligence annotations.</p>
  </div>
</div>

Normalization also requires flattening nested structures where useful and harmonizing identifiers so automated cross-tool correlation works.

## Governance and sustainability

Normalization is not a one-time project. As new data sources arrive, as vendors update their formats, as new schemas emerge, the normalization layer needs maintenance.

<Callout variant="info" title="Treat it like infrastructure">
- Document the mapping logic and version it.
- Test mappings against representative payloads before production rollout.
- Collaborate across <DefineTerm term="Security Operations" display="security operations" />, data engineering, and tool owners. None of them can do this alone.
- Set a regular review cadence so format drift gets caught early.
</Callout>

Tools that help: **<DefineTerm term="Logstash" />**, **<DefineTerm term="Fluentd" />**, **<DefineTerm term="Cribl" />**, and the native normalization capabilities in modern SIEMs.

Within ASSURED, prioritize normalization of detection <DefineTerm term="Metadata" display="metadata" />, affected entities, and primary observables. Those are the fields downstream phases depend on.

<KeyTakeaway>
<DefineTerm term="Schema Normalization" display="Schema normalization" /> is the unsung <DefineTerm term="Infrastructure" display="infrastructure" /> of effective triage. Invisible when it works. Painful when it does not. The foundation everything else builds on.
</KeyTakeaway>
