Reading a methodology and running one are different skills, and the gap between them only closes on cases. The eight packets on this page are synthetic cases built for practice: realistic artifacts, tasks phased to the seven letters, and an answer key that stays sealed until you have written your own answers. They are deliberately not the worked-example cases from the chapters, whose verdicts you already know. When you are ready to pull the evidence yourself, the <a href="/docs/labs/">telemetry labs</a> run the same seven phases on public attack telemetry.

## How to work a packet

<ul class="ex-howto">
  <li><strong>Write before you peek.</strong> Work every task in writing: actual close-note sentences, not mental bullet points. The traps this practice exists to catch (see <a href="/docs/cognitive-traps/">Cognitive traps</a>) live in the gap between "I basically know" and what ends up on the page.</li>
  <li><strong>Use the real templates.</strong> Where a task asks for a record, fill the corresponding <a href="/docs/documentation/templates/">downloadable template</a>. The friction is the training.</li>
  <li><strong>Then open the key.</strong> Each key gives a model answer phase by phase, the common failure for each phase, the traps planted in the packet, and a scoring grid. Your answer does not need to match the model; it needs to survive comparison with it.</li>
  <li><strong>In a group, debrief out loud.</strong> The <a href="/docs/teaching/">teaching guide</a> has session plans, timings, and debrief questions for running these as workshops.</li>
</ul>

## Exercise 1 · The print server's new scheduled task

<p class="ex-meta"><span class="ex-tag">Full arc</span> <span class="ex-tag">Guided</span> <span class="ex-tag">60-90 minutes</span></p>

**Briefing.** Sunday, 03:41 UTC. You are the on-shift analyst. One alert is in the queue.

<pre><code>{`SIEM alert, 03:41:02 UTC
  rule:      Scheduled task created by service account (rule-4698-svc)
  severity:  Medium
  host:      prt-01 (Windows Server 2019, print services)
  event:     4698 (scheduled task created)
  task name: \\Microsoft\\Windows\\UpdateHealth
  action:    powershell.exe -NoP -W Hidden -EncodedCommand JAB3AGMAPQBOAGUA...
  principal: svc-printmgmt`}</code></pre>

Pulling the host's authentication log and the proxy log for context gives you two more artifacts:

<pre><code>{`Authentication log excerpt, prt-01
  03:22:17  4624  logon type 3 (network)            svc-printmgmt  from 10.20.8.114 (wkst-hr-22)
  03:24:05  4624  logon type 10 (RemoteInteractive)  svc-printmgmt  from 10.20.8.114 (wkst-hr-22)
  90-day baseline: svc-printmgmt appears on prt-01 as a service logon only;
  no interactive or RDP logons on record`}</code></pre>

<pre><code>{`Proxy log excerpt
  03:44:51  prt-01  CONNECT files-cdn-sync.example:443  allowed  bytes_out=2.1 MB
  90-day baseline: prt-01 outbound is Windows Update and print-vendor telemetry only`}</code></pre>

**Tasks.** Work each phase in order. Write your answers before opening the key.

<ol class="ex-tasks">
  <li><strong>Alert.</strong> State the claim the rule makes, and which detection mechanism this is. What is your first parsing action on the alert payload? Which of the three artifacts carries the most validation weight, and why?</li>
  <li><strong>Subject.</strong> The named principal is a service account. Who acted? List the candidate answers and the evidence that discriminates between them. Run the four dimensions on what you decide the subject is.</li>
  <li><strong>Scope.</strong> Draw the initial boundary: entities, time window, and lookback. Name one thing you are deliberately leaving out of scope, and the observation that would pull it in.</li>
  <li><strong>Uncover.</strong> List the sources you would pull, in order, with the question each answers. What are the two questions your timeline must answer before Risk can score this? Where does your hypothesis ledger stand: what is the leading hypothesis, and what is the strongest surviving alternative?</li>
  <li><strong>Risk.</strong> Score impact and likelihood separately, one paragraph of justification each, and label your confidence in the likelihood judgment. What cell and priority does the matrix give, and what move does Risk recommend?</li>
  <li><strong>Escalation decision.</strong> Which escalation criteria are confirmed by a supplied artifact, and which are one query away? Close or escalate: on what basis, on what clock, and what would change the answer?</li>
  <li><strong>Documentation.</strong> Write the record's summary paragraph. Then write one detection-engineering feedback item this case earns, and say which event it targets.</li>
  <li><strong>Stretch: the handoff.</strong> Fill sections 1, 5, 6 and 8 of the <a href="/templates/handoff-packet.md" download>handoff packet</a>. In section 6, state what you deliberately did not do, and why.</li>
</ol>

<Reveal summary="Answer key: Exercise 1" variant="example">

**Alert.**

- The rule claims a service account created a scheduled task: a rule-based detection on event 4698.
- First parsing action: decode the command. Part of the answer is honesty about what the packet actually contains. The alert carries only the payload's opening characters: "JAB3AGMAPQBOAGUA…" decodes (base64, UTF-16LE) to "$wc=Ne". That is consistent with "$wc=New-Object Net.WebClient", a stock PowerShell downloader idiom. "Consistent with" is a hypothesis, not a finding.
- The full decoded command sits in the 4698 event data (the TaskContent field). Pulling it is this case's first evidence request.
- The heaviest validation artifact is the authentication log. Logon type 10 means someone opened an interactive RDP (Remote Desktop Protocol) desktop as a service account, and the baseline says that has never happened in 90 days. Task-creation alerts are common; a service account with an RDP session is the anomaly that carries the case.
- Note the 03:22 type 3 as well. RDP with Network Level Authentication (NLA) logs a type 3 seconds before the type 10, so a gap of nearly two minutes points to separate network access first (a file share over SMB, the Server Message Block protocol, or remote administration). Either way it is also off-baseline, and the authentication package and logon process fields in that 4624 are worth pulling.

*Common failure:* writing "downloader" as a finding because the first six characters fit the idiom.

**Subject.**

- The principal on the alert is svc-printmgmt, but a service account is a credential, not an actor. Candidates: (a) an administrator legitimately using the account, (b) an automation process on wkst-hr-22, (c) a human attacker who has obtained the account's credentials and is operating from wkst-hr-22.
- The logon type discriminates against (b). Service (type 5) and network (type 3) logons are the normal lanes for service and automation accounts, and svc-printmgmt's 90-day baseline on prt-01 contains nothing else. Some RPA (robotic process automation) platforms do open RDP sessions, but from the robot machine to itself under a known robot account. A type 10 session from an HR workstation into a print server, under a print-management account, fits neither.
- Between (a) and (c) the supplied artifacts cannot decide (both put a human on wkst-hr-22 holding the credential). The checks that separate them, a change-ticket search and one message to the account's owning team, are evidence requests the model answer states rather than presumes.
- The working subject is whoever was interactive on wkst-hr-22 at 03:24, acting through the service account.
- Four dimensions on that composite subject. Authentication: abnormal (first RemoteInteractive logon in the 90-day baseline). Authorization: unestablished (nothing supplied gives an HR workstation a maintenance path to a print server, and no change record is in the packet; verify, do not assume). Behavior: abnormal (task creation, hidden-window encoded PowerShell). Relationships: now spanning two hosts and one service identity.

*Common failure:* treating svc-printmgmt as the subject and stopping there.

**Scope.**

- Entities: prt-01, svc-printmgmt, wkst-hr-22, and wkst-hr-22's assigned user as a distinct fourth entity whose own compromise is now the leading question.
- Window: 03:00 UTC to now for the activity in front of you. Add a longer lookback (7 days minimum) on wkst-hr-22: if the credential was taken from that workstation, the theft happened at some earlier, unknown time. The lookback prices that hypothesis without asserting it.
- Deliberately out: the other print servers and every other host svc-printmgmt can reach, until Uncover produces evidence of contact. The observation that pulls them in is any successful authentication sourced from either host inside the window.

*Common failure:* scoping every host the account can reach on day one, or giving wkst-hr-22 no lookback.

**Uncover.**

- Sources in order, each with its question:
  - the full decoded command from the 4698 event data (what does the task actually run?);
  - EDR (endpoint detection and response) on wkst-hr-22 (is it compromised, and what else has it touched?);
  - EDR on prt-01 (what has executed since 03:22?);
  - domain authentication logs filtered on svc-printmgmt and on wkst-hr-22 as source (has it spread?);
  - proxy history for both hosts (what is files-cdn-sync.example to this network?);
  - the change-management system (does anything authorize weekend work on prt-01?).
- Note the transfer's direction: bytes_out means prt-01 *sent* 2.1 MB. Net.WebClient uploads as easily as it downloads, so the decode question is "downloader or uploader?", and an uploader answer moves exfiltration onto the criteria list.
- The timeline's two required answers: how did whoever was on wkst-hr-22 come to hold service-account credentials, and what has executed on prt-01 since the 03:22 logon.
- Ledger. Leading hypothesis: hands-on-keyboard use of the account from a compromised workstation, with the scheduled task as persistence. Strongest surviving alternative: an administrator doing undocumented weekend maintenance from a borrowed desk.
- Nothing in the packet kills that alternative: no artifact shows the ticket search coming back empty or the owning team denying the session. So the ledger holds it open, names the two checks that would settle it, and records "cannot determine yet" beside it.

*Common failure:* burying the alternative under an assumed empty ticket queue. That answer fails this phase.

**Risk.**

- Impact: High. An actor with working service-account credentials and interactive access on a server is positioned to reach anything that account and host can touch. Print servers are reachable from most of the fleet, run the Print Spooler as SYSTEM (the PrintNightmare class of bugs shows what that exposes), and often host vendor management agents with stored credentials.
- Likelihood: Medium. The chain is multi-source and artifact-backed: a first-in-baseline RemoteInteractive logon, a task named to mimic an OS component, hidden-window encoded PowerShell, and 2.1 MB outbound to a domain absent from a 90-day baseline. But one benign explanation would account for the logon, and it is untested. Judging malice highly likely means judging that explanation unlikely, and the packet gives you no way to test it yet.
- Confidence in that judgment: medium, on the <a href="/docs/documentation/standards/#confidence">shared rubric</a> (independent artifacts, one live alternative unexamined). Unexamined is not Low: the open alternative holds the estimate at Medium, and nothing here pushes it down.
- Upgrade triggers, named: the decoded command resolving to a downloader or uploader, an empty change-ticket search, or the owning team denying the session.
- Matrix: High/Medium, P2. Risk's recommended move: escalate within 4 hours, the P2 decision clock.
- In production you would not score around a one-query gap on a live case. The full TaskContent sits in the same 4698 event, so pull it before writing the score. The packet stops here to test whether you can tell evidence you hold from evidence you assume. P2 is the floor, and every named trigger is minutes away.

*Common failure:* scoring likelihood High. That requires facts the packet does not contain, and writing "no surviving benign explanation" over a live alternative is the exact move the ledger exists to prevent.

**Escalation decision.**

- Confirmed by a supplied artifact: none, and writing that sentence is the graded move. "Confirmed" means supported at High confidence on the shared rubric, and nothing here is there yet.
- The type 10 logon confirms an interactive hop as a service account (an artifact-backed anomaly), but lateral movement as an escalation criterion means attacker-driven expansion, which requires the administrator alternative dead first. The 2.1 MB transfer is a Scope question until the decode or the destination says what it was.
- Confirmed malicious activity not fully contained by a control requires the decoded command or destination intelligence on files-cdn-sync.example, and the packet contains neither.
- The decision: escalate on the matrix. No criterion is confirmed, but the cell is P2, and P1 or P2 escalates. The escalation basis in the packet is the cell (High/Medium: P2), on the 4-hour clock.
- The <a href="/docs/escalation/criteria/#tripwire">escalation tripwire</a> is primed rather than fired. The moment any named trigger returns hostile (the decode is a downloader or uploader, the ticket search is empty and the owning team denies the session, intelligence condemns the domain), confirmation exists. The case becomes P1 and pages IR (incident response) from wherever in the arc that result lands.
- On the page: preserve before you contain (the 4698 event data, the proxy record, prt-01's volatile state), then take only the reversible actions the protocol pre-authorizes. The rest of the arc continues under IR's clock, with triage working only on the scoping tasks the IR owner assigns.

*Common failure:* ticking lateral movement and exfiltration because a second entity appeared and bytes left the network.

**Documentation.**

- Summary model, observations first, assessment second, confidence labeled per claim: "First interactive (RemoteInteractive) logon on record for service account svc-printmgmt, from workstation wkst-hr-22 to print server prt-01 at 03:24 UTC Sunday, preceded by a network logon at 03:22, against a 90-day baseline of service logons only. The account created a scheduled task masquerading as an OS component at 03:41 via hidden-window encoded PowerShell; at 03:44, prt-01 sent 2.1 MB to files-cdn-sync.example, a destination absent from its 90-day baseline. Assessed with medium confidence as hands-on-keyboard use of the account from wkst-hr-22, with the task as persistence; low confidence on what the task runs until the full command is decoded from the 4698 event data. The undocumented-maintenance alternative remains open pending the change-ticket search and account-owner contact. Escalated on the matrix at P2 (High/Medium) within the 4-hour clock; the decoded command, the ticket search, and destination intelligence are the recorded escalation-tripwire triggers."
- Detection feedback, two items. Detection: alert on any logon by an account in the service-account inventory (a directory attribute or group, not the svc-* name) that is interactive or RemoteInteractive, or that comes from a source host outside its baseline. That rule would have fired at 03:22, nineteen minutes before this one. Prevention: grant service accounts "Deny log on through Remote Desktop Services" and "Deny log on locally".

*Common failure:* a summary with no confidence labels, or one that states the downloader as fact.

**Stretch: the handoff.** Section 1 is the summary above, shortened to what IR needs first. Section 5 carries impact High, likelihood Medium with medium confidence, the cell (High/Medium: P2), and the recommended response. Section 6 names what was done (the 4698 event data and the proxy record exported and hashed) and what was deliberately not done: svc-printmgmt was not disabled before IR decides, because that would break printing, tip off the operator, and destroy the chance to watch the next move; prt-01 was not isolated, because no criterion is confirmed and isolation is IR's call on the P2 clock. Section 8 lists the three open checks (decode, ticket search, destination intelligence), each with the query that settles it.

**Traps planted in this packet.** Anchoring: the alert names a Medium-severity task-creation event, and the task's OS-flavored name invites a "Windows doing Windows things" dismissal. The case pivots on an artifact the alert never mentions. Availability: if your last service-account case was a misconfigured backup job, candidate (b) feels more likely than the evidence supports. The logon type is the discriminator that beats both. The third trap is the invented fact: the artifacts stop exactly where the satisfying conclusions start. Grading rewards the answer that marks the decoded command, the ticket search, and the transfer's nature as "cannot determine yet," each with the query that settles it, and penalizes the answer that asserts them. An analyst who manufactures the missing facts has failed the packet even while guessing the author's intended incident.

**Scoring grid (10 points, one each).**

1. The decode is noted as a hypothesis, with the full command named as the first evidence request.
2. The type 10 logon is named as the heaviest artifact, with the baseline as the reason.
3. Candidate (b) is eliminated with logon-type evidence.
4. Candidates (a) and (c) are left open, with the two checks that separate them.
5. wkst-hr-22's assigned user is scoped as an entity in its own right.
6. A lookback of 7 days or more on wkst-hr-22.
7. Likelihood Medium, with a confidence label and the named upgrade triggers.
8. P2 from the matrix, escalated on the 4-hour clock with the cell as the basis.
9. "No criterion confirmed" stated, with the reason lateral movement is not yet confirmed.
10. A detection item that fires earlier than the 4698 rule.

Disqualifier: the write-up asserts the decoded command, the ticket-search result, or the nature of the transfer as fact.

## Exercise 2 · The consent grant in the migration window

<p class="ex-meta"><span class="ex-tag">Full arc</span> <span class="ex-tag">Less guidance</span> <span class="ex-tag">45-60 minutes</span></p>

**Briefing.** Tuesday, 10:05 UTC. The queue hands you an identity alert. Per the migration runbook, IT revokes the vendor app's grant at the end of each wave, so every wave starts with a fresh consent.

<pre><code>{`IdP alert, 10:05:33 UTC
  rule:      OAuth consent granted to unverified publisher (rule-oauth-unv)
  severity:  High
  account:   adm-jkoh (IT administration)
  app:       "SharePoint Migration Manager"   publisher: unverified
  scopes:    Sites.FullControl.All, offline_access
  consent:   10:02:14 UTC, interactive, MFA satisfied, corporate device`}</code></pre>

<pre><code>{`Tenant audit excerpt, 10:00-10:40 UTC
  10:12-10:38  bulk file reads by app "SharePoint Migration Manager"
               ~14,000 items across 6 site collections
               source IP range: 198.51.100.32/28`}</code></pre>

<pre><code>{`Change-management system, search result
  CHG-4182  "SharePoint tenant migration, wave 3 of 5"
            window: Tuesday 09:00-17:00 UTC
            executed by: adm-jkoh
            vendor: CloudShift Migrations Ltd
            vendor doc: migration traffic sources 198.51.100.32/28`}</code></pre>

**Tasks.** Same seven phases, fewer hints. This packet's questions are shorter on purpose; the discipline being trained is verification.

<ol class="ex-tasks">
  <li><strong>Alert.</strong> Did the rule do its job? What verdict type is still open, and which <a href="/docs/glossaries/clear/">C.L.E.A.R. glossary</a> term names it?</li>
  <li><strong>Subject → Uncover.</strong> The change ticket looks like it explains everything. List every claim in the ticket you can independently verify against the two log artifacts, and verify each one. Then list the checks the artifacts <em>cannot</em> satisfy, and where you would go for each.</li>
  <li><strong>Risk.</strong> Write the Risk assessment paragraph: impact, likelihood with its confidence, the matrix cell and priority, and the recommended move. Include what stops this from being a close-on-sight.</li>
  <li><strong>Escalation decision → Documentation.</strong> There are two more migration waves scheduled. What artifact should this close produce so waves 4 and 5 start from a written verification checklist instead of from scratch, and which two fields in it must be re-verified every wave rather than assumed? (Check first: what is the lowest rung of the depth ladder this subject can ever be worked at, and why?)</li>
</ol>

<Reveal summary="Answer key: Exercise 2" variant="example">

**Alert.**

- The detection is a true positive: an unverified-publisher app did receive tenant-level consent.
- The open question is the activity axis, and the verdict this is heading toward is a benign true positive: detection true positive, activity authorized. The logic matched exactly what it describes, and the local context (a sanctioned migration) would clear it.
- That is not a false positive, and recording the difference matters: a false-positive verdict sends tuning feedback against a rule that is working. (In Microsoft Sentinel's classification this is a Benign Positive; in Defender XDR, "Informational, expected activity".)
- Depth: Level 2 from intake. Only an administrator can grant tenant-wide consent to Sites.FullControl.All, and the alert labels adm-jkoh as IT administration. A privileged identity fails the Level 0 eligibility gate and meets a Level 2 entry criterion, however routine the change looks.

*Common failure:* calling it a false positive because the activity turns out to be sanctioned.

**Subject → Uncover.**

- Verifiable claims, verified against the artifacts:
  - the ticket's executor matches the consenting account (adm-jkoh on both);
  - the consent timestamp sits inside the ticket's window (10:02 inside 09:00-17:00);
  - the app's activity source range matches the vendor's documented range (198.51.100.32/28 on both);
  - the consent ceremony is consistent with a human administrator (interactive, MFA, corporate device), not a hijacked session.
- First check locally, before anyone outside the SOC: does the consented application's ID (from the consent audit event) match the app consented in waves 1 and 2? Then the reply URLs, the publisher tenant, and the service principal's creation date. "SharePoint Migration Manager" is also the name of Microsoft's own first-party migration tool, which a third-party app has no reason to borrow.
- Checks the artifacts cannot satisfy, and where each goes:
  - whether the app is actually CloudShift's registered application rather than a lookalike display name: the app ID from the vendor's onboarding doc, or a call to the vendor, because display names are attacker-choosable;
  - whether adm-jkoh actually performed the consent: one out-of-band message to adm-jkoh settles "was it you", and CHG-4182's approver (someone independent of the subject) settles "was it allowed";
  - whether the read volume matches the wave's expected site collections: the migration runbook.
- The name-versus-identity check is the load-bearing one. Timing an attack inside someone else's maintenance window, with a plausibly named app, is an established adversary pattern.

*Common failure:* counting the matching source range as proof the app is the vendor's app.

**Risk.**

- Model assessment: "Impact if hostile: High (full control of every site collection the consenting admin can reach, meaning read, write, delete, and change permissions, with standing access through offline_access refresh tokens). Likelihood pending two checks: the app-ID match against CloudShift's registered application, and an out-of-band confirmation from adm-jkoh. Until both return, likelihood is Medium (unexamined is never Low) with low confidence on the app's identity: the cell is High/Medium, P2, and the recommended move is escalation within 4 hours unless the checks return first. When both return clean: likelihood Low with high confidence, High/Low, P3 on the tightened high-impact clock, re-scored when the end-of-wave revocation is verified, then a documented close as detection true positive, activity authorized (a benign true positive)."
- The close-on-sight stopper: until the app ID and the executor are verified, the ticket is a hypothesis, not an explanation. A change ticket in the search results is a fact about the change-management system, not about the consent event.

*Common failure:* writing that the app identity was confirmed. Nothing in the packet shows that check; asserting it is the invented fact Exercise 1 penalizes.

**Escalation decision → Documentation.**

- The decision for wave 3: the checks are minutes of work against a 4-hour P2 clock. If both return clean, the case re-scores to P3 and closes as documented above. If either fails, or neither has returned when the clock runs out, it escalates on the P2 cell (and on the escalation tripwire, if the app turns out to be a lookalike).
- The artifact: a documented expected-change record linked to CHG-4182, listing the verification checks this wave needed, so waves 4 and 5 start from a written checklist instead of from scratch.
- Waves 4 and 5 cannot close at Level 0, and they cannot run at Level 1 either. adm-jkoh is a privileged identity, which fails the Level 0 eligibility gate and meets a Level 2 entry criterion however clean the pattern looks. What the record buys is speed inside the full arc: Subject and Scope arrive pre-answered, and the analyst's time goes to the fields that must be re-verified.
- The two fields re-verified every wave: the consenting principal against that wave's ticket executor, and the application ID against the vendor's registered app.
- The fields that may be inherited: the vendor's source range (re-checked against the vendor doc quarterly). Each wave's window is checked against that wave's own ticket.
- An entry whose discriminators are "there was a ticket" will eventually close the real thing.

*Common failure:* writing a Level 0 pattern entry for waves 4 and 5.

**Traps planted in this packet.** Deference and premature closure: the change ticket radiates authority, and everything after it reads as confirmation. The packet is passed only by treating the ticket as one more claim to verify. Circular corroboration, a deference variant: the vendor's own doc supplied the IP range, so the match proves the traffic came from the vendor's infrastructure, not that the app is the vendor's app. The pattern reflex: three clean waves invite a fast-path entry, and a privileged identity never earns one.

**Scoring grid (10 points, one each).**

1. Detection true positive, activity still open, heading toward a benign true positive (not a false positive).
2. Level 2 from intake, because adm-jkoh is a privileged identity.
3. Executor, window, and source range each verified against an artifact.
4. The circularity named: the source range proves vendor infrastructure, not the vendor's app.
5. The app ID (not the display name) named as the load-bearing open check, with where to get it.
6. Out-of-band confirmation from adm-jkoh, and authorization from someone independent of the subject.
7. Impact High, scored on full control, not on read access.
8. Likelihood Medium pending the checks (never Low on unexamined evidence), with the P2 cell and the clean path to P3.
9. The waves 4 and 5 artifact is an expected-change checklist, not a Level 0 pattern entry.
10. The two re-verified fields named: principal against executor, and app ID against the vendor's registered app.

Disqualifier: the write-up asserts the app ID was verified, or routes waves 4 and 5 to Level 0 or Level 1.

</Reveal>

## Exercise 3 · The Level 0 drill

<p class="ex-meta"><span class="ex-tag">Fast path</span> <span class="ex-tag">Timed: 5 minutes</span></p>

**Briefing.** Drill date: 2026-10-06. Set a five-minute timer. This is a queue-speed drill for the <a href="/docs/fast-path/">fast path</a>: one recurring alert, one pattern-library entry, one decision.

<pre><code>{`EDR alert, 02:47:10 UTC
  rule:      Possible cryptomining: sustained CPU >90% for 30m
             + persistent outbound TLS to non-allowlisted host

- Preserve, under legal hold with a chain-of-custody record, without tipping the subject: the DLP records, the source-control audit log, the proxy records for the upload, and the endpoint timeline for lt-eng-311.
- Deliberately not done by triage: disabling the account, contacting pnair, blocking the storage service for her, or touching the laptop. Each one tips the subject or changes the evidence. In an insider case, even the reversible pre-authorized actions wait for the insider-risk lead and legal: the escalation is immediate, the containment is coordinated.
- Feedback: alert on bulk clones of repositories outside an account's baseline. That rule would have fired at 20:58, six minutes before the first upload.

**Traps planted in this packet.** The personal detail: the email hands you exactly the information the SOC must not record. Authority: the manager asks for a pull, and a manager's request feels like a mandate. Judging intent: "she resigned and she's stressed" invites a motive story that no artifact supports. The tip-off: disabling the account is the fastest way to lose the next move and warn the subject.

**Scoring grid (8 points, one each).**

1. Detection true positive; activity policy violation; the risk-versus-threat label left open.
2. The record's sentence uses account, host, UTC times and volumes, with no motive or adjectives.
3. Nothing about the divorce or stress in the record; the resignation reaches the case only through the insider-risk route.
4. No activity pull to the manager, a request not to discuss the case, and the email routed to the insider-risk process.
5. Impact High; likelihood High with high confidence on three sources; High/High: P1.
6. Exfiltration confirmed with the exception register as the benign alternative ruled out; escalated through the insider route with restricted visibility.
7. Preservation under legal hold without tipping the subject; account disable and subject contact deliberately left to the program, with the reason.
8. A detection item that fires before the upload.

Disqualifier: the record contains the subject's personal circumstances, or the SOC sends the activity pull to the manager.

</Reveal>

## Exercise 7 · The report button

<p class="ex-meta"><span class="ex-tag">User-reported phish</span> <span class="ex-tag">Grouped case</span> <span class="ex-tag">30-45 minutes</span></p>

**Briefing.** Monday 2026-08-17, 09:48 UTC. Three users reported the same email through the report button, and the reported-phish queue grouped the reports into one case.

<pre><code>{`Reported-phish case, 09:46 UTC (3 reports grouped)
  subject:   "Action required: your mailbox storage is full"
  sender:    it-support@mail-quota-notice[.]example
             SPF pass, DKIM pass (d=mail-quota-notice[.]example)
  link:      hxxps://portal-sso-check[.]example/owa/login (rewritten by the URL-protection service)
  reporters: jbell 09:39, lgomez 09:41, tchen 09:44`}</code></pre>

<pre><code>{`Message trace, 08:57-08:58 UTC
  delivered to 23 mailboxes, all in Customer Support; 0 quarantined`}</code></pre>

<pre><code>{`URL-protection click log, portal-sso-check[.]example
  09:12:41  aokafor  allowed  (verdict at click time: unknown)
  09:30:02  verdict updated: phishing (credential harvest)
  09:37:15  jbell    blocked  (verdict: phishing)`}</code></pre>

<pre><code>{`Proxy log (TLS inspection on), 09:00-09:48 UTC, requests to portal-sso-check[.]example
  09:12:43  laptop-cs-17 (aokafor)  GET   /owa/login   200
  09:13:20  laptop-cs-17 (aokafor)  POST  /owa/login   302 -> the real corporate webmail
  no requests from any other host`}</code></pre>

<pre><code>{`IdP sign-in log, aokafor, 08:30-09:48 UTC
  08:41:10  sign-in success  192.0.2.10 (corporate VPN egress)  MFA satisfied
  no other sign-ins`}</code></pre>

**Tasks.**

<ol class="ex-tasks">
  <li><strong>Alert.</strong> One case or three? The verdict on both axes for the reported message, and the depth level.</li>
  <li><strong>Scope.</strong> Who is in scope, and on what evidence? Work jbell and aokafor separately.</li>
  <li><strong>Escalation decision.</strong> Is a criterion confirmed for anyone? Which path does each clicker take, and what cell do you record?</li>
  <li><strong>Documentation.</strong> List the actions in order, and write the one line the record carries about aokafor's status.</li>
</ol>

<Reveal summary="Answer key: Exercise 7" variant="example">

**Alert.**

- One case. Three reports of one message to one set of recipients in one window are one unit of work, and the riskiest member sets the level.
- The reporters are the detector, and they were right: detection true positive. Activity: malicious, a credential-harvest kit (the URL-protection verdict at 09:30, and a login page imitating corporate webmail on a domain the organization does not own).
- SPF and DKIM pass prove that mail-quota-notice[.]example sent the message. They say nothing about whether that domain is legitimate.
- Depth: Level 1 at intake, ordinary users and a bounded blast radius. The proxy POST makes the depth question moot within minutes, because confirmation escalates from any level.

*Common failure:* reading the authentication passes as a reason to doubt the reporters.

**Scope.**

- In: all 23 recipients (delivery is the exposure surface), the two clickers and their hosts, the sending domain and the kit's domain. Out: other departments, until a tenant-wide trace for the sender, subject line and URL shows more deliveries.
- jbell: clicked at 09:37, blocked at click time, and the proxy shows no request from any other host. Contained by a control, once the block is verified (it is: the click log and the proxy agree).
- aokafor: clicked at 09:12, eighteen minutes before the verdict changed. Her laptop fetched the kit's login page and then POSTed to it, followed by the kit's tidy redirect to the real webmail. She reached the credential step and submitted it: credential-exposed until the password is reset, sessions are revoked and MFA methods are reviewed.
- The quiet sign-in log does not clear her. It says nobody has used the password yet. An adversary-in-the-middle kit would have produced a sign-in from the kit's infrastructure at 09:13, and there is none, which points to a plain harvest; the password is gone either way.
- Sweep: every other recipient's click and proxy records for the kit's domain (any POST is another aokafor), and the IdP for sign-ins to any recipient from first-seen addresses.

*Common failure:* generalizing jbell's block to everyone ("the URL service caught it").

**Escalation decision.**

- aokafor: criterion 1 is confirmed. A confirmed kit harvested a credential, and no control contained it: the verdict arrived after her click. Two independent sources carry it (the URL-protection verdict and her own laptop's proxy POST), and the benign alternative (a real storage portal) dies on the kit's page and its domain. That is High, so the escalation tripwire fires from Scope: P1, escalated through the tier the protocol names. Many protocols pre-authorize the response for exactly this scenario; where yours does, the escalation and those actions run together.
- The cell, recorded anyway: impact Medium (an ordinary support mailbox and its single sign-on apps), likelihood High: Medium/High, P2. The tripwire makes it P1 whatever the cell.
- jbell: no page and no credential action. Record the member as contained by a control, verified.
- The other 21 recipients: the message comes out of their mailboxes, and any later click gets the same check.

**Documentation.**

- Actions in order: preserve (the message with full headers, the click log, aokafor's proxy records, her IdP sign-in and audit records); escalate; revoke aokafor's sessions and refresh tokens (reversible); reset her password and review her MFA methods, with IR or owner approval unless the protocol lists them for phishing credential exposure; purge the message from all 23 mailboxes and block the kit's domain and the sender, as IR's calls unless pre-authorized; run the sweep.
- The line about aokafor: "aokafor: credential-exposed (password submitted to a confirmed phishing kit at 09:13:20 UTC, per the proxy record for laptop-cs-17); no use observed in IdP sign-ins through 09:48 UTC; exposed until password reset, session revocation and MFA review are complete."
- Feedback: alert on any POST from a corporate host to a domain first seen in the last few days. That rule would have fired at 09:13:20, seventeen minutes before the verdict. And thank the three reporters; the report button is a sensor worth keeping warm.

**Traps planted in this packet.** Anchoring on the authentication results. Absence read as innocence: no sign-in is not no exposure. The unit of work: three reports invite three tickets, and three tickets hide that one member is a P1. A control's success on one member read as its success on all.

**Scoring grid (8 points, one each).**

1. One grouped case, with the riskiest member setting its level.
2. SPF and DKIM passes read as sender authentication, not legitimacy.
3. jbell recorded as contained by a control, after the block was verified against the proxy.
4. aokafor recorded as credential-exposed on the POST evidence, not cleared by the quiet sign-in log.
5. Criterion 1 confirmed for aokafor on two independent sources; P1 by the escalation tripwire; the cell recorded (Medium/High: P2).
6. Preservation first, sessions revoked, the reset and MFA review per the protocol, and the purge and blocks as IR's calls unless pre-authorized.
7. A sweep of the other 21 recipients' click and proxy records.
8. One detection item that would have fired before the URL verdict.

Disqualifier: aokafor closed as clean because no sign-in followed, or the case closed on the URL service's block.

</Reveal>

## Exercise 8 · The certutil that downloaded nothing

<p class="ex-meta"><span class="ex-tag">Genuine false positive</span> <span class="ex-tag">Level 1</span> <span class="ex-tag">20-30 minutes</span></p>

**Briefing.** Friday 2026-09-11, 06:05 UTC. A High-severity endpoint alert on a monitoring server. Detection engineering changed this rule yesterday.

<pre><code>{`EDR alert, 06:00:14 UTC
  rule:     LOLBin download: certutil URL cache (rule-lolbin-certutil, v4)
  logic:    process name = certutil.exe AND command line matches (?i)certutil.*url
  severity: High
  host:     ops-mon-03 (monitoring server, standard criticality)
  user:     svc-certcheck
  command:  certutil.exe -verifystore Root "URL Filter Root CA"
  parent:   powershell.exe -File C:\\Ops\\cert-expiry-check.ps1  (scheduled task "CertExpiryCheck")`}</code></pre>

<pre><code>{`EDR detail, certutil.exe (PID 4412), 06:00:14-06:00:15 UTC
  network connections: none
  files written:       none
  exit code:           0
  history:             the same command line runs daily at 06:00 from this task (180 days on record)`}</code></pre>

<pre><code>{`Rule change record, rule-lolbin-certutil
  v3: command line contains "-urlcache" (case-insensitive)
  v4: regex (?i)certutil.*url, "to catch /urlcache and other variants"
      deployed 2026-09-10 15:20 UTC`}</code></pre>

**Tasks.**

<ol class="ex-tasks">
  <li><strong>Alert.</strong> What does the rule claim happened? Did it happen? Write the verdict on both axes, and say why it is not a benign true positive.</li>
  <li><strong>Subject → Risk.</strong> What level does this run at, what cell does it land in, and why is a pattern entry the wrong tool?</li>
  <li><strong>Documentation.</strong> Write the tuning request: what goes in it, and what is the risk of the change you propose?</li>
  <li><strong>Escalation decision.</strong> Close or escalate, and which reopen condition goes in the record?</li>
</ol>

<Reveal summary="Answer key: Exercise 8" variant="example">

**Alert.**

- The rule claims certutil fetched something from a URL: a living-off-the-land download (ATT&CK T1105, Ingress Tool Transfer).
- It did not happen. The command is -verifystore, a check against the local certificate store, and the EDR detail shows no network connection and no file written. The regex matched the letters "URL" in a certificate's display name.
- Verdict: detection false positive (logic), because the rule's logic matched something its own description says it is not hunting. Activity: benign-confirmed, a daily certificate-expiry check with 180 days of identical history.
- Not a benign true positive: that verdict needs the detection to be right about what happened, on activity that context clears. Here the thing the rule claims never occurred. Not a false positive (data) either: every field was parsed correctly, and the logic is what broke.

*Common failure:* "benign true positive, add a suppression for ops-mon-03."

**Subject → Risk.**

- Level 1: no pattern entry, one non-human identity with ordinary privilege, and the verdict question answerable from telemetry already in hand.
- One cheap check the packet does not show: the parent script's hash against the operations repository, because a scheduled task that runs a script is a persistence location. Record it as an open item until it is run; it does not change the detection verdict, which rests on what certutil did.
- Cell: impact Medium (a monitoring server, with the broad read access monitoring usually has), likelihood Low on examined evidence: Medium/Low, P4.
- A pattern entry, or a suppression keyed to this host or account, would leave the broken logic in place and blind the rule to a real certutil download from ops-mon-03 or svc-certcheck for as long as the entry lives. Pattern entries document benign behavior that a correct rule catches. They are not patches for a rule that is wrong.

**Documentation.**

- The tuning request carries: the rule ID and version (rule-lolbin-certutil v4); the change that caused it (v3 to v4, deployed 2026-09-10 15:20 UTC); the sample alert IDs; the precision since v4 (a sweep of every v4 alert since 15:20 yesterday, by host); the proposed change; its risk; an owner; and test cases.
- Proposed logic: key on the verbs that download, in either prefix form and any case, with a URL argument, instead of on the letters u-r-l anywhere in the line. <a href="https://lolbas-project.github.io/lolbas/Binaries/Certutil/" target="_blank" rel="noopener noreferrer">LOLBAS</a> documents certutil downloads through -urlcache and through -verifyctl with -f, so both belong in the rule.
- The risk of the change: any narrowing can miss a variant. The test cases are the mitigation: -urlcache -split -f with an https URL, /urlcache, -URLCache in mixed case, and -verifyctl -f with an https URL must all fire; the -verifystore line from this alert must not.
- This is a false-positive verdict, so the remedy is detection-side: the rule's logic changes. No exception, no pattern entry, no expiry to manage.

**Escalation decision.**

- Close, a documented P4 close within the queue SLA, and a first-class verdict.
- Reopen conditions: certutil on this host or under this account with a network connection or a file write; a command line carrying a download verb or a URL; or the parent script's hash changing outside a change ticket.
- The close is also a finding: every host that runs this check fires the rule daily until v5 ships. Each of those alerts is the same false positive (logic) only after the same check against its own EDR detail.

**Traps planted in this packet.** Anchoring: "High" plus "LOLBin" pulls toward escalation before the command is read. The convenient misfile: calling it a benign true positive leads straight to a suppression that outlives the bug. The pattern reflex: a daily alert invites an entry, and an entry is the wrong instrument for a broken rule.

**Scoring grid (8 points, one each).**

1. The rule's claim stated, and shown not to have happened, from the EDR network and file detail.
2. Detection false positive (logic), not data and not a benign true positive, with the reason.
3. Activity benign-confirmed for the certutil run, with the script hash named as an open check rather than assumed.
4. Level 1 and Medium/Low: P4, with no pattern entry and no host or account suppression.
5. The v3-to-v4 change identified as the cause.
6. A tuning request with rule ID and version, samples, proposed logic, risk, owner and test cases, including this alert's -verifystore line as a must-not-fire case.
7. The proposed logic still catches /urlcache, mixed case and -verifyctl downloads.
8. A reopen condition, and a sweep for the same false positive on other hosts.

Disqualifier: a suppression keyed to ops-mon-03 or svc-certcheck, or a benign-true-positive verdict.

</Reveal>

<Callout variant="info" title="Writing your own packets">
These packets follow a reusable shape: a briefing an analyst would actually receive, artifacts with the discriminating detail buried in a boring field, tasks phased to the letters, a key that names the planted traps, and a scoring grid. Closed cases from your own queue make better packets than anything synthetic, once sanitized per the <a href="/docs/documentation/example/">Documentation example's</a> sharing discipline. A workable recipe: replace addresses with the documentation ranges (RFC 5737: 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24; RFC 3849: 2001:db8::/32), replace domains with reserved names (RFC 2606: <code>.example</code>, <code>.test</code>, <code>.invalid</code>), pseudonymize every user, host, and ticket ID consistently, shift dates while keeping intervals intact, and strip the verdict. The <a href="/docs/teaching/">teaching guide</a> covers turning a real case into an exercise.
</Callout>

<KeyTakeaway>The methodology is learned in the writing: the close note that has to cite an artifact, the ledger that has to hold an alternative, the discriminator that has to be checked against the field instead of the memory. Eight packets is a start; a team that converts one real case a month into a packet builds a training library no course can sell them.</KeyTakeaway>
