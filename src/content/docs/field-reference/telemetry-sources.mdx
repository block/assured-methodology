<a id="security-logs"></a>
## SIEM alerts and correlated detections

The alert layer: the detections and correlation-rule outputs the <DefineTerm term="Security Information and Event Management (SIEM)" display="SIEM" /> raises from the sources below, plus the alerts that IDS/IPS and other security products forward to it. This is usually where the case starts, and it shows what else fired around the same entity and window. The raw firewall, proxy and IDS device logs behind those alerts are covered under <a href="#network">network traffic</a>.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Establishing the initial alert trail and identifying upstream/downstream events.</li>
      <li>Grouping related alerts on the same entity and window into one case.</li>
      <li>Reviewing the rule's fidelity history and triage metadata.</li>
      <li>Building a first-pass timeline across security products.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Alert volume includes significant noise and false positives; the rule's history tells you how much.</li>
      <li>An alert is a summary. The SIEM often keeps only the fields the rule needed, so go to the underlying source for the full event.</li>
      <li>Ingestion lag and silent sources create timing gaps: a source that stopped sending looks the same as a quiet one.</li>
    </ul>
  </div>
</div>

<a id="edr"></a>
## Endpoint detection and response logs

EDR platforms monitor <DefineTerm term="Endpoint" display="endpoint" /> activity in real time. Process creation, parent-child relationships, registry changes, file system activity, network connections, memory execution. This data lets analysts reconstruct attacker behavior at a granular level, from initial execution to <DefineTerm term="Lateral Movement" display="lateral movement" /> and <DefineTerm term="Persistence" display="persistence" />.

<Reveal summary="Key EDR data points" variant="info">

- Process execution with full command-line arguments
- Parent-child <DefineTerm term="Process Relationships" display="process relationships" /> and process-tree visualization
- File creation, modification, and deletion events
- Registry modifications and persistence-mechanism creation
- Network connection attempts with destination information
- Memory manipulation and code-injection attempts
- User account activity and privilege-elevation events

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Identifying execution chains and suspicious child processes.</li>
      <li>Detecting unauthorized file modifications or malicious payloads.</li>
      <li>Investigating persistence mechanisms or privilege misuse.</li>
      <li>Reconstructing attack timelines at the endpoint level.</li>
      <li>Validating suspicious network connections seen in other logs.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Requires an agent: unmanaged and BYOD endpoints have little or no coverage.</li>
      <li>Legitimate binaries abused by attackers (<DefineTerm term="LOLBins" /> such as rundll32, mshta, certutil, regsvr32) are recorded but often not flagged: they blend into normal activity unless hunted for.</li>
      <li>Sensors can be disabled or blinded (EDR-killer tools, vulnerable-driver abuse; ATT&amp;CK T1685). Check sensor health for the whole window before treating silence as absence; the <a href="/docs/uncover/correlation/#when-to-stop">dry-thread checks</a> walk through it.</li>
      <li>Console retention is often days to weeks depending on license; export what the case needs early.</li>
    </ul>
  </div>
</div>

<a id="os-logs"></a>
## Operating-system audit logs and host artifacts

The operating system's own logging, and the traces it leaves on disk. This is the evidence when EDR is absent, blinded, or out of retention. On Windows: the Security event log and, where someone deployed it, <DefineTerm term="Sysmon" />. On Linux: auditd and journald. On macOS: the unified log and Endpoint Security events. Host artifacts (Prefetch, Amcache, ShimCache, SRUM on Windows) can show that a program was present, and often that it ran, after the event logs have rolled over.

<Reveal summary="Event IDs worth knowing" variant="info">

- Windows Security 4624 and 4625: successful and failed logon (the logon type separates interactive, network, and remote sessions)
- Windows Security 4688: process creation (the command line is recorded only if the audit policy enables it)
- Windows Security 1102: the Security log was cleared
- Windows System 7045: a service was installed
- PowerShell 4104: script block logging
- Sysmon 1 (process creation), 3 (network connection), 22 (DNS query)
- Linux auditd execve records; macOS Endpoint Security exec and authentication events

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Confirming execution on a host with no EDR, or outside the EDR's retention.</li>
      <li>Reading the logon type and source behind a host-level sign-in.</li>
      <li>Finding service installs and scheduled tasks created for persistence.</li>
      <li>Cross-checking EDR on a host whose sensor may have been tampered with.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Audit policy is thin by default: 4688 command-line capture is off, and Sysmon is not installed unless someone deployed it.</li>
      <li>Local logs roll over within days on a busy host unless they are forwarded.</li>
      <li>Attackers clear these logs (ATT&amp;CK T1685.005, Clear Windows Event Logs). A gap, or a 1102 event, is itself evidence.</li>
    </ul>
  </div>
</div>

<a id="network"></a>
## Network traffic and communication logs

Network telemetry covers how data moves across internal and external environments: <DefineTerm term="NetFlow" />, DNS, full packet capture (PCAP), proxy and web gateway logs, and the device logs of firewalls and IDS/IPS sensors. Analysts use it to trace lateral movement, identify C2 channels, detect <DefineTerm term="Beaconing" display="beaconing" />, and examine <DefineTerm term="Data Exfiltration" display="data exfiltration" />. Network logs matter most where endpoint telemetry is missing or untrustworthy: unmanaged, BYOD, IoT and OT devices, network and edge appliances that cannot run an agent, and hosts whose sensor has been disabled or subverted. They also give the cross-host view. A DGA pattern or a beacon schedule is often clearest when resolver or proxy logs show it across the whole fleet.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Tracing the source or destination of suspicious traffic.</li>
      <li>Detecting exfiltration techniques (DNS tunneling, HTTPS uploads).</li>
      <li>Correlating DNS or proxy logs to identify attacker infrastructure.</li>
      <li>Mapping lateral movement patterns across the network.</li>
      <li>Identifying beaconing or periodic communication indicative of C2.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Full PCAP is storage-intensive; retention is often short.</li>
      <li>TLS encryption obscures payload content without decryption. Encrypted DNS (DoH/DoT) and Encrypted Client Hello also hide the domain names DNS and proxy logs rely on, so expect less SNI and resolver visibility over time. TLS fingerprints (JA4) and flow metadata remain.</li>
      <li>Cloud and remote-work traffic that never crosses a corporate sensor is invisible here.</li>
      <li>High-volume environments sample flows, so a short connection may be missing.</li>
    </ul>
  </div>
</div>

<a id="edge"></a>
## Remote access and edge appliances

VPN concentrators, ZTNA and SSE services, and the system logs of the firewalls and gateways themselves. Exploitation of internet-facing systems, very often edge devices, leads current breach reporting as an initial-access vector (vulnerability exploitation is 31% in Verizon's 2026 DBIR and exploits are 32% in M-Trends 2026), and these appliances rarely run EDR. Their logs are frequently the only record of who connected from outside, from where, and what the appliance itself did.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Tying a remote session to a user, a source IP, and the internal address the appliance assigned.</li>
      <li>Checking remote sign-ins for unfamiliar locations, devices, or posture failures.</li>
      <li>Looking for appliance compromise: configuration changes, new admin accounts, crashes or unexpected processes, outbound connections from the appliance itself.</li>
      <li>Establishing when a known-exploited vulnerability on the device was first hit.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Appliance logs often live in small rolling buffers on the device and are not forwarded by default.</li>
      <li>A compromised appliance can edit or suppress its own logs; the vendor's integrity-check tool and external flow data are the cross-check.</li>
      <li>Fields vary by vendor and firmware, and the assigned internal IP (the join key to everything else) is the field most often missing.</li>
    </ul>
  </div>
</div>

<a id="waf"></a>
## WAF, CDN and web-server access logs

Request-level records for public-facing applications: the web application firewall's verdicts, the CDN's edge logs, and the web server's own access log. Exploitation of a public-facing application (ATT&amp;CK T1190) leaves its probing here first: scanning paths, injection payloads, unusual methods, and the one request that returned a 200 where the rest returned errors.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Finding probing and exploitation attempts against a public application.</li>
      <li>Identifying the first request that succeeded, and the source behind it.</li>
      <li>Tying a web shell or new file on the server back to the request that planted it.</li>
      <li>Scoping which sources and user agents hit the vulnerable path.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Many WAFs log only blocked requests by default, so the allowed request that succeeded may be missing.</li>
      <li>Request bodies are rarely logged: a POST-based payload shows only its path and size.</li>
      <li>Behind a CDN or load balancer, the client IP is in a forwarded header, not the connection source.</li>
    </ul>
  </div>
</div>

<a id="iam"></a>
## User identity and access management logs

Logs from identity providers (Active Directory, <DefineTerm term="Okta" />, <DefineTerm term="Microsoft Entra ID (formerly Azure AD)" display="Microsoft Entra ID" />), SSO platforms, MFA systems, and directory services. They record login attempts, access denials, role escalations, password resets and token activity. This source is critical for account compromise, <DefineTerm term="Password Spraying" display="password spraying" />, session hijacking, and unauthorized access. The <a href="/docs/alert/parsing/cloud-identity/">cloud and identity parsing page</a> covers reading a sign-in record.

<div class="iam-grid">
  <div class="iam-card">
    <h3>User authentication</h3>
    <p>Login attempts, successes, failures, lockouts across identity systems. Reveals brute force or credential stuffing.</p>
  </div>
  <div class="iam-card">
    <h3>Privilege management</h3>
    <p>Role assignments, permission changes, elevation requests. The path of any privilege-escalation attempt.</p>
  </div>
  <div class="iam-card">
    <h3>MFA activities</h3>
    <p>Enrollment, verification, bypass attempts. The trail of sophisticated account-takeover tactics.</p>
  </div>
  <div class="iam-card">
    <h3>Session management</h3>
    <p>Token issuance, validation, expiration. Helps detect token theft and session manipulation.</p>
  </div>
</div>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Validating whether access to sensitive systems was legitimate.</li>
      <li>Detecting anomalies (logins at odd hours or unfamiliar locations).</li>
      <li>Investigating failed authentication, lockouts, or MFA bypass.</li>
      <li>Tracking privilege escalation across user accounts.</li>
      <li>Correlating identity events with endpoint and network activity.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Non-interactive and service-principal sign-ins live in separate logs (Entra) and are often not forwarded; check both before concluding a token was not used.</li>
      <li>The log shows authentication, not what the session did afterward. That lives in the SaaS and cloud audit logs.</li>
      <li>Federated and hybrid setups split one sign-in across several logs (on-premises AD, the federation service, the cloud IdP).</li>
      <li>Retention can be as short as 7 days; see the <a href="/docs/uncover/data-sources/#retention">retention table</a>.</li>
    </ul>
  </div>
</div>

<a id="cloud"></a>
## Cloud activity and configuration logs

Cloud-native logs: <DefineTerm term="AWS CloudTrail" />, Azure Activity Logs, GCP Audit Logs. API calls, configuration changes, login activity, resource provisioning. Foundational for detecting cloud misconfigurations, account abuse, <DefineTerm term="Privilege Escalation" display="privilege escalation" />, and exposure of cloud storage or compute.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Tracking IAM changes (user/role creation, key usage, permission escalation).</li>
      <li>Auditing bucket and compute resource policies.</li>
      <li>Investigating provisioning of new cloud resources.</li>
      <li>Detecting exfiltration through cloud storage or automation.</li>
      <li>Reconstructing actions across multiple cloud accounts.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Control-plane audit logs are on by default but limited: CloudTrail Event history keeps 90 days of management events per Region and account, Azure's Activity Log keeps 90 days, and GCP Admin Activity audit logs are always written and kept for 400 days. Data-plane logs (S3 and other CloudTrail data events, GCP Data Access logs other than BigQuery, Azure resource logs) stay off until someone enables them, and longer retention or cross-account search needs a trail, event data store, or export.</li>
      <li>Interpretation requires familiarity with each provider's services and API names.</li>
      <li>Rapid provisioning and teardown complicate timeline reconstruction: the resource may be gone before the alert is read.</li>
    </ul>
  </div>
</div>

<a id="saas"></a>
## SaaS audit logs

Every sanctioned SaaS tenant keeps its own audit trail: the Microsoft 365 unified audit log, Google Workspace audit logs, and the per-app equivalents in Salesforce, Slack, GitHub, and the rest. This is where tenant-level attacker behavior lives: inbox rules created, files shared or mass-downloaded, OAuth applications granted consent, admin settings changed. For a business-email-compromise or token-theft case, this source is the investigation.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Reconstructing what a hijacked session actually did after the IdP alert: mailbox rules, delegations, sharing changes.</li>
      <li>Investigating OAuth consent abuse: which app was granted which scopes, by whom, when.</li>
      <li>Detecting exfiltration through sharing links, mass downloads, or third-party sync apps.</li>
      <li>Auditing admin and configuration changes inside the tenant.</li>
      <li>Scoping a compromise across every user who touched the same attacker artifact (rule name, app ID, sharing target).</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Audit depth is often license-gated; the events you need most may require the premium tier.</li>
      <li>Ingestion lag of minutes to hours between the action and its appearance in the log.</li>
      <li>Default retention is short unless deliberately extended or forwarded to the SIEM.</li>
      <li>Every app logs in its own schema; cross-app correlation is manual without normalization.</li>
      <li>Only sanctioned tenants are covered. Shadow SaaS produces no audit trail you can reach.</li>
    </ul>
  </div>
</div>

<Callout variant="info" title="The identity chain is the join">
SaaS audit events rarely share a host or PID with anything. They join to the rest of the case through the identity chain: the user, the session ID, and the source IP and user agent the IdP recorded at sign-in. The <a href="/docs/alert/parsing/cloud-identity/">cloud and identity parsing page</a> covers reading that chain.
</Callout>

<a id="k8s"></a>
## Kubernetes audit logs

The <DefineTerm term="Kubernetes" /> API server can record every request it handles: who ran <code>kubectl exec</code> into which pod, who read which secret, what changed in RBAC, which workloads were created and from which images. Paired with container runtime telemetry, this is the visibility layer for cluster-native attacks that never touch a traditional endpoint.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Investigating suspected service-account token theft: what did the token do, from which source address?</li>
      <li>Tracing interactive access into workloads: exec, attach, and port-forward events.</li>
      <li>Auditing secret reads and RBAC changes around a suspected escalation.</li>
      <li>Spotting unusual workload creation: cryptominers, privileged pods, unfamiliar images.</li>
      <li>Reconstructing what a compromised CI/CD credential deployed and when.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Audit logging is off or minimal by default in many distributions; the policy has to be configured before the incident.</li>
      <li>Volume at scale is enormous; unfiltered policies overwhelm storage and search.</li>
      <li>Pods are ephemeral: names and IPs recycle in minutes, so capture has to be fast and joins need the pod UID.</li>
      <li>The API server sees control-plane actions only; in-container process activity needs a runtime sensor.</li>
      <li>Managed offerings expose different subsets of the audit stream with different retention. EKS control-plane audit logging is off until someone enables it per cluster, and AKS needs a diagnostic setting; GKE writes Admin Activity audit logs by default.</li>
    </ul>
  </div>
</div>

<a id="cicd"></a>
## Developer platform and CI/CD telemetry

Source-control, pipeline and package-registry audit trails: GitHub or GitLab audit logs, workflow and runner logs, package publish events on registries such as npm and PyPI, and secret-scanning alerts. Supply-chain intrusions such as the 2025 Shai-Hulud npm worm run through this layer, and the code they plant later executes inside signed, trusted processes on developer endpoints and build servers.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Tracing who changed a workflow, added a deploy key or token, or approved a merge.</li>
      <li>Tying a malicious package version to the publish event and the credential that pushed it.</li>
      <li>Finding which builds and hosts pulled a compromised dependency.</li>
      <li>Checking secret-scanning hits for credentials an attacker could reuse.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Audit depth and retention are plan-gated; enterprise tiers keep more.</li>
      <li>Runner logs are often ephemeral and expire with the job.</li>
      <li>What runs on the developer's machine (IDE extensions, MCP servers, package-manager scripts) shows up only in endpoint telemetry, and a trusted signer and install path do not clear code running inside a signed host.</li>
    </ul>
  </div>
</div>

<a id="ai-agents"></a>
## AI assistant and agent activity logs

Assistant interaction events (for example, Copilot interaction records in the Microsoft Purview audit log), cloud model-invocation logs, AI gateway and MCP gateway logs, and each agent's connector inventory with the scopes it holds. When an AI agent is a subject of the case, this is where its actions and its data diet are recorded; see <a href="/docs/subject/entity-types/">entity types</a> and <a href="/docs/ai-triage/#ai-agents-as-subjects">AI agents as subjects</a>. When the agent is your own triage automation, the same logs are the audit trail for the <a href="/docs/ai-triage/#governed-automation">governed automation tier</a>, and <a href="/docs/ai-governance/">governing automated triage</a> samples its tool-call log as evidence for the logging gate.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Reconstructing what an assistant retrieved, generated, or did through its tools for a given user and session.</li>
      <li>Checking whether a prompt-injection payload in a document or email preceded unexpected tool calls or outbound links.</li>
      <li>Inventorying which connectors and scopes an agent held at the time.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Logging is uneven and often license-gated; some tools record only that an interaction happened, not the prompt or the response.</li>
      <li>Tool calls made by local agents or MCP servers on an endpoint may appear only in EDR process and network telemetry.</li>
      <li>Prompt and response content can itself hold sensitive data, so access to it needs the same care as mailbox content.</li>
    </ul>
  </div>
</div>

<a id="ti"></a>
## Threat intelligence and IOC feeds

Structured data on known malicious indicators: domains, IPs, <DefineTerm term="Hash" display="hashes" />, URLs. Commercial, community, or internal. Matching internal activity against these indicators lets analysts assess credibility quickly and link activity to known malware families or threat actors. This entry covers the feed as evidence; the discipline of using intel (indicator matching, attribution, TTP hunting, validation) is the <a href="/docs/uncover/threat-intelligence/">threat-intelligence pillar</a>, and the platform that operationalizes feeds is <a href="/docs/field-reference/tool-families/#ti">the TIP</a> in the tool catalog.

Commercial providers offer curated, high-confidence indicators with context, at higher cost. Open-source feeds are broader but noisier. Industry ISACs deliver sector-specific intelligence. The best programs balance multiple sources and apply explicit validation. Treat threat intel as a hypothesis source, not a verdict.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Enriching indicators (hash, domain) with threat-actor attribution.</li>
      <li>Prioritizing activity involving known malicious infrastructure.</li>
      <li>Correlating internal observations with campaign data or bulletins.</li>
      <li>Expanding searches via related indicators in the same campaign.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Includes outdated or overused indicators (sandbox IPs, expired domains).</li>
      <li>False positives from benign reuse of known infrastructure: shared hosting, reassigned cloud IPs.</li>
      <li>Presence of an IOC does not confirm compromise; requires validation.</li>
    </ul>
  </div>
</div>

<a id="vuln"></a>
## Vulnerability and patch management logs

Logs from scanners (<DefineTerm term="Qualys" />, <DefineTerm term="Tenable" />, <DefineTerm term="Rapid7 InsightVM / Nexpose" display="Rapid7 InsightVM" />, now also packaged in Rapid7 Exposure Command) and patch management tooling: Microsoft Configuration Manager (ConfigMgr; formerly MECM and SCCM), Microsoft Intune, and WSUS (deprecated in September 2024 but still widely deployed, and still the engine under ConfigMgr's software update point). They show exposed vulnerabilities, patch application status and security baselines. Paired with threat intelligence and exploit telemetry, they help identify at-risk systems and likely exploit vectors.

<Reveal summary="Key vulnerability data points" variant="info">

- CVE identifiers and vulnerability descriptions
- CVSS base and environmental scores (note whether v3.1 or v4.0; see <a href="/docs/risk/framework/#cvss">CVSS adaptation for triage</a>)
- Exploitation evidence: CISA KEV listing, EPSS probability, public exploit or proof-of-concept availability
- Affected software versions and components
- Remediation status and patch application history
- Asset exposure duration (time since vulnerability discovery)
- Compensating controls and mitigation status

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Determining if exploited CVEs are present in the environment.</li>
      <li>Verifying which systems are unpatched or missing mitigations.</li>
      <li>Identifying likely attack vectors based on known vulnerabilities.</li>
      <li>Assessing exploitability of systems involved in incidents.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Scan coverage may be incomplete or out of date: assets added since the last scan are missing.</li>
      <li>Scanners report false positives, especially when they infer vulnerability from version banners and miss backported patches.</li>
      <li>Patch status is not proof of safety: a host patched today may already have been exploited before the patch.</li>
      <li>Freshly disclosed vulnerabilities appear only after the scanner's checks catch up.</li>
    </ul>
  </div>
</div>

<a id="fim"></a>
## File integrity monitoring (FIM)

FIM tools record changes to files, directories, registry keys and configurations against a baseline; deciding whether a change was authorized means correlating it with change records. They are used to detect tampering with critical system files, injection of malicious binaries, or modification of application code.

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Detecting unauthorized changes to system binaries or config files.</li>
      <li>Identifying tampering attempts post-intrusion.</li>
      <li>Confirming presence of malware implants or backdoors.</li>
      <li>Tracking modifications to sensitive application code.</li>
      <li>Validating whether critical security controls were disabled.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Noisy if baselines are not tuned, especially on hosts that change often.</li>
      <li>Does not distinguish legitimate from malicious changes; the change record does.</li>
      <li>Blind to memory-only or fileless attacks.</li>
    </ul>
  </div>
</div>

<a id="email"></a>
## Email security logs

Logs from Secure Email Gateways (SEGs), spam filters, and <DefineTerm term="Phishing" display="phishing" />-detection platforms. Sender domains, attachment hashes, headers, click-through behavior on malicious links. Email is still one of the top initial-access vectors; these logs are invaluable for tracing the origin of many incidents.

The variant these logs are weakest against is the one that carries no payload. <DefineTerm term="Business Email Compromise (BEC)" display="Business email compromise" /> and <DefineTerm term="Pretexting" display="pretexting" /> ask the recipient to act, not to click: a wire transfer to updated account details, a payroll change, gift cards for the "CEO". With no attachment to detonate and no URL to rewrite, the verdict fields stay quiet. Read these fields instead:

- **Authentication results on a lookalike domain:** it passes SPF and DKIM for itself, so "pass" proves nothing about the brand it imitates.
- **Display-name or reply-to mismatch:** a familiar name over an unfamiliar address, or replies routed somewhere else.
- **First-contact flag:** a sender seen for the first time who claims an established relationship.
- **A reply inside a legitimate thread:** the counterparty's mailbox is compromised and the attacker answers in the real conversation (thread hijacking).

When the case smells like BEC, pivot next to the <a href="#saas">SaaS audit logs</a> above for the inbox rules and sign-in anomalies that usually travel with it.

User reports are a second way into the same mail. A <a href="/docs/alert/intake/#user-reported-phishing">user-reported phishing</a> case starts from the message the user forwarded, and these logs answer who else received it and who clicked. Any user who reached the credential step of a phishing kit is credential-exposed until the password is reset, sessions are revoked and MFA methods are reviewed.

<Reveal summary="Key email security data points" variant="info">

- Sender information (email, domain, IP, <DefineTerm term="Geolocation" display="geolocation" />)
- Authentication results (SPF, DKIM, DMARC)
- Subject lines and content snippets
- Attachment details (filename, type, size, hash)
- Embedded URL information and reputation scores
- User interaction data (opens, clicks, forwards, replies)
- Detection verdicts and quarantine actions

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Tracing suspected phishing campaigns or credential harvesting.</li>
      <li>Investigating BEC and pretexting: authentication results, lookalike domains, reply-to divergence, thread hijacking.</li>
      <li>Reviewing user interaction with malicious links or attachments.</li>
      <li>Identifying every recipient of the same campaign.</li>
      <li>Correlating email-based attacks with other security events.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Limited visibility into content without sandboxing or deep inspection; encrypted attachments pass unread.</li>
      <li>Mail that never crosses the gateway is invisible: internal-to-internal messages, including lateral phishing from a compromised mailbox (ATT&amp;CK T1534, Internal Spearphishing), usually appear only in the tenant's own message trace or in API-based integrated cloud email security (ICES) tools.</li>
      <li>Sophisticated social engineering can lack obvious indicators.</li>
      <li>Personal email on corporate devices is often invisible.</li>
    </ul>
  </div>
</div>

<a id="appdb"></a>
## Application and database logs

Application and database logs offer visibility into use and abuse of business-critical systems. Transaction anomalies, privilege escalations, <DefineTerm term="SQL Injection" display="SQL injection" /> attempts, unauthorized queries. Particularly useful for investigating data breaches or access to sensitive records.

<div class="appdb-grid">
  <div class="appdb-card">
    <h3>Authentication events</h3>
    <p>Login attempts, session management, role and permission changes, account lockouts, password resets.</p>
  </div>
  <div class="appdb-card">
    <h3>Data access activities</h3>
    <p>Query execution, record CRUD operations, bulk exports, access to sensitive fields.</p>
  </div>
  <div class="appdb-card">
    <h3>System operations</h3>
    <p>Configuration changes, backups and restores, schema modifications, integration API calls.</p>
  </div>
</div>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Investigating activity within custom or sensitive applications.</li>
      <li>Detecting unauthorized queries or privilege escalation.</li>
      <li>Confirming access to regulated or sensitive data sets.</li>
      <li>Tracing the business impact of technical compromises.</li>
      <li>Establishing evidence for breach notification or compliance.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Logging is application-specific: check what the application actually records before relying on it.</li>
      <li>Often not forwarded to the SIEM, so the application owner may have to pull it.</li>
      <li>Verbose data-access logging is often off for performance, so reads of sensitive records may not be recorded at all.</li>
    </ul>
  </div>
</div>

<a id="cmdb"></a>
## Asset inventory, configuration and IP assignment

ServiceNow CMDB, <DefineTerm term="Lansweeper" />, AWS Config. Current and historical asset state: ownership, software versions, hardware specs, business functions. Analysts use these to assess <DefineTerm term="Asset Criticality" display="asset criticality" />, validate baselines, and map IPs/hostnames to physical or virtual systems. DHCP leases and IPAM records belong here too: they answer the question every network-based alert eventually asks, which host held this IP at that moment.

<Reveal summary="Key asset data elements" variant="info">

- System identifiers (hostname, IP, MAC, asset tag)
- DHCP lease history (which MAC and hostname held which IP, and when)
- Hardware specifications and physical location
- Installed software inventory and versions
- Operating system details and patch levels
- Ownership and responsible teams
- Business criticality and data classification
- Network segment and security zone information
- Relationships and dependencies with other systems

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Identifying asset owners for follow-up or scope assessment.</li>
      <li>Verifying whether a system is production, test, or abandoned.</li>
      <li>Determining system criticality and potential business impact.</li>
      <li>Resolving an IP to the host that held it at a specific time.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>CMDB entries go stale without regular maintenance, and untagged assets are missing entirely.</li>
      <li>DHCP lease logs are often kept briefly on the DHCP server and not forwarded; once the history is gone, the IP cannot be tied to a host.</li>
      <li>Limited visibility into cloud or shadow IT resources.</li>
    </ul>
  </div>
</div>

<a id="dlp"></a>
## Data loss prevention (DLP)

DLP platforms monitor and control <DefineTerm term="Sensitive Data" display="sensitive data" /> movement across endpoints, email, cloud, and network. They record when protected information (PII, intellectual property, source code, financial data) is accessed, transferred, or potentially exfiltrated.

<div class="dlp-grid">
  <div class="dlp-card">
    <h3>Email DLP</h3>
    <p>Outbound email and attachment monitoring. Detects sensitive content leaving via corporate or personal mail channels.</p>
  </div>
  <div class="dlp-card">
    <h3>Endpoint DLP</h3>
    <p>File operations, clipboard use, device transfers on workstations. Identifies unauthorized data handling at the user level.</p>
  </div>
  <div class="dlp-card">
    <h3>Network DLP</h3>
    <p>Inspects traffic for sensitive content. Catches unauthorized transfers over web upload, FTP, or other protocols.</p>
  </div>
  <div class="dlp-card">
    <h3>Cloud DLP</h3>
    <p>Monitors data movement to and between cloud services. Detects inappropriate sharing or storage of sensitive information.</p>
  </div>
</div>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Confirming whether sensitive data was accessed or exfiltrated.</li>
      <li>Reviewing policy violations related to data movement.</li>
      <li>Investigating unusual outbound transfers or clipboard use.</li>
      <li>Assessing the scope and impact of data breaches.</li>
      <li>Identifying unauthorized cloud-service usage.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>High false-positive rate from generic rule matching.</li>
      <li>Can be bypassed by encrypted or obfuscated channels.</li>
      <li>Limited visibility into unmanaged devices or networks.</li>
    </ul>
  </div>
</div>

<a id="deception"></a>
## Deception and honeypot logs

Deception platforms deploy decoys throughout the environment: fake credentials, deceptive files, memory lures, simulated services. Because these decoys have no business use, interaction with them strongly indicates malicious activity. The result is high-fidelity alerts with very few <DefineTerm term="False Positive" display="false positives" />. The benign hits that do occur come from vulnerability scanners, EDR and AV sweeps, and backup or inventory tools touching a decoy: benign true positives, which are excluded by source at deployment. This entry covers the logs those platforms emit; the platform capabilities, limitations, and vendor landscape live in <a href="/docs/field-reference/tool-families/#deception">the tool catalog</a>.

<div class="deception-grid">
  <div class="deception-card">
    <h3>Credential honeypots</h3>
    <p>Fake user accounts, tokens, or access keys. Triggered alerts on authentication use reveal credential harvesting or brute force.</p>
  </div>
  <div class="deception-card">
    <h3>System decoys</h3>
    <p>Simulated servers and workstations that appear legitimate. Detect lateral movement and reconnaissance with high confidence.</p>
  </div>
  <div class="deception-card">
    <h3>File lures</h3>
    <p>Deceptive documents with enticing names placed strategically. Identify data theft attempts and reveal attacker interests.</p>
  </div>
  <div class="deception-card">
    <h3>Application honeypots</h3>
    <p>Fake services that emulate production. Capture attacker techniques without risk to real assets.</p>
  </div>
</div>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Detecting lateral movement and credential harvesting.</li>
      <li>Triggering high-fidelity alerts on credential reuse or scanning.</li>
      <li>Assessing attacker intent through decoy interactions.</li>
      <li>Gathering intelligence on attacker TTPs.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Rarely deployed comprehensively, so a decoy that stayed quiet proves little.</li>
      <li>Attackers may avoid honeypots if they suspect their presence; decoys need upkeep to stay believable.</li>
      <li>Value against automation depends on targeting: indiscriminate automation (scanners, worms, ransomware sweeping SMB shares) trips decoys reliably, but automation aimed at known real assets (credential stuffing against a SaaS login, exploitation of one specific host) never touches them, and the intent and TTP intelligence from decoy interactions assumes a human operator.</li>
    </ul>
  </div>
</div>

<a id="backup"></a>
## Backup and snapshot metadata

<DefineTerm term="Veeam" />, <DefineTerm term="Druva" />, AWS Backup, EBS snapshots, Azure disk snapshots. Backup metadata is both a forensic resource and a recovery lifeline. Investigators use it to establish historical context, to detect sabotage (deleted or encrypted backups, a common <DefineTerm term="Ransomware" display="ransomware" /> tactic), and to check whether backup repositories were accessed.

<Reveal summary="Key backup metadata elements" variant="info">

- Backup job execution times and status
- Systems and data included in each backup
- Backup storage locations and retention periods
- Verification and validation results
- Access logs for backup management interfaces
- Restoration testing activity
- Modifications to backup policies or schedules

</Reveal>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Confirming whether clean backups exist pre-compromise.</li>
      <li>Detecting attempts to delete or encrypt backups.</li>
      <li>Identifying forensic artifacts in historical snapshots.</li>
      <li>Determining the earliest known clean state for affected systems.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Visibility is limited to the systems and storage the backup actually protects.</li>
      <li>Often managed by separate IT or operations teams; request access early in the case.</li>
      <li>Metadata for cloud-based or offsite backups is often incomplete.</li>
    </ul>
  </div>
</div>

<a id="physical"></a>
## Physical security and access control logs

Badge swipes, biometric authentication, visitor records, video surveillance, secure-zone access. These logs add a dimension digital telemetry cannot. By establishing the physical location of individuals at specific times, they help validate or refute hypotheses about who performed certain actions.

<Callout variant="info" title="Badge data and local sessions">
If an interactive console logon happens on a workstation inside a badge-controlled area while the owner's badge places them somewhere else, someone else probably used the credentials. That inference holds only for local, physical sessions: badge data says nothing about VPN or remote sessions, absence from the building is normal for hybrid staff, tailgating leaves no badge record, and an insider who shares credentials produces the same pattern. Treat the correlation as one input, and follow the <a href="/docs/subject/insider-analysis/">insider-analysis guardrails</a> (HR and legal involvement) before badge or video data enters a case.
</Callout>

<div class="src-detail">
  <div class="src-detail__col src-detail__col--use">
    <p class="src-detail__label"><span aria-hidden="true">✓ </span>When to use</p>
    <ul>
      <li>Correlating console logon times with building entry logs.</li>
      <li>Investigating physical theft or unauthorized access to secure areas.</li>
      <li>Corroborating or contradicting where an account's owner physically was when the account acted.</li>
    </ul>
  </div>
  <div class="src-detail__col src-detail__col--limit">
    <p class="src-detail__label"><span aria-hidden="true">✗ </span>Limitations</p>
    <ul>
      <li>Access is usually restricted: biometric and video records fall under privacy law (for example GDPR and Illinois BIPA) and employee agreements. Request them through the insider-analysis process with HR and legal rather than pulling them directly.</li>
      <li>Often not real-time or centralized, and policies vary by facility.</li>
      <li>Badge sharing and tailgating compromise accuracy.</li>
    </ul>
  </div>
</div>
