## The four entity types

Modern environments produce four broad categories of identities. Each one has its own normal patterns, its own ways of being abused, and its own analysis priorities. The first checks on each card are the minimum pass; the sections below develop each type.

<div class="entity-grid">
  <div class="entity-card entity-card--users">
    <span class="entity-card__tag">01</span>
    <h3>User accounts</h3>
    <p>Standard users, administrators, service accounts, external partners. Identity verification and access monitoring drive the analysis.</p>
    <ol class="entity-card__checks">
      <li>Who owns it, and is the owner still employed in the same role?</li>
      <li>How did it authenticate this time, compared with its usual pattern?</li>
      <li>What changed on it recently: groups, roles, MFA methods, password?</li>
    </ol>
  </div>
  <div class="entity-card entity-card--endpoints">
    <span class="entity-card__tag">02</span>
    <h3>Endpoints</h3>
    <p>Physical and virtual devices: workstations, servers, mobile, IoT, network infrastructure, cloud workloads. The host is the address where activity actually happens.</p>
    <ol class="entity-card__checks">
      <li>Who or what was running on it at the alert timestamp?</li>
      <li>Is it managed, compliant, and covered by EDR?</li>
      <li>What does it normally run and talk to?</li>
    </ol>
  </div>
  <div class="entity-card entity-card--apps">
    <span class="entity-card__tag">03</span>
    <h3>Applications and services</h3>
    <p>Business applications, dev tools, automation pipelines, cloud functions, OAuth apps, AI agents, and the cloud roles and managed identities they run as. Non-human identities with predictable but consequential behavior.</p>
    <ol class="entity-card__checks">
      <li>Which role or identity is attached, and who owns it?</li>
      <li>Was this launched or changed by the usual pipeline?</li>
      <li>Do its API calls match its own history and its peers'?</li>
    </ol>
  </div>
  <div class="entity-card entity-card--network">
    <span class="entity-card__tag">04</span>
    <h3>Network identifiers</h3>
    <p>IPs, domains, protocols, MAC addresses, certificates. Not identities in the strict sense, but the markers the system uses to route trust.</p>
    <ol class="entity-card__checks">
      <li>Which entity did it resolve to at the alert timestamp?</li>
      <li>Is it shared: NAT, proxy, SASE egress, CDN?</li>
      <li>What do its age, ownership, and reputation say?</li>
    </ol>
  </div>
</div>

Sessions and tokens are identity objects profiled alongside the four types. A browser session, a refresh token, or a Kerberos ticket can act without its account authenticating again, so when the alert turns on one, profile it next to the account that owns it.

## From identifier to identity

The alert rarely names a person. It names an IP, a hostname, or an account string, and the analyst resolves that identifier into an entity with a role and an owner before any of the analysis below applies. The pivot chain is mechanical:

1. **IP to host.** Asset inventory or CMDB for static assignments; DHCP lease logs, the VPN concentrator, or the wireless controller for dynamic ones. Match the lease that covers the alert timestamp, not the current one, because the address may have been reassigned since. If the IP is your own egress NAT, proxy, or SASE address, it maps to many users: pivot on the proxy or ZTNA logs for the session instead. For cloud private IPs, resolve through the network interface records or VPC flow logs at the alert timestamp, because workloads recycle addresses in minutes.
2. **Host to account.** Endpoint agent telemetry, workstation logon events, or VPN session logs show which account was interactive on the host during the window.
3. **Account to person and role.** The identity provider resolves the account string to a directory record; the HR system resolves the record to a name, team, manager, and employment status.

Every hop can be wrong: DHCP reassigns, workstations are shared, accounts are borrowed. Note the confidence of each hop, because "the IP resolved to jsmith" quietly stacks three separate inferences.

<Reveal summary="Example: one alert, two entity types" variant="example">
An EDR alert fires on build-07, a Linux build server: <code>curl</code> fetched a script from <code>pkg-mirror-cdn.example</code>, a domain registered three days earlier, and piped it to a shell.

**Endpoint lens first.** build-07 is a server, so its baseline is narrow: the same compilers and the same package mirrors, every night. That domain is not one of them. Who was running on it at the time? No person: the process tree descends from the CI runner's agent.

**That moves the question to Applications and services.** The runner executes jobs as svc-ci, so the first checks apply to the job, not only to the account. Which pipeline launched it? A job on a feature branch pushed forty minutes earlier. Who pushed that branch? A contractor account making its first push to this repository. Do the job's calls match its peers'? No other build job has ever contacted that domain.

The endpoint lens alone says "a server ran curl." The two lenses together say "an unfamiliar contributor changed what the pipeline runs," which is the lead Scope and Uncover pick up.
</Reveal>

## User accounts

<DefineTerm term="User" /> accounts are where much of the actionable evidence of compromise collects, because almost every intrusion eventually acts through one, even when initial access came through an exploited edge device. The analyst's job is to evaluate the activity against the account's expected pattern and lifecycle.

<div class="user-lifecycle">
  <div class="user-lifecycle__row">
    <h3>Creation and provisioning</h3>
    <p>Cross-reference account creation against HR onboarding and approved automation. Accounts that appear without a matching workflow are the classic backdoor pattern.</p>
  </div>
  <div class="user-lifecycle__row">
    <h3>Modification events</h3>
    <p>Privilege grants, group memberships, role changes. Each is a moment where an attacker could be establishing or expanding their access.</p>
  </div>
  <div class="user-lifecycle__row">
    <h3>Dormancy</h3>
    <p>Accounts inactive for 30+ days without being deprovisioned are a known soft target. They are credentials with no human watching them.</p>
  </div>
  <div class="user-lifecycle__row">
    <h3>Termination</h3>
    <p>Off-boarded users should lose access across every integrated system within hours of HR's record being updated. Orphaned credentials are how former employees become external attackers.</p>
  </div>
  <div class="user-lifecycle__row">
    <h3>Password resets</h3>
    <p>Resets the user did not initiate, and above all help-desk resets of a password or MFA method followed quickly by a new MFA registration and a sign-in from a new device or unexpected location (the Scattered Spider pattern, CISA AA23-320A). Verify any assisted reset against its ticket and <a href="/docs/escalation/communication/#out-of-band">a call-back to a number already on file</a>.</p>
  </div>
</div>

### Subtypes of user accounts

<div class="user-subtypes">
  <div class="user-subtype">
    <h4>Standard users</h4>
    <p>Predictable patterns tied to business hours and job function. Most volume, least permission.</p>
  </div>
  <div class="user-subtype">
    <h4>Service accounts</h4>
    <p>Non-interactive by design. Highly predictable behavior. Interactive logins from a service account are a near-canonical compromise signal. These accounts straddle two categories: analyze the credential and its logons here, as an account, and analyze what it does inside a pipeline or application under <a href="#applications-and-services">Applications and services</a>. A CI/CD service account gets both lenses.</p>
  </div>
  <div class="user-subtype">
    <h4>Administrative accounts</h4>
    <p>High impact if abused. Should be used through privileged access management, not for routine work. Watch for admin accounts doing user-tier activities.</p>
  </div>
  <div class="user-subtype">
    <h4>External accounts</h4>
    <p>Contractors, partners, vendor logins. Limited organizational visibility, broader attack surface. Compensating controls (time-bound access, narrow scope) are essential.</p>
  </div>
  <div class="user-subtype">
    <h4>Shared accounts</h4>
    <p>Single credentials used by multiple people. Attribution becomes impossible from the account alone. Record the attribution gap explicitly, then narrow it with session context (source host, VPN or ZTNA session, PAM checkout, badge logs). Shared accounts are both a documentation and a security problem.</p>
  </div>
  <div class="user-subtype">
    <h4>Break-glass (emergency access) accounts</h4>
    <p>Reserved for when the normal admin path is broken (IdP or federation outage, MFA service or devices unavailable, no PIM approvers). They skip PAM and just-in-time elevation by design but should still use phishing-resistant MFA (a FIDO2 key or certificate) distinct from everyday admin methods; Microsoft Entra now requires MFA for them. Every sign-in should alert. Any use outside a pre-announced validation drill (Microsoft recommends one at least every 90 days) escalates immediately and needs a post-use review. (This is the industry meaning of break-glass. ASSURED's rule for escalating from any phase is the escalation tripwire.)</p>
  </div>
</div>

## Endpoints

Each <DefineTerm term="Endpoint" display="endpoint" /> is a place where activity happens and a window into the broader environment.

<div class="endpoint-patterns">
  <div class="endpoint-card">
    <h3>Workstations</h3>
    <p>Standard user productivity machines. Compare current activity against the user's historical pattern on this specific device.</p>
  </div>
  <div class="endpoint-card">
    <h3>Servers</h3>
    <p>Mostly service-account driven, predictable workloads, narrow user-interactive activity. Interactive logins on production servers deserve a closer look.</p>
  </div>
  <div class="endpoint-card">
    <h3>Mobile devices</h3>
    <p>Personal and managed. Check enrollment and compliance in your device-management platform (<DefineTerm term="Unified Endpoint Management (UEM)" display="UEM" />, for example Intune or Jamf) and app-protection status (<DefineTerm term="Mobile Application Management (MAM)" display="MAM" />) for personally owned devices. Off-network activity may be invisible to corporate logging.</p>
  </div>
  <div class="endpoint-card">
    <h3>IoT and OT</h3>
    <p>Limited instrumentation. Often legacy. Trust boundaries depend on segmentation rather than endpoint detection.</p>
  </div>
  <div class="endpoint-card">
    <h3>Cloud workloads</h3>
    <p>VMs (EC2, Azure VMs, GCE), Kubernetes pods, serverless functions. Short lifetimes mean baselines are statistical, not per-instance. The workload's attached role or managed identity is analyzed under <a href="#applications-and-services">Applications and services</a>.</p>
  </div>
  <div class="endpoint-card">
    <h3>Network infrastructure</h3>
    <p>Routers, switches, firewalls, VPN concentrators. Edge devices are now a leading initial-access target: in the 2025 Verizon DBIR, edge and VPN devices made up 22% of vulnerability-exploitation actions, up from 3% the year before, and state actors such as Salt Typhoon persist on backbone and edge routers. They rarely run EDR, so watch for new local admin accounts, outbound connections the device starts itself, gaps in its logs, and config or firmware changes with no change ticket.</p>
  </div>
  <div class="endpoint-card">
    <h3>Virtual desktops</h3>
    <p>VDI sessions, often accessed via thin clients or BYOD. Attribution is harder because sessions are ephemeral. Watch clipboard transfers, drive mapping, and process execution outside normal user hours.</p>
  </div>
  <div class="endpoint-card">
    <h3>Developer workstations</h3>
    <p>Run compilers, IDEs, repository tools. Broad internal access by design. Behavior that would alarm on a standard endpoint (scripting, unsigned local builds, dynamic loaders) is part of the job. That access makes them prime targets: they hold tokens, cloud keys, and signing material, and malicious packages or IDE extensions run with the developer's rights. A trusted signer and install path do not clear code running inside a signed host: IDE extensions, MCP servers, and package-manager scripts all run under it, so inventory them. New package installs followed by credential-file access are worth a look. Apply tighter baselines on the developer's history rather than the environment-wide norm.</p>
  </div>
</div>

## Applications and services

Applications and services are <DefineTerm term="Non-Human Identity (NHI)" display="non-human identities" /> that act on behalf of (or alongside) human users. The cards below are the first pass. [Non-human identities](/docs/subject/non-human-identities/) goes deeper: cloud roles and assumed-role sessions, workload identity federation, CI/CD tokens and AI agents, how to answer "who is behind this" when no person is, and how to baseline automation.

<Callout variant="info" title="Why these often hide in plain sight">
Applications and services often have broad, persistent access and very predictable behavior. That predictability is what makes anomalies stand out. A CI/CD service account that suddenly accesses a database it has never touched before is a louder signal than the same access from a human, precisely because the service account's baseline is tight.
</Callout>

<div class="app-grid">
  <div class="app-card">
    <h3>Business applications</h3>
    <p>ERP, HR, finance, CRM. Sensitive data, predictable workflows, regulatory exposure.</p>
  </div>
  <div class="app-card">
    <h3>Development tools</h3>
    <p>Source control, CI/CD pipelines, package registries. Often have credentials that can deploy code into production.</p>
  </div>
  <div class="app-card">
    <h3>System utilities</h3>
    <p>Backup agents, monitoring tools, configuration management. Run continuously, touch many systems, easy to overlook.</p>
  </div>
  <div class="app-card">
    <h3>Cloud services</h3>
    <p>Managed cloud functions, container orchestration, service meshes. The identity boundary is often a cloud role, service principal, or managed identity rather than a credential: ask who can assume or use it, and trace the session back to the person or pipeline that started it. <a href="/docs/subject/non-human-identities/">Non-human identities</a> shows how to follow that trail.</p>
  </div>
  <div class="app-card">
    <h3>OAuth / third-party applications</h3>
    <p>Apps granted delegated access to user or organizational data through a consent screen. Each holds its own grant and its own refresh tokens, so password resets and MFA changes do not remove it. Inventory what has been consented and with which scopes; a newly registered app holding broad read scopes is the <a href="/docs/subject/four-dimensions/#cloud-identity-patterns-youll-see-today">consent-grant abuse</a> pattern. Cutting it off takes two kinds of action. Disabling the app's sign-in (its service principal) and revoking the affected users' refresh tokens are reversible and stop the tokens it already holds, though issued access tokens run until they expire. Deleting the delegated grants and any application-permission (app-role) assignments cannot be undone, so it waits for IR or owner approval unless the protocol pre-authorizes it; until then the grant survives every user-focused action. Block re-consent afterwards. Consent audit events can lag by up to 24 hours.</p>
  </div>
  <div class="app-card">
    <h3>AI agents and assistants</h3>
    <p>Copilots, RAG pipelines, and agentic automation hold delegated access to mail, documents, repos, and tickets, and act at machine speed. Agents increasingly get identities of their own (Microsoft Entra Agent ID, for example), so the agent itself can be the primary subject, not only the user it acts for. Baseline them like service accounts (tight scopes, predictable patterns) but treat their <em>inputs</em> as attack surface too: a prompt-injected assistant misusing its own legitimate token looks like an insider, not an intruder. The <a href="/docs/ai-triage/#ai-agents-as-subjects">AI-assisted triage page</a> covers both directions: the agent as analyst and the agent as subject.</p>
  </div>
  <div class="app-card">
    <h3>Credentials of non-human identities</h3>
    <p>API keys, client secrets, certificates, personal access tokens, and cloud access keys are credentials that belong to the identities above, not identities of their own. Track each by owner of record, issuance date, last-use date, scope, and age since rotation. Tokens that re-emerge after long silence, a secret flagged by leaked-secret scanning, or a new credential added to an existing app or role (T1098.001 Additional Cloud Credentials) often indicate compromise. Permissions a credential has never used are the ones to trim.</p>
  </div>
</div>

## Network identifiers

Network identifiers are how systems decide who is who when they cannot ask a person directly. Each identifier carries different forensic weight, and most of the analytical work is resolving them into the entities above (the pivot chain in [From identifier to identity](#from-identifier-to-identity)). Two habits carry most of the value: validate that traffic conforms to the protocol its port implies (SSH riding 443 is the classic bypass: a common port proves nothing, and a rare port is only a weak hint on its own), and treat every identifier as a pivot key into inventory, DHCP, and identity logs rather than as an answer by itself.

The identifier-by-identifier breakdown (ten types, with their forensic weight and classic abuse patterns) lives in the [reference below](#network-identifier-reference). Skim it once, then return to it during live cases. It is a lookup table, not a lesson to memorize.

## Network-identifier reference

A lookup table for triage: what each identifier is good for and the abuse pattern to check against it.

| Identifier | Good for | Abuse to check |
| --- | --- | --- |
| IP addresses | Source and destination locators for traffic. Internal IPs map to assets via the inventory; external IPs map to reputation via threat intelligence. | Geolocation, WHOIS ownership, and prior association with malware infrastructure. A clean residential IP proves nothing on its own. |
| Domain names | A naming layer attackers often use to mask infrastructure. | Typosquatting, fast-flux, and algorithmically generated (DGA) domains. Assess domain age, registrar patterns, resolution frequency, and passive DNS history. |
| Protocols and ports | Checking that traffic is what its port claims. | The stronger signal is protocol/port mismatch, not port rarity alone: SSH riding port 443 or DNS on an arbitrary high port is the classic bypass pattern, and 443 is the most common port on the internet. |
| MAC addresses | Tying DHCP leases to a device within a segment. | Modern phones and laptops present a randomized per-network MAC by default (Android 10+, iOS 14+), so the address may not match the hardware MAC in asset inventory and its OUI tells you nothing. Randomization alone is normal. The signals are the same MAC seen on two ports at once, a corporate-asset MAC on an unmanaged port, or a known asset's MAC whose posture or fingerprint does not match (NAC evasion or device impersonation). |
| BGP ASN | Grouping IPs by upstream provider. | Traffic from ASNs linked to bulletproof hosting, rapid ASN reassignment, or geolocation/ASN mismatches that suggest infrastructure churn. |
| FQDN patterns | Spotting generated or staging hostnames. | Algorithmically generated subdomains, excessive subdomain depth, wildcard DNS abuse, or staged-malware delivery domains. Subdomain entropy is a cheap first-pass filter, not a verdict: CDN and cloud hostnames (CloudFront's d111111abcdef8.cloudfront.net, for example) are random by design, so suppress known provider zones and weigh entropy together with label length, query volume to a single parent zone, and domain age (see DNS query behavior below). |
| SSL/TLS certificates | Linking servers that share issuance patterns. | Examine issuer, issuance date, SANs, and key. Self-signed or default-template certificates (known C2 framework defaults), SANs that do not match the contacted domain, and a certificate issued hours before first contact for a newly registered domain are the useful signals. Short validity on its own is now normal: public TLS certificates have been capped at 200 days since March 2026, and Let's Encrypt has offered 6-day certificates since January 2026. Pivot through Certificate Transparency logs (crt.sh) and JA4X/JARM server fingerprints. |
| DNS query behavior | Seeing covert channels that ride name resolution. | Queries to external resolvers, uncommon record types (TXT, NULL), unusually high query rates, or high entropy in queried names can signal data exfiltration or tunneling over DNS. |
| JA3 / JA4 fingerprints | Recognizing malicious clients or C2 infrastructure even when IPs and domains rotate. | Fingerprints that deviate from enterprise baselines. ClientHello extension randomization (Chrome since 2023) degraded JA3; JA4 is the successor, and modern feeds publish both. |
| URI / URL structures | Reading path depth, encoded parameters, and file extensions. | Unusual paths (for example /api/config.zip) or base64-encoded parameters that may indicate phishing kits, staged payloads, or HTTP-based tunneling. |

<KeyTakeaway>
Each <DefineTerm term="Entity" display="entity" /> type has its own pattern of normal and its own ways of being abused. Strong Subject analysis matches the analytical lens to the type. Treating a service account like a user (or a cloud role like a host) is how attackers go uninvestigated even when their activity is in the logs.
</KeyTakeaway>
