<ChapterExample
  title="Finding all the identities behind the alert"
  scenario="The Alert chapter handed Subject one named user (dlin, a finance analyst) and one host (laptop-finance-09) connected to a suspicious PowerShell event. Subject's job is to find every other identity that the alert touches and assess each one."
>

<ExampleStepper steps={["Start with the named user", "Expand to non-human identities", "Apply the four dimensions", "Check relationships", "Hand off to Scope"]}>

  <div data-step class="example-step">
    <h3>Step 1. Start with the named user</h3>
    <p>The alert names dlin. The Subject phase begins by profiling that user explicitly:</p>
    <ul class="example-step__list">
      <li><strong>Identity verification.</strong> The account is provisioned, matches an HR record, and is in the expected finance role.</li>
      <li><strong>Authentication history.</strong> Recent logins look normal until the day of the alert. Then a 09:08 login from the usual workstation, followed by the alert at 09:11.</li>
      <li><strong>Authorization.</strong> dlin has read access to finance reporting systems and the standard productivity stack. No administrative privileges.</li>
      <li><strong>Behavior.</strong> Activity profile is consistent with a finance analyst role. PowerShell is not part of dlin's normal pattern.</li>
    </ul>
    <p>Three of the four dimensions agree. The behavior dimension does not. PowerShell on this account is the first concrete signal that the alert is more than a misfire.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Expand to non-human identities</h3>
    <p>Subject does not stop at the named user. Every identity touched by the activity gets profiled.</p>
    <ul class="example-step__list">
      <li><strong>The host.</strong> laptop-finance-09 is a managed corporate device, enrolled in the EDR, with a baseline of activity matching dlin's role.</li>
      <li><strong>The machine account.</strong> laptop-finance-09 is domain-joined, so it has its own computer account that authenticates to domain services independently of dlin. Anything running as SYSTEM on the host speaks as that account, so its recent activity becomes part of the picture.</li>
      <li><strong>The Outlook session.</strong> The parent process of the PowerShell invocation. Each Outlook session has its own token, mailbox identity, and audit trail.</li>
      <li><strong>The cloud identity.</strong> dlin's federated SSO identity for the cloud-based finance reporting platform. Has the same recent-login pattern as the on-premises account.</li>
    </ul>
    <p>One named user has become five identities: the user account, the host, the machine account, the Outlook session, and the federated cloud identity. The Outlook session is assessed as part of dlin's own primary investigation, same principal, same token chain, which leaves four distinct entities to profile. Three get full primary depth (dlin, the laptop, dlin's federated cloud identity); the machine account gets secondary depth. Step 4 will add two more finance users to the map. Each one is a potential lateral-movement vector. Each one needs its own assessment.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Apply the four dimensions</h3>
    <p>The four dimensions are now applied to <em>every</em> identity in the list, not just dlin.</p>
    <ul class="example-step__list">
      <li><strong>Authentication.</strong> All four identities authenticated normally. No impossible travel, no MFA bypass, no token replay signals.</li>
      <li><strong>Authorization.</strong> No identity exceeded its assigned permissions during the relevant window. Authorization checks pass.</li>
      <li><strong>Behavior.</strong> dlin's user account behaved abnormally (PowerShell). The host's process baseline shows no prior PowerShell use under this user. The machine account and cloud identity show no unusual activity.</li>
      <li><strong>Relationships.</strong> The four identities are tightly connected: same user, same device, same SSO chain. No surprising new connections to entities outside that cluster.</li>
    </ul>
    <p class="example-step__what-not"><strong>What a less experienced analyst could miss:</strong> applying the dimensions only to the named user. The machine account and cloud identity are easy to overlook because the alert did not name them, but they share trust paths and could expose lateral movement if compromised.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Check relationships</h3>
    <p>The relationship dimension expands beyond the four identities into the systems and people they touch.</p>
    <ul class="example-step__list">
      <li><strong>Communication graph.</strong> dlin's mailbox in the relevant window shows a recent email with an unfamiliar attachment from an external sender. The sender is a candidate for the originating phishing source.</li>
      <li><strong>Other recipients.</strong> The same email pattern landed in three other finance team mailboxes. Two of them opened the attachment. Two more potential compromise candidates.</li>
      <li><strong>Downstream access.</strong> The cloud finance platform that dlin can access is connected to a vendor payment workflow. If the compromise extends to the cloud identity, payment systems are in scope for the next phase.</li>
    </ul>
    <p>The Subject picture now consolidates: 3 primary entities (dlin, the laptop, the cloud identity) + 3 secondary entities (the machine account, two other finance users who opened the email) + 1 downstream system (the cloud finance platform feeding the vendor payment workflow), plus the external originating sender tracked as the originating threat. That is the map Scope inherits.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Hand off to Scope</h3>
    <p>Subject ends with a structured, defended view of every identity connected to the alert. The handoff to Scope answers:</p>
    <ul class="example-step__list">
      <li><strong>Primary entities.</strong> dlin (user), laptop-finance-09 (host), dlin's cloud identity (SSO).</li>
      <li><strong>Secondary entities.</strong> The machine account of laptop-finance-09. Two other finance users who opened the same email.</li>
      <li><strong>Originating threat.</strong> The external sender behind the phishing email, tracked as a threat entity rather than an internal identity.</li>
      <li><strong>High-value paths.</strong> The cloud finance platform → vendor payment workflow. Lateral movement here would have regulatory and financial impact.</li>
      <li><strong>Insider risk indicators.</strong> None. The pattern looks like external phishing, not insider activity. No anti-forensic signs.</li>
    </ul>

    <Reveal summary="What the Subject deliverable looks like in practice" variant="example">
      <p>Subject's output is a short, structured document the next phase can act on without redoing the work:</p>
      <ul>
        <li>Map of every identity in scope (primary + secondary + downstream).</li>
        <li>Per-identity assessment across the four dimensions.</li>
        <li>List of relationships that expand the investigation beyond the alert.</li>
        <li>Recommended scope parameters: time window (24 hours before the alert), entities (the list above), depth of investigation (full for primary identities, baseline-comparison for secondary).</li>
      </ul>
      <p>Scope picks up here and turns this map into the formal boundary of the investigation.</p>
    </Reveal>
  </div>

</ExampleStepper>

</ChapterExample>

<KeyTakeaway>
The Subject phase turned one named <DefineTerm term="User" display="user" /> into a map of 3 primary entities + 3 secondary entities + 1 downstream system, plus the external originating sender tracked as the originating threat. That expansion is the whole point. Without Subject, the investigation would have stayed on one user and one host. With Subject, it knows to follow the trust paths.
</KeyTakeaway>

## A second scenario: the developer workstation

The first walkthrough showed Subject <em>expanding outward</em> from a single named user. Real triage often goes the other way: a noisy alert hits a high-skill identity whose normal behavior looks suspicious. Subject's job there is to <em>contain</em> the assessment, not expand it.

<ChapterExample
  title="Reading Subject when the named user is a developer"
  scenario="An EDR alert fires on a macOS laptop. A signed helper binary (Cursor Helper, part of the Cursor AI-assisted IDE) spawned a child process that disabled its sandbox and made encrypted outbound network calls. The pattern technically matches the Empire post-exploitation toolkit. The named user is a frontend engineer. The host is corporate-managed."
>

<ExampleStepper steps={["Classify the device", "Read the user identity", "Evaluate the application", "Check access scope", "Decide the operational risk"]}>

  <div data-step class="example-step">
    <h3>Step 1. Classify the device</h3>
    <p>Subject begins with what the asset is, not what the alert says. Subject does not have to redo Alert's parsing, but it does have to attach the activity to a device profile.</p>
    <ul class="example-step__list">
      <li><strong>Hardware and OS.</strong> Corporate macOS laptop, recent build, FileVault on.</li>
      <li><strong>Management posture.</strong> MDM-enrolled, JAMF profile verified, EDR (CrowdStrike) agent reporting normally, Gatekeeper enforced.</li>
      <li><strong>Classification.</strong> Developer workstation. This matters because the expected behavior is different from a standard productivity laptop.</li>
      <li><strong>Recent change history.</strong> No new admin agents, no recent OS reinstall, no profile drift in the last 90 days.</li>
    </ul>
    <p>The device classification reframes the alert. On a finance laptop, the activity is suspicious-by-default. On a developer workstation, scripting and child-process activity are part of the role. The investigation does not stop here; the bar shifts.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 2. Read the user identity</h3>
    <p>The four-dimensions analysis on the named user, focused on what the role allows.</p>
    <ul class="example-step__list">
      <li><strong>Authentication.</strong> SSO login at 09:14, expected location, expected device, FIDO2 second factor. No anomalies.</li>
      <li><strong>Authorization.</strong> Frontend engineer, developer group, no admin rights, no production access. Some elevated capabilities granted to specific applications via macOS TCC, all approved.</li>
      <li><strong>Behavior.</strong> Spawning helper processes from IDEs is part of this user's daily pattern. Encrypted outbound traffic from an IDE is normal (LSP backends, AI inference, package installs).</li>
      <li><strong>Relationships.</strong> Normal communication graph for the team. No new SSO links, no unexpected resource access this week.</li>
    </ul>
    <p>All four dimensions agree on legitimate. That is a real signal, not the absence of one. Subject records it explicitly so Scope inherits a defensible verdict, not a shrug.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 3. Evaluate the application</h3>
    <p>The detection fired on a process. Subject has to assess the process's identity as carefully as the user's.</p>
    <ul class="example-step__list">
      <li><strong>Binary identity.</strong> Cursor Helper (Plugin), signed by Anysphere, notarized by Apple. Hash matches the public release.</li>
      <li><strong>Installation path.</strong> /Applications/Cursor.app/Contents/Frameworks/..., the expected location for a vendor-installed Electron application.</li>
      <li><strong>Runtime posture.</strong> Electron framework with sandbox disabled at runtime, which is the documented operating mode for the IDE's plugin host. Not an attacker turning off protections; a vendor design choice.</li>
      <li><strong>Behavioral baseline.</strong> The same binary has been running on this laptop and on dozens of peers on the same team for months. No prior alerts on the binary itself.</li>
    </ul>
    <p class="example-step__what-not"><strong>What an Empire-style attacker would look different on:</strong> the binary would either be unsigned or signed by a key that does not match the vendor; the install path would be in a user-writable directory; the behavioral baseline would show first appearance within the last few days. None of those match.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 4. Check access scope</h3>
    <p>Even when the user, device, and application all read legitimate, Subject has to record what the activity actually had access to. Scope inherits this directly.</p>
    <ul class="example-step__list">
      <li><strong>Privilege level.</strong> Standard user context, no sudo or root elevation, no privilege escalation events in the timeline.</li>
      <li><strong>Sandbox status.</strong> Explicitly disabled, but only for the plugin helper as documented. Other Cursor processes still sandboxed.</li>
      <li><strong>Paths touched.</strong> User home, /tmp, Cursor's application support directory. No system paths, no other users' homes, no credential stores.</li>
      <li><strong>Network destinations.</strong> Cursor's vendor endpoints plus a small number of resolved code-completion model hosts. All previously seen, all signed certs, no DNS anomalies.</li>
    </ul>
    <p>Subject's access-scope verdict: bounded to the user's own profile and to expected vendor infrastructure. That bounds Scope's environmental footprint to roughly the same surface.</p>
  </div>

  <div data-step class="example-step">
    <h3>Step 5. Decide the operational risk</h3>
    <p>The four-dimensions and access-scope checks all return clean. Operational function is the final filter: even when nothing is wrong, the value of the asset informs how much weight Subject gives to remaining ambiguity.</p>
    <ul class="example-step__list">
      <li><strong>Business function.</strong> Daily development of customer-facing software. Code commits multiple times per day.</li>
      <li><strong>Data sensitivity.</strong> Source code, dev secrets, possibly customer-data-adjacent test fixtures. High.</li>
      <li><strong>Lateral movement risk.</strong> Moderate. SSH keys to build environments. Persistent terminal sessions to CI runners.</li>
      <li><strong>Persistence potential.</strong> High. The machine is on every day, with predictable patterns an attacker could blend into.</li>
    </ul>

    <Reveal summary="Subject's verdict and the Scope handoff" variant="example">
      <p><strong>Subject's conclusion:</strong> false-positive with explicit caveats. The activity matches a known Empire-style pattern in the detection logic but is consistent with the documented operating mode of a signed, trusted, role-appropriate application running on a high-trust developer workstation.</p>
      <p><strong>What Subject hands to Scope:</strong></p>
      <ul>
        <li><strong>Primary entities:</strong> the developer, the laptop, the Cursor Helper binary. All read clean across four dimensions.</li>
        <li><strong>Confidence:</strong> high on the binary identity and user behavior. Medium on the runtime posture, because sandbox-disabled behavior is hard to baseline.</li>
        <li><strong>Recommended scope:</strong> narrow. 24-hour time window. Just this host and the user. No peer-group expansion required.</li>
        <li><strong>Open question for Uncover:</strong> are there detection rules that should be tuned for Cursor's plugin-host pattern so this stops firing repeatedly? Yes, but that is improvement work, not investigation work.</li>
        <li><strong>Insider posture:</strong> none observed. Normal behavior for this role.</li>
      </ul>
      <p>This handoff is what a "false-positive" looks like when written properly. Not "dismissed." Documented.</p>
    </Reveal>
  </div>

</ExampleStepper>

</ChapterExample>

<Callout variant="info" title="Two shapes of Subject analysis">
The two scenarios show the two main shapes Subject takes. Sometimes Subject expands the investigation outward (the finance <DefineTerm term="Phishing" display="phishing" /> case) because the named <DefineTerm term="Entity" display="entity" /> is the tip of a much larger pattern. Sometimes Subject contains the investigation inward (the developer case) because the named entity's context explains the activity. Both are correct Subject outcomes. The methodology is the same; the answer differs.
</Callout>

---

<KeyTakeaway>
Subject's verdict is rarely "compromise" or "false-positive" as a binary. It is a structured map of identities with per-dimension assessments and explicit confidence levels. That structure is what lets Scope draw clean boundaries instead of guessing.
</KeyTakeaway>
