The data-sources page tells you where evidence lives. This page teaches what you actually do with it: the mechanics behind sentences like "firewall logs show outbound TLS at 09:11:43, exactly correlated with the PowerShell PID." That correlation did not happen by staring. It happened because two events shared a join key, their clocks were trustworthy enough to order them, and the analyst was testing a specific hypothesis when they ran the query.

## Join keys: how two events meet

Two events from different sources correlate when they share an identifier inside a plausible time window. These are the keys, and each has a trap:

<div class="joinkey-grid">
  <div class="joinkey-card">
    <h3>Host</h3>
    <p>Hostname, asset ID, or agent ID ties endpoint, network, and directory events together.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> IP is not host identity. DHCP reassigns, VPN pools rotate, NAT aggregates. Join on IP only inside a window where you have verified the lease, or prefer the asset ID.</p>
  </div>
  <div class="joinkey-card">
    <h3>User</h3>
    <p>Account name or directory SID joins authentication, endpoint, email, and SaaS events.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> the account is not the person. Shared accounts, service accounts, and a second account for the same human all break the assumption. Subject-phase entity work is what keeps this join honest.</p>
  </div>
  <div class="joinkey-card">
    <h3>Process</h3>
    <p>PID plus host plus time window joins an EDR process event to the network connections and file writes it caused.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> PIDs are recycled. A PID is only unique per boot, per host, while the process lives. Prefer the EDR's globally unique process identifier when the console exposes one.</p>
  </div>
  <div class="joinkey-card">
    <h3>Logon and session IDs</h3>
    <p>Windows logon IDs, IdP session IDs, and cloud session names tie every action inside one session to the authentication that started it.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> sessions outlive credential changes. A reset password does not kill an already-issued session token, so "we reset the account" does not end this join.</p>
  </div>
  <div class="joinkey-card">
    <h3>Network tuple</h3>
    <p>Source IP:port to destination IP:port, inside a time window, joins host telemetry to firewall, proxy, and flow logs.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> proxies and NAT collapse many hosts into one source IP. The proxy log, not the firewall log, holds the original client.</p>
  </div>
  <div class="joinkey-card">
    <h3>Artifact hash</h3>
    <p>A file hash joins sightings across every host and the sandbox report, regardless of filename.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> ubiquity cuts both ways. A hash seen on 4,000 hosts is probably a legitimate binary being abused, not 4,000 infections. Prevalence is context, not a verdict.</p>
  </div>
</div>

## Clock skew: order is evidence, and clocks lie

Whether the login preceded the download or followed it can decide a verdict, so the ordering itself is evidence, and it is only as good as the clocks that produced it.

<div class="clock-rules">
  <div class="clock-rule">
    <span class="clock-rule__num">01</span>
    <p><strong>Normalize everything to UTC first.</strong> Appliances log local time, cloud logs UTC, endpoints follow their user's timezone. A timeline mixing conventions manufactures false sequences. Convert at the moment you copy the event out, not later.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">02</span>
    <p><strong>Use event time, not ingest time.</strong> The SIEM's index timestamp records when the log arrived, and forwarders batch, retry, and fall behind. Sorting by ingest time can order a Tuesday event after a Wednesday one.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">03</span>
    <p><strong>Pick a spine clock.</strong> Choose the best-synchronized source that spans the case (usually EDR or the cloud provider) as the timeline's backbone, and hang other sources' events off it. Note which source provided each timestamp.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">04</span>
    <p><strong>Treat near-ties across sources as unordered.</strong> Two events from different sources a second apart are simultaneous for reasoning purposes unless you have verified both clocks. If a conclusion depends on which came first inside the skew window, the conclusion needs different evidence.</p>
  </div>
</div>

## The timeline is the artifact

Correlated evidence goes into one place: a running timeline you build as you investigate, not a cleanup task performed at the end. Memory does not preserve ordering; the artifact does.

Every entry carries the same fields:

<div class="timeline-shape">
  <div class="timeline-shape__row timeline-shape__row--head">
    <span>Time (UTC)</span><span>Source</span><span>Entity</span><span>What happened</span><span>Confidence</span>
  </div>
  <div class="timeline-shape__row">
    <span>09:02:11</span><span>Email gateway</span><span>dlin</span><span>Delivery of invoice-themed message with attachment</span><span>Confirmed</span>
  </div>
  <div class="timeline-shape__row">
    <span>09:11:41</span><span>EDR</span><span>laptop-finance-09</span><span>powershell.exe spawned with encoded command</span><span>Confirmed</span>
  </div>
  <div class="timeline-shape__row">
    <span>09:11:43</span><span>Firewall</span><span>laptop-finance-09</span><span>Outbound TLS to newly registered domain, joined on host + time to the PowerShell PID</span><span>Corroborated</span>
  </div>
  <div class="timeline-shape__row">
    <span>09:23 onward</span><span>(none)</span><span>cloud finance platform</span><span>No in-app telemetry yet: vendor logs requested but not landed, a gap, not verified quiet</span><span>Gap</span>
  </div>
</div>

Three habits make the artifact trustworthy. Label provenance on every row: confirmed by the source, corroborated across sources, single-source, or inferred. Those labels map onto the shared LOW/MEDIUM/HIGH confidence rubric the <a href="/docs/uncover/transition/">transition page</a> demands at handoff. Record gaps as rows: "no telemetry between X and Y" is a finding, and hiding it makes the narrative look more complete than the evidence is. And never let a row smuggle in a conclusion; "attacker exfiltrated data" is a hypothesis, "7.2 GB outbound to unknown host over 40 minutes" is an event.

## Pivot discipline: the hypothesis ledger

A pivot is a query run to test a hypothesis. That definition is the discipline: if you cannot name the hypothesis your current query tests, you are browsing, not investigating.

The working tool is a hypothesis ledger kept next to the timeline. Each hypothesis gets a line: what you think happened, the evidence for it, the evidence against it, and its status.

<div class="ledger-demo">
  <div class="ledger-row ledger-row--head"><span>Hypothesis</span><span>For</span><span>Against</span><span>Status</span></div>
  <div class="ledger-row"><span>Macro in the attachment launched the PowerShell stage</span><span>winword.exe parent; decode matches cradle</span><span></span><span class="ledger-status ledger-status--supported">Supported</span></div>
  <div class="ledger-row"><span>Attacker moved laterally to a second host</span><span></span><span>No new logons from host; no SMB/WMI to peers in window</span><span class="ledger-status ledger-status--refuted">Refuted</span></div>
  <div class="ledger-row"><span>Cloud finance session was attacker-driven</span><span>Timing proximity to C2</span><span>No token-theft evidence yet</span><span class="ledger-status ledger-status--open">Open</span></div>
</div>

<div class="pivot-rules">
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Cheapest, most specific query first.</strong> The narrow EDR lookup that can kill a hypothesis in one result runs before the broad SIEM sweep. Expensive queries are for windows that cheap queries have already narrowed.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Negative results get recorded.</strong> "Queried DNS logs for the domain across the fleet, zero other hosts" moves a hypothesis to refuted and defends the close later. An unrecorded negative result is work that evaporates.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Refuted stays in the ledger.</strong> The hypothesis you killed is part of the deliverable, the same doctrine that makes a false-positive close a finding rather than a shrug. The Risk phase needs to see what was ruled out, not just what survived.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>New leads become hypotheses, not detours.</strong> Something interesting but unrelated to any open hypothesis gets one ledger line and no queries yet. It is triaged like everything else, not chased because it sparkled.</div>
  </div>
</div>

## When to stop

The intro names rabbit-holes as a defining junior failure, and Uncover is where they happen. Stopping is a rule-driven decision, not a feeling:

<div class="stop-grid">
  <div class="stop-card">
    <h3>🧱 The Scope boundary holds</h3>
    <p>The entity, time, and infrastructure lines drawn in the Scope phase are the outer wall. Evidence pointing past them is grounds for a documented scope expansion decision, not silent drift into new territory.</p>
  </div>
  <div class="stop-card">
    <h3>📉 Marginal return</h3>
    <p>When consecutive pivots stop producing rows for the timeline or movement in the ledger, that thread is going dry — two empty pivots on the same hypothesis is the cue to run the dry-thread checklist below. An empty result only counts as evidence of absence after the checklist says the emptiness is real.</p>
  </div>
  <div class="stop-card">
    <h3>⚖️ Verdict stability</h3>
    <p>When new evidence no longer changes any hypothesis status, Uncover has done its job. More queries buy confidence theater, not confidence. Write the narrative and hand off to Risk.</p>
  </div>
  <div class="stop-card">
    <h3>🚨 An escalation trigger fires</h3>
    <p>Hitting an escalation criterion ends Uncover immediately, mid-thread if necessary. Confirmed active compromise belongs to incident response; continuing to dig solo delays the people who own containment.</p>
  </div>
</div>

<Callout variant="warn" title="Before you call a thread dry: four checks">
An empty pivot is only meaningful if the query could have found something. Before closing a hypothesis on empty results, confirm: <strong>(1) Query validity</strong> — the query ran without error and returns rows for a known-good control (the same query against an entity that definitely has activity). A silently wrong field name looks identical to a clean host. <strong>(2) Telemetry coverage</strong> — the source actually collects for this entity over this window: sensor healthy, log source onboarded, retention reaches back far enough. A coverage gap is a finding to record, not an absence of activity. <strong>(3) Alternatives</strong> — the remaining plausible route for the hypothesis has been queried, not just the first one (a different source, join key, or window that could also confirm it). <strong>(4) Consequence</strong> — what closing this thread wrongly would cost. On a high-impact subject, unresolved uncertainty does not close quietly: record the gap and route it through Risk's override rules, where unknown is not Low. Two empty pivots plus these four checks is a defensible stop. Two empty pivots alone is a guess.
</Callout>

<Callout variant="info" title="The rabbit-hole test">
At any moment you should be able to answer one question: which open hypothesis does the query on my screen test? A clear answer means you are investigating. No answer means you are exploring, and exploring during triage is time taken from the queue. Log the curiosity as a hunt idea and return to the ledger.
</Callout>

<Callout variant="info" title="See it run">
The <a href="/docs/uncover/example/">Uncover worked example</a> is this page in motion: joins on host, PID, and session across EDR, firewall, DNS, and identity sources; negative results recorded; and a benign true positive closed with the same rigor as the intrusion.
</Callout>

<KeyTakeaway>
Correlation is joining events on real keys within honest clocks; the <DefineTerm term="Timeline" display="timeline" /> is the running, confidence-labeled artifact that holds it; the hypothesis ledger keeps every pivot pointed at a question; and the stopping rules end the phase on evidence rather than exhaustion. This is the verb the rest of the chapter's nouns exist to serve.
</KeyTakeaway>
