The data-sources page tells you where evidence lives. This page teaches what you actually do with it: the mechanics behind sentences like "proxy logs show the connection to invoice-records[.]example at 09:11:43, joined to the PowerShell process on host, source port, and time." That correlation did not happen by staring. It happened because two events shared a join key, their clocks were trustworthy enough to order them, and the analyst was testing a specific hypothesis when they ran the query.

## Join keys: how two events meet

Two events from different sources correlate when they share an identifier inside a plausible time window. "Plausible" is a number you state, not a feeling: seconds for sources on the same host or the same network path, a minute or more across organizations or vendors whose clocks you do not control, and always written in the case file. These are the keys, and each has a trap:

<div class="joinkey-grid">
  <div class="joinkey-card">
    <h3>Host</h3>
    <p>Hostname, asset ID, or agent ID ties endpoint, network, and directory events together.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> IP is not host identity. DHCP reassigns, VPN pools rotate, NAT aggregates. Join on IP only inside a window where you have verified the lease, or prefer the asset ID.</p>
  </div>
  <div class="joinkey-card">
    <h3>User</h3>
    <p>Account name or directory SID joins authentication, endpoint, email, and SaaS events. Prefer immutable IDs (AD objectGUID or SID, Entra object ID, Okta user ID) over UPNs, which change on rename, and map each namespace (directory account, UPN, IdP user ID, SaaS principal) once in the case file.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> the account is not the person. Shared accounts, service accounts, and a second account for the same human all break the assumption. Subject-phase entity work is what keeps this join honest.</p>
  </div>
  <div class="joinkey-card">
    <h3>Process</h3>
    <p>PID plus host plus time window joins an EDR process event to the network connections and file writes it caused.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> PIDs are recycled. A PID is only unique per boot, per host, while the process lives. Prefer the EDR's globally unique process identifier when the console exposes one (Sysmon ProcessGuid, Elastic process.entity_id, CrowdStrike TargetProcessId/ContextProcessId).</p>
  </div>
  <div class="joinkey-card">
    <h3>Logon and session IDs</h3>
    <p>Windows logon IDs, IdP session IDs, and cloud session names tie every action inside one session to the authentication that started it.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> sessions outlive credential changes. A password reset does not reliably end existing sessions. Depending on the identity provider and how the session was established, some refresh tokens and session cookies are revoked, but already-issued access tokens live until expiry, non-password-based tokens can survive, and third-party SaaS sessions are not touched at all. "We reset the account" does not end this join; "we revoked sessions everywhere and verified" might. The <a href="/docs/reference/identity-sweep/">identity-persistence sweep</a> lists what to check.</p>
  </div>
  <div class="joinkey-card">
    <h3>Network tuple</h3>
    <p>Source IP:port to destination IP:port, inside a time window, joins host telemetry to firewall, proxy, and flow logs.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> proxies and NAT collapse many hosts into one source IP. Behind a proxy, the proxy log holds the original client; behind NAT, the translating device's session log does (usually the firewall itself, which records pre- and post-NAT source). Logs further downstream see only the shared address.</p>
  </div>
  <div class="joinkey-card">
    <h3>Artifact hash</h3>
    <p>A file hash joins sightings across every host and the sandbox report, regardless of filename.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> ubiquity cuts both ways. A hash seen on 4,000 hosts is probably a legitimate binary being abused, not 4,000 infections. Prevalence is context, not a verdict. And absence cuts too: per-victim builds change the hash, so pivot on fuzzy and structural hashes (imphash, ssdeep, TLSH) or on behavior before calling a sample unique.</p>
  </div>
  <div class="joinkey-card">
    <h3>Message, request, and credential IDs</h3>
    <p>The Internet Message-ID joins the email gateway, the mailbox audit, and the user's report of the same message. Cloud request IDs tie an API call to its errors and follow-on events. An AWS accessKeyId shows whether a call used temporary credentials (ASIA…) or a long-term key (AKIA…). Device IDs join the IdP, MDM, and EDR views of one machine.</p>
    <p class="joinkey-card__trap"><strong>Trap:</strong> these keys name an artifact, not an actor. Every call a key makes shares its ID, and a sender controls the Message-ID it writes. Pair them with a session or host key before you attribute an action to someone.</p>
  </div>
</div>

A join written down looks like this: the EDR network event for the PowerShell process matched to the proxy's record of the same connection, on host and client source port, inside a stated window. The syntax is pseudo-KQL; the shape is the same in SPL or SQL.

<pre><code>{`// EDR network events for the suspect process, joined to proxy logs
edr_network
| where host == "laptop-finance-09" and process_id == 8128
| join kind=inner (proxy_logs | where client_host == "laptop-finance-09")
    on $left.local_port == $right.client_port
| where abs(datetime_diff('second', edr_time, proxy_time)) <= 2   // window: 2 s, same host
| project edr_time, proxy_time, process_name, local_port, request, bytes_out, bytes_in`}</code></pre>

The same shape joins identity to activity. In the replayed-session case (Case C), the identity provider's sign-in log and the tenant audit log meet on the session ID, and a session that acts from a network other than the one it signed in from is the replay:

<pre><code>{`// IdP interactive sign-ins for the account, joined to tenant audit events on session ID
idp_signins
| where user == "rvega" and event_type == "interactive"
| join kind=inner (tenant_audit | where user == "rvega") on session_id
| where audit_client_ip != signin_ip      // same session, different network
| project session_id, signin_time, signin_ip, audit_time, audit_client_ip, operation`}</code></pre>

Run against the case, it returns session S2: issued at 08:53:37 through the proxy address, then acting from 198.51.100.77 from 09:06 onward. One join, two sources, and the replay is a corroborated row rather than a single-source suspicion.

Joins at scale depend on normalization: a schema such as OCSF, ECS, ASIM, or UDM gives the same entity the same field name across sources, which is what lets one query join them.

## Clock skew: order is evidence, and clocks lie

Whether the login preceded the download or followed it can decide a verdict, so the ordering itself is evidence, and it is only as good as the clocks that produced it. Practice: <a href="/docs/labs/#lab-3">Lab 3</a> has a host log and a packet capture of the same exchange exactly five hours apart.

<div class="clock-rules">
  <div class="clock-rule">
    <span class="clock-rule__num">01</span>
    <p><strong>Normalize everything to UTC first.</strong> Sources disagree about what a timestamp means. Classic syslog (RFC 3164) records device local time with no timezone and no year. Windows event logs store UTC, but Event Viewer and many exports display local time. Cloud audit logs are usually UTC. Daylight-saving changes repeat or skip an hour. A timeline mixing conventions manufactures false sequences. Convert at the moment you copy the event out, not later, and note the source's original zone.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">02</span>
    <p><strong>Use event time, not ingest time.</strong> The SIEM's index timestamp records when the log arrived, and forwarders batch, retry, and fall behind. Sorting by ingest time can order a Tuesday event after a Wednesday one. Know the field names: Splunk <code>_time</code> versus <code>_indextime</code>; Microsoft Sentinel <code>TimeGenerated</code> versus <code>ingestion_time()</code> (for some custom tables <code>TimeGenerated</code> is the ingestion time unless a transform sets it); Elastic <code>@timestamp</code> versus <code>event.ingested</code>. If event time equals ingest time on every row, the parser failed and you are looking at arrival order. <a href="/docs/cases/case-d/#alert-an-arrival-not-a-burst">Case D</a> shows what this looks like in an alert: seven hours of sign-ins arriving in 54 seconds.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">03</span>
    <p><strong>Pick a spine clock.</strong> Choose the best-synchronized source that spans the case (usually EDR or the cloud provider) as the timeline's backbone, and hang other sources' events off it. Note which source provided each timestamp.</p>
  </div>
  <div class="clock-rule">
    <span class="clock-rule__num">04</span>
    <p><strong>Treat near-ties across sources as unordered.</strong> Two events from different sources a second apart are simultaneous for reasoning purposes unless you have verified both clocks. If a conclusion depends on which came first inside the skew window, the conclusion needs different evidence.</p>
  </div>
</div>

## The timeline is the artifact

Correlated evidence goes into one place: a running timeline you build as you investigate, not a cleanup task performed at the end. Memory does not preserve ordering; the artifact does.

Every entry carries the same fields:

Three habits make the artifact trustworthy. Label provenance on every row (corroborated, single-source, inferred, or gap), then map it onto the shared <a href="/docs/documentation/standards/#confidence">confidence rubric</a>: corroborated by an independent source with the alternatives tested is HIGH; a single trusted source or strong inference is MEDIUM; circumstantial inference is LOW; a gap gets no label and becomes an open question, which under Risk's unknown-is-not-Low rule lowers confidence rather than likelihood. That is the same scale the handoff to Risk uses, so each row's label travels with it. Record gaps as rows: "no telemetry between X and Y" is a finding, and hiding it makes the narrative look more complete than the evidence is. And never let a row smuggle in a conclusion: "attacker exfiltrated data" is a hypothesis; "7.2 GB outbound to an unknown host over 40 minutes" is an event.

Any tool that keeps these fields will do: the case-management system's timeline, a shared spreadsheet with these six columns, or a super-timeline tool such as Timesketch fed by Plaso when host artifacts run into the thousands. What matters is that it is one artifact, built as you go.

One case, one timeline. When grouped alerts form a single case (the <a href="/docs/fast-path/#correlated-cases">correlated-cases rules</a>), every member's evidence lands on the same timeline and the same ledger, while each member alert keeps its own detection-axis verdict.

## Pivot discipline: the hypothesis ledger

A pivot is a query run to test a hypothesis. That definition is the discipline: if you cannot name the hypothesis your current query tests, you are browsing, not investigating.

The working tool is a hypothesis ledger kept next to the timeline. Each hypothesis gets a line: what you think happened, the evidence for it, the evidence against it, and its status. Open every ledger with at least two hypotheses, one of them the most plausible benign explanation, so the first query has something to discriminate between: a ledger with one line is a conclusion, not a test. A hunt finding arrives with its first line already written (see <a href="/docs/alert/intake/#hunt-findings">Other intake</a>). The ledger below is the finance case's as it stood at 10:35 UTC, before the identity pull.

Refuted on the third line means host-to-host movement only. The identity pivot into the cloud finance platform (ATT&CK T1550.004, which ATT&CK files under Lateral Movement) has its own line, the open one, and it is the movement the escalation criteria count once it is confirmed.

Weigh evidence by diagnosticity, not volume. Evidence that fits every hypothesis (PowerShell ran during business hours, on a finance laptop) moves nothing; evidence that fits only one (a sign-in whose user agent does not match dlin's browser) moves a lot. Before you run a query, name the result that would separate two lines of the ledger; a query whose every possible result fits all of them can wait. The ledger is Analysis of Competing Hypotheses scaled to triage speed; the <a href="/docs/positioning/">positioning page</a> credits the source.

<div class="pivot-rules">
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Cheapest, most specific query first.</strong> The narrow EDR lookup that can kill a hypothesis in one result runs before the broad SIEM sweep. Expensive queries are for windows that cheap queries have already narrowed.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Negative results get recorded.</strong> "Queried proxy and DNS logs for the domain across the fleet (control query against a known-visited domain returned hits): zero other hosts" moves a hypothesis to refuted and defends the close later. The control query matters: behind an explicit proxy, clients never resolve the destination themselves, so client DNS logs would be empty either way. An unrecorded negative result is work that evaporates.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>Refuted stays in the ledger.</strong> The hypothesis you killed is part of the deliverable, the same doctrine that makes a benign close a finding rather than a shrug. The Risk phase needs to see what was ruled out, not just what survived.</div>
  </div>
  <div class="pivot-rule">
    <span class="pivot-rule__bullet"></span>
    <div><strong>New leads become hypotheses, not detours.</strong> A lead that bears on this case gets one ledger line and no queries yet; it is triaged like everything else, not chased because it sparkled. A curiosity that does not bear on this case goes to the hunt backlog.</div>
  </div>
</div>

## When to stop

The intro names rabbit-holes as a defining junior failure, and Uncover is where they happen. Stopping is a rule-driven decision, not a feeling:

<div class="stop-grid">
  <div class="stop-card">
    <h3>The Scope boundary holds</h3>
    <p>The entity, time, and infrastructure lines drawn in the Scope phase are the outer wall. Evidence pointing past them is grounds for a documented scope expansion decision, not silent drift into new territory.</p>
  </div>
  <div class="stop-card">
    <h3>Marginal return</h3>
    <p>When consecutive pivots stop producing rows for the timeline or movement in the ledger, that thread is going dry: two empty pivots on the same hypothesis are the cue to run the dry-thread checklist below. An empty result only counts as evidence of absence after the checklist says the emptiness is real.</p>
  </div>
  <div class="stop-card">
    <h3>Verdict stability</h3>
    <p>When every hypothesis that could change Risk's rating or recommended move is supported, refuted, or recorded as a gap, and the last pivots moved nothing, Uncover has done its job. More queries buy confidence theater, not confidence. Write the narrative and hand off to Risk.</p>
  </div>
  <div class="stop-card">
    <h3>An escalation criterion is confirmed</h3>
    <p>A confirmed escalation criterion ends solo Uncover immediately, mid-thread if necessary: escalate under the escalation tripwire. From then on IR owns the case; the analyst works the open hypotheses only as IR-assigned scoping support, on IR's clock and questions. A suspected criterion becomes an open hypothesis and a Scope question, not a stop. Confirmed active compromise belongs to incident response; continuing to dig solo delays the people who own containment.</p>
  </div>
</div>

<Callout variant="warn" title="Before you call a thread dry: four checks">
<p>An empty pivot is only meaningful if the query could have found something. Before closing a hypothesis on empty results, confirm:</p>
<ol>
  <li><strong>Query validity:</strong> the query ran without error and returns rows for a known-good control (the same query against an entity that definitely has activity). A silently wrong field name looks identical to a clean host.</li>
  <li><strong>Telemetry coverage and depth:</strong> the source collects for this entity across this whole window. The sensor heartbeat is continuous, the log source is onboarded, and retention reaches back far enough. Silence can also be manufactured, so look for tampering (a cleared event log, Windows event 1102 or 104; a sensor that stopped checking in; CloudTrail StopLogging), the behaviors ATT&amp;CK files under Defense Impairment (TA0112). A coverage gap is a finding to record, not an absence of activity.</li>
  <li><strong>Alternatives:</strong> the remaining plausible route for the hypothesis has been queried, not just the first one (a different source, join key, or window that could also confirm it).</li>
  <li><strong>Consequence:</strong> what closing this thread wrongly would cost. On a high-impact subject, unresolved uncertainty does not close quietly: record the gap and route it through Risk's override rules, where unknown is not Low.</li>
</ol>
<p>Two empty pivots plus these four checks is a defensible stop. Two empty pivots alone is a guess.</p>
</Callout>

<Callout variant="info" title="The rabbit-hole test">
At any moment you should be able to answer one question: which open hypothesis does the query on my screen test? A clear answer means you are investigating. No answer means you are exploring, and exploring during triage is time taken from the queue. If it bears on the case, give it a ledger line; if not, log it as a hunt idea. Either way, return to the ledger.
</Callout>

The <a href="/docs/uncover/example/">Uncover worked example</a> is this page in motion: joins on host, source port, and session across EDR, proxy, identity, and tenant audit sources; negative results recorded; and a benign true positive closed with the same rigor as the intrusion.

<KeyTakeaway>
Correlation is joining events on real keys within honest clocks; the <DefineTerm term="Timeline" display="timeline" /> is the running, confidence-labeled artifact that holds it; the hypothesis ledger keeps every pivot pointed at a question; and the stopping rules end the phase on evidence rather than exhaustion. This is the verb the rest of the chapter's nouns exist to serve.
</KeyTakeaway>
