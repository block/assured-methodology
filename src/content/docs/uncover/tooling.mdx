<h2 id="choosing">Choosing the right tool for the question</h2>

Pick the tool from the question, never the other way around. The pattern is always the same:

<div class="choose-flow">
  <div class="choose-step">
    <span class="choose-step__num">01</span>
    <p><strong>Start with the question.</strong> What does the analyst actually need to know? "Did this binary run?" "Did this user authenticate to that system?" "Where did this traffic go?"</p>
  </div>
  <div class="choose-step">
    <span class="choose-step__num">02</span>
    <p><strong>Identify which tool category can answer it.</strong> EDR for process execution. Identity logs for authentication. Network analysis for traffic destination. The mapping is learned deliberately and becomes reflex with practice.</p>
  </div>
  <div class="choose-step">
    <span class="choose-step__num">03</span>
    <p><strong>Plan the query order.</strong> If the answer requires multiple sources, run the cheapest or most specific query first. SIEM queries that scan everything can wait until the EDR query has narrowed the window.</p>
  </div>
  <div class="choose-step">
    <span class="choose-step__num">04</span>
    <p><strong>Document tools and queries used.</strong> Audit trail matters for the handoff to Risk, for detection engineering feedback, and for compliance review later.</p>
  </div>
</div>

The mapping, written down:

| Question | First stop | Caveat |
|---|---|---|
| Did it run? | EDR process events (or Sysmon event 1, Windows Security 4688) | Retention window; check sensor health before reading silence as clean |
| Who authenticated, and from where? | IdP sign-in logs (or Windows Security 4624) | A replayed session needs no new sign-in |
| Where did this traffic go? | Proxy and firewall logs, network analysis | Behind a proxy, the firewall sees the proxy, not the host |
| Did data leave? | Proxy, DLP, cloud data events | Prove it where the data crosses a boundary you can observe |
| Is this file or URL malicious? | Hash lookup in the TIP, then a private sandbox | A clean run is weak evidence of benign |
| What changed in the cloud? | CloudTrail and its equivalents, CDR | Data events are often off by default |
| Who received this email, and who clicked? | Message trace, gateway click records | Sent Items can be cleaned; the trace and the audit log cannot |
| Did this happen anywhere else? | SIEM, or the data lake for older windows | Ingest lag and parser failures look like absence |
| Do these alerts belong together? | The XDR incident, then your own join | Check the join keys behind the stitch before inheriting it |
| Is someone abusing an identity, not a machine? | ITDR, IdP risk and audit logs | Tokens already issued to third-party SaaS can outlive a revocation |
| Is someone exploring where nobody legitimate should be? | Deception alerts | Scanners and inventory tools touch decoys too; exclude them at deployment |
| Was this system exposed to what the attacker used? | Vulnerability scanner, with KEV and EPSS | Agentless scans are point-in-time |
| Could the cloud configuration have allowed this? | CSPM | Configuration is not activity; confirm use in the audit log |
| What exactly happened on this host, in a form that holds up? | Targeted collection (Velociraptor, KAPE), then the forensics team | Collection can destroy evidence; <a href="/docs/escalation/preserve/">preserve first</a> |
| What did an AI assistant or agent do? | <a href="/docs/uncover/data-sources/#ai-agents">Agent action and tool-call logs</a>, MCP gateway logs | The assistant's own summary is not evidence of what it ran |

Each family's capabilities and limits are on the [Tool families](/docs/field-reference/tool-families/) reference page.

## The tool families

Fifteen families cover the Uncover phase, each answering a class of question. What each one sees, and where it goes blind, is on the [Tool families](/docs/field-reference/tool-families/) reference page; the <a href="/docs/glossaries/cat/">C.A.T. glossary</a> carries the vendor detail.

<div class="tool-grid">
  <a id="siem" href="/docs/field-reference/tool-families/#siem" class="tool-card"><h3>SIEM</h3><p>Centralized log search and correlation. The investigation's primary query window.</p></a>
  <a id="edr" href="/docs/field-reference/tool-families/#edr" class="tool-card"><h3>EDR</h3><p>Process trees, command lines, on-host containment.</p></a>
  <a id="xdr" href="/docs/field-reference/tool-families/#xdr" class="tool-card"><h3>XDR</h3><p>Vendor-stitched correlation across endpoint, identity, email, cloud.</p></a>
  <a id="itdr" href="/docs/field-reference/tool-families/#itdr" class="tool-card"><h3>ITDR</h3><p>Attacks on the identity plane: directories, IdPs, tokens, sessions.</p></a>
  <a id="network" href="/docs/field-reference/tool-families/#network" class="tool-card"><h3>Network analysis</h3><p>Wire-level observation. Catches what endpoint cannot.</p></a>
  <a id="ti" href="/docs/field-reference/tool-families/#ti" class="tool-card"><h3>Threat intelligence</h3><p>Enrichment and hypothesis generation.</p></a>
  <a id="deception" href="/docs/field-reference/tool-families/#deception" class="tool-card"><h3>Deception</h3><p>Anything that touches deception is suspicious by definition.</p></a>
  <a id="forensics" href="/docs/field-reference/tool-families/#forensics" class="tool-card"><h3>Digital forensics</h3><p>Deep host analysis for confirmed cases.</p></a>
  <a id="sandbox" href="/docs/field-reference/tool-families/#sandbox" class="tool-card"><h3>Sandbox / detonation</h3><p>Run the suspicious thing safely and watch what it does.</p></a>
  <a id="vuln" href="/docs/field-reference/tool-families/#vuln" class="tool-card"><h3>Vulnerability scanners</h3><p>What is exposed and what is patched.</p></a>
  <a id="soar" href="/docs/field-reference/tool-families/#soar" class="tool-card"><h3>SOAR</h3><p>Playbook execution and triage automation.</p></a>
  <a id="cspm" href="/docs/field-reference/tool-families/#cspm" class="tool-card"><h3>CSPM</h3><p>Cloud misconfiguration and exposure visibility.</p></a>
  <a id="cdr" href="/docs/field-reference/tool-families/#cdr" class="tool-card"><h3>CDR</h3><p>Runtime cloud detection: control-plane and workload activity, live.</p></a>
  <a id="lake" href="/docs/field-reference/tool-families/#lake" class="tool-card"><h3>Data lake</h3><p>Scalable retention and ML-friendly analytics.</p></a>
  <a id="ai" href="/docs/field-reference/tool-families/#ai" class="tool-card"><h3>AI assistants and agents</h3><p>Drafting, enrichment, and query generation, under the admission gate.</p></a>
</div>

For hands-on practice with a SIEM (Splunk) and network analysis (Security Onion), the <a href="/docs/labs/">telemetry labs</a> run one lab per phase on public attack data. AI assistants and agents, including the LLM agents SOAR platforms now embed beside their deterministic playbooks, work under the <a href="/docs/ai-triage/#before-the-first-prompt-the-admission-gate">admission gate</a> on the <a href="/docs/ai-triage/">AI-assisted triage</a> page.

<KeyTakeaway>
Tools serve the question, not the other way around. Strong analysts learn the question-to-tool mapping deliberately and reach for the right one at the right step. The common failure is running the same SIEM query against every alert and hoping. The methodology asks for the deliberate choice every time.
</KeyTakeaway>
